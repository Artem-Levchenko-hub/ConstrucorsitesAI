new submission created2965379 once. MAX menu refresh restored the old receipt;
full tab reload/reopen lost the form confirmation entirely. Both remained in
history. The actual component reproduced both defects when its session context
was replaced: a new succeeded intent and a new unknown intent reverted to legacy
success. This identifies a storage-lifetime gap; it does not establish every
internal detail of MAX embedding.

The candidate stores whitelisted receipt key/ID/digests and adoption marker in
origin-scoped `localStorage`, further scoped by genuine MAX actor and mode.
It stores no form name/phone/email/comment, CRM history, tokens or credentials.
Validated old scoped `sessionStorage` pending/success is copied once, with extra
fields stripped and every present digest independently validated. A persistent
`null` tombstone prevents a deliberately cleared receipt from re-importing an
old session success. The global `lead_idempotency_key` is never written/deleted.

An absent global key after reopen uses only the durable scoped adoption marker;
that marker is still matched to the exact authenticated read-only server receipt
on each mount. An existing contradictory global key or server mismatch blocks
submission. Current success is revalidated by exact authenticated key/ID/digest lookup and lead status before
rendering. Missing, rejected, ambiguous, malformed or mismatched legacy receipts
remain quarantined. No create request is sent to recover an identity.

Exclusive Web Locks serialize adoption, consent/dispatch and explicit New/reset
for the same scope across component instances/tabs. Missing locks or denied
storage fail closed for submission; readonly preview remains available. On
actor/unmount the lifetime becomes inactive before abort releases the lock; late
SDK callbacks cannot overwrite or populate a new actor instance. Pending key,
fingerprint, attempted flag and marker/success CAS checks remain required.
Unknown outcomes first try readonly exact-key recovery, keep the same key when unconfirmed, and allow only identical payload replay;
later422 cannot clear a prior unknown, and New is permitted only after a verified
success. History focus/visibility refresh and server checked_at remain unchanged.

Origin storage may still be cleared or partitioned by a browser. Verify real MAX
menu refresh and full tab reload/reopen before claiming live durability. If an
old new-intent key was already lost everywhere, this fix cannot reconstruct it

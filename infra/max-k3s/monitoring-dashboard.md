# Мониторинг Yleum

Админ-центр загружает каталог и данные из `/api/admin/monitoring`. Маршруты чтения принимают сессию администратора платформы или отдельного наблюдателя мониторинга. Каталог сохраняет номера исходных 93 метрик. Источники можно включать поэтапно. У каждой метрики есть собственное состояние, поэтому пустые значения и ошибки подключения видны в интерфейсе.


## Отдельный вход наблюдателя

Для наблюдателя используется `/monitoring/login`. Его сессия действует восемь часов, хранится в Redis и даёт доступ только к дашборду и его маршрутам чтения. Выход отзывает текущую сессию. При смене хэша предыдущие сессии перестают приниматься.

Аккаунт включается переменными `MONITORING_VIEWER_USERNAME` и `MONITORING_VIEWER_PASSWORD_HASH` в production compose API. Имя входа по умолчанию `monitoring`. Хэш формируется через `yleum_api.core.security.hash_password` по паролю, полученному из закрытого хранилища. Сохраните хэш как одинарно-кавычное значение в production `.env`, чтобы Compose сохранил символы `$` в bcrypt. Пустой хэш отключает вход; при его настройке или ротации применяется штатная выкладка API.

## Источники

- PostgreSQL предоставляет журнал генераций, вызовы провайдеров, отчёты редактора и посещения MAX. Значения по типам генерации используют сохранённый тип из резерва единиц. Исторические данные без типа могут попадать в строку «тип неизвестен».
- Сбор активности редактора добавляет одну запись на пользователя, приложение, версию интерфейса и минуту. События содержат флаги открытия, активности или ошибки. Для сеанса используется пауза в 30 минут, а активные минуты соседних вкладок объединяются.
- `MONITORING_PROMETHEUS_URL` указывает на внутренний Service `monitoring-prometheus` на core. Старый адрес нельзя переносить при пересоздании Service с новым ClusterIP. Для зарегистрированных клиентских целей сборщик должен получать доверенные метки `vps`, `client_id` и `deploy_target_id`. Имена core, runtime и commerce относятся к инфраструктуре платформы. Они доступны в фильтре VPS и не входят в счётчик клиентских целей.
- Платформенный `node_exporter` слушает только адрес WireGuard. На каждом из трёх узлов `install-monitoring-host.sh` подключает textfile collector с системным таймером. Он публикует выбранный ядром внешний сетевой интерфейс и состояние ночных бэкапов по квитанциям `HOST-SNAPSHOT.json`. Время последнего успешно сформированного снимка не означает подтверждение тестового восстановления. Ранние окна без истории квитанций не считаются пропущенными.
- Задержка чтения/записи строится по логарифмическим гистограммам завершённых блочных операций. Системный сервис bpftrace публикует bucket-счётчики по физическим устройствам и направлению. Нужны bpftrace и BTF ядра. Устаревшая экспозиция не участвует в расчёте.
- Узел commerce каждые 30 секунд проверяет публичный `https://yleum.ru/api/health` и готовность воркера генерации. Запрос не создаёт генерацию. Контрольная точка измеряет доступность платформенного сервиса, а новые клиентские VPS требуют собственной внешней проверки.
- Сбор HTTP и SQL выполняется через `GET /internal/monitoring/metrics` на loopback core с Bearer-аутентификацией. Узловой таймер передаёт сохранённую экспозицию в приватный `node_exporter`. При ошибке чтения он удаляет предыдущую копию. Запрос без токена получает 404. Внешний порт для API-сбора не нужен.
- Для предпросмотра используются отметки времени проверенного изображения рабочей среды или версии. Восстановленные позднее скриншоты не участвуют. У старых записей без отметки времени историческое измерение отсутствует.
- Метрики публикаций читают терминальные записи контроллеров по проектам, включая первый успешный выпуск и привязанные операции восстановления. Проверки уже опубликованной версии, изменения конфигурации без нового релиза и отказы до постановки в очередь исключены. В журнал дашборда не передаются приватные параметры, URL и тексты ошибок.
- Связанные автоматические повторы провайдеров считаются по `generation_provider_attempts`. История охватывает задачи с этим журналом.

## Включение в production

1. На core дождаться освобождения замка production-релиза. Получить ClusterIP командой `kubectl -n monitoring get svc monitoring-prometheus -o jsonpath='{.spec.clusterIP}'`. Из действующего контейнера API проверить `http://<ClusterIP>:9090/-/ready`.
2. Через `infra/release/update-env-value.sh` записать URL в `MONITORING_PROMETHEUS_URL` production-файла `/opt/omnia/apps/llm-gateway/deploy/full/.env`. Один раз сгенерировать 32 случайных байта в hex и передать их тому же скрипту через stdin для `MONITORING_SCRAPE_TOKEN`. Сохранить существующий токен при повторной установке. Не выводить его в журнал и не вносить в Git.
3. Выкатить проверенную ревизию штатным `infra/release/deploy-prod.sh <sha> --no-web`, если в интервале релиза нет изменений web. Скрипт production использует основную compose-конфигурацию.
4. На каждом узле из проверенной ревизии выполнить `sudo bash infra/max-k3s/install-monitoring-host.sh <core|runtime|commerce>`. На core установщик читает токен из production compose env и переносит его в закрытый credential-файл systemd. Автоматической ротации нет. При ротации повторить шаги 2–4 на core.
5. Проверить таймеры и цели: `systemctl status yleum-monitoring-host.timer`, `up{job="node-exporter"}`, `node_textfile_scrape_error`. Затем сверить сетевые и backup-серии всех трёх узлов, внешнюю пробу core, счётчики HTTP/SQL и панели дашборда. Не использовать второй раз полный host provisioner только ради включения сборщика.

## Проверка выпуска

Выкладка платформы выполняется по [production runbook](../release/README.md). Перед подключением Prometheus проверить `/-/ready`, перечень целей и тестовый запрос из контейнера API. После выпуска проверить `/api/health`, запрет анонимного доступа к каталогу, вход в админ-центр, наличие 93 метрик и соответствие контрольных значений PostgreSQL и Prometheus. Новый источник принимать по контрольному событию и его появлению в конкретной метрике.

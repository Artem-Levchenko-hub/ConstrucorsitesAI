## 6. Что остаётся закончить в текущей работе

1. **Передать идентичный архив внутри серверной сети.** Для нового scratch-target
   047 подготовлен отдельный upload. Требуются настоящие сборка его точных
   framing-байтов на Core и mesh-передача, затем полный stage-result. Прежний
   частичный target 73a не переиспользовать и не считать завершённым.
2. **Восстановить PostgreSQL.** Оригинальные роли, платформенная/пользовательская
   базы и каждый включённый cell-dump должны восстановиться в одноразовые базы.
   Сверить ошибки SQL, схему, владельцев и write/restart проверки harness.
3. **Восстановить и проверить MinIO.** Текущий harness поднимает архив и проверяет
   GET/hash одного заранее известного существующего объекта после рестарта.
   Этот ограниченный тест ещё нужно выполнить. Полная сверка всех объектов —
   отдельная недоделанная проверка для следующей штатной копии.
4. **Опубликовать честное доказательство восстановления.** Сопоставить настоящие
   receipts, коды завершения worker, coverage, ключ получателя и хеш копии.
   RESTORE_TEST.json создаётся только после успешного validator; прежние
   квитанции и canonical-объекты не перезаписываются.
5. **Проверить свежую внешнюю копию.** После proof запустить штатный offhost
   workflow и убедиться, что он скачал именно CMS 104532 и принял её proof.
6. **Переключить старые host pre-шаги.** Сначала замкнуть соответствие новой
   копии всем прежним хранилищам; затем сохранить и убрать только три точных
   drop-in, вернуть таймеры и выполнить настоящий backup/push на каждом узле.
7. **Выложить последние исправления.** Один штатный deploy-prod, затем сверка
   ревизий, health, gateway, данных и отсутствия забытых ограничений.
8. **Повторить полный backup обычным новым запуском.** Историческое продолжение
   104532 не доказывает, что обновлённая автоматическая цепочка теперь целиком
   проходит от старта службы до внешней копии и восстановления.
9. **Проверить следующий автоматический запуск и предупреждения.** Получить
   фактическую квитанцию следующего цикла; ошибка должна быть видна владельцу.

Отдельный незакрытый пробел: автоматический производитель restore-proof для
каждой новой копии пока не настроен. Одна ручная успешная приёмка не обеспечит
прохождение будущих ночных restore-gates. Для этого нужен отдельный доверенный
offhost-проверяющий процесс с локальным доступом к ключу; при выключенном
компьютере проверка должна честно оставаться ожидающей, а не становиться зелёной.
Ещё один пробел — полный ожидаемый inventory объектов MinIO и его сверка после
восстановления. Текущий witness одного объекта этого не доказывает; scope proof
должен явно сохранять это ограничение.

## 8. Достаточно ли снимков у провайдера

Снимки VPS полезны для быстрого возврата всего диска. Для нашей задачи разумны
два самостоятельных пути: снимок провайдера для быстрого восстановления VPS и
переносимая зашифрованная копия для восстановления на других мощностях.

Для PostgreSQL обычное копирование меняющихся файлов не равно согласованному
снимку. Настоящий frozen snapshot должен включать данные и WAL; для нескольких
томов важна одновременность. Это прямо описано в
[официальной документации PostgreSQL](https://www.postgresql.org/docs/current/backup-file.html).
Даже корректные отдельные снимки трёх VPS ещё не доказывают согласованность
связей между базами, объектами и публикациями приложения.

По открытому [сайту serverum.ru](https://serverum.ru/) в этой проверке не удалось
подтвердить точные гарантии snapshot/export/restore для нашего тарифа. Это не
означает отсутствия функции. Требуется проверить в кабинете или получить
официальные условия: какие диски входят, можно ли создать новый VPS из снимка,
сохраняется ли копия после удаления VPS, доступен ли экспорт, где она хранится,
каковы срок хранения и время восстановления. Материалы serverum.com не
используются как подтверждение возможностей serverum.ru.

Snapshot ID без успешного восстановления в отдельный VPS будет считаться
«снимок создан», а не «аварийное восстановление проверено».

## 9. Независимость от IP и восстановление одной командой

Уже существует отдельный [draft PR №99](https://github.com/Artem-Levchenko-hub/ConstrucorsitesAI/pull/99),
head 8fc135321600d11a26a878bac222963e95a28160. На момент проверки он открыт,
не объединён с main и не выложен. В нём есть основа contracts/profile/storage/
release_bundle и локальная Windows-защита ключа. В описании зафиксированы
133 локальных теста; в этом продолжении они заново не запускались.

Остаток PR №99 включает полные export/import трёх ролей, исполняемый runner,
Windows-кнопку, отдельный CI и учение на трёх чистых VPS. Нельзя создавать
вторую параллельную основу: сначала сверить этот PR с актуальным backup v2.
Проверка разблокировки профиля на втором физическом компьютере обязательна.

«Без привязки к старому IP» означает: роль сервера хранится отдельно от текущего
адреса, новые SSH endpoints задаются в защищённом профиле, а runner обновляет
маршруты, сетевые разрешения, DNS и сертификаты. Какие-то адреса всё равно
существуют; автоматизация должна управлять ими. API Serverum не является
обязательным условием: первый штатный путь может принимать SSH-доступы к уже
созданным трём VPS. Старые IP и текстовые подстановки по всему репозиторию не
должны быть источником конфигурации.

При аварии восстанавливается точная версия, связанная с копией, а не случайный
свежий main. Обновление продукта после восстановления — отдельная доставка.

## 10. Потеря последних данных и время восстановления

Ежедневная копия возвращает состояние на момент её создания. При потере всех
серверов она сама по себе не гарантирует сохранение записей, подтверждённых
позже. Сейчас нулевую потерю данных и восстановление за несколько минут
объявлять нельзя: соответствующего учения не было.

Для сокращения потери последних записей нужен отдельный этап: base backup и
непрерывная архивация WAL во внешнее хранилище, проверка непрерывности и
восстановления на выбранный момент. Логические SQL-dumps нельзя просто
«докрутить WAL»: это разные форматы восстановления, как объясняет
[PostgreSQL PITR](https://www.postgresql.org/docs/current/continuous-archiving.html).
Для строгой гарантии сохранения подтверждённых записей при потере всей площадки
нужно отдельно спроектировать удалённое подтверждение долговечности для баз и
файлов; одно расписание резервирования этого не обеспечивает.

Время измерять отдельно: подготовка VPS → сеть → скачивание → расшифровка →
restore → запуск → проверка → переключение. Плановый перенос с заранее готовыми
мощностями и холодное восстановление после потери всех VPS — разные замеры.
Цель «две минуты» ранее обсуждалась для выкладки новой версии и пока тоже не
подтверждена.

## 11. Как сделать систему проще и надёжнее

- Один штатный runner вместо новых несвязанных helper-скриптов для каждого
  инцидента. Сохранённый журнал этапов позволяет продолжить тот же запуск.
- Проверять размер, свободное место, исходные байты команды, host keys,
  производительность передачи и ожидаемое время до начала тяжёлой операции.
- Передавать большие файлы напрямую по проверенному серверному каналу;
  при переносе за другую площадку — независимое внешнее хранилище с проверкой
  полного ciphertext после скачивания. Промежуточный компьютер нужен для
  локального ключа, но не обязан дважды передавать все данные через медленный WAN.
- Копировать и публиковать без перезаписи прежних объектов. Семантика
  If-None-Match описана в [S3 conditional writes](https://docs.aws.amazon.com/AmazonS3/latest/userguide/conditional-writes.html),
  но её поведение на нашем MinIO требуется измерять настоящим запросом.
- Защиту от удаления/перезаписи на уровне хранилища рассматривать отдельно:
  [S3 Object Lock](https://docs.aws.amazon.com/AmazonS3/latest/userguide/object-lock.html)
  требует versioning и относится к конкретным версиям объектов. Здесь не
  утверждается, что Object Lock уже включён или доступен в текущем MinIO.
- Разделить права: сборщик может создавать новые копии, restore-оператор —
  читать/расшифровывать, очистка истории — отдельная ограниченная роль.
- В интерфейсе и мониторинге различать «создана», «загружена», «расшифрована»,
  «восстановлена» и «все три роли запущены». Один зелёный значок этого не заменяет.

## 12. Что будет означать «готово»

Текущее резервирование принято, когда один новый штатный backup-run завершился
успешно, новая CMS сохранена вне всей VPS-площадки, та же CMS действительно
расшифрована и восстановлена в изолированной среде с полной ожидаемой сверкой
объектов MinIO, proof связан с точным
файлом, старые копии сохранены, host backup/push прошли, последние исправления
доставлены и следующий автоматический цикл подтвердился. Для заявления об
автоматической регулярной проверке требуется действующий offhost restore-runner,
а не одна ручная квитанция.

Полное восстановление одной командой принято только после отдельного учения
на трёх чистых VPS: возвращены настройки, данные, образы, владельцы, доступ и
работающие службы, измерены потери/время и проверено безопасное продолжение
после прерванного этапа. Пользовательский путь остаётся отдельной отложенной
приёмкой. Ни один из этих двух результатов на момент среза не объявлен готовым.

## 13. Где лежат доказательства и что вошло в этот коммит

Публичный [индекс доказательств](evidence-index.json) содержит только имена
операторских записей, SHA-256, времена и ограниченные итоги. Полные локальные
QA-материалы находятся в qa-evidence/release-resume-20261021 в рабочем каталоге
инженера; приватные архивы и PEM находятся отдельно от репозитория.

Этот коммит сохраняет отчёт, план, безопасный индекс и ссылку из прежнего
LaunchAudit. Одноразовые helper-скрипты, полные выгрузки состояния, закрытые
ключи, SQL, расшифрованные архивы и доступы в GitHub этим коммитом не добавляются.
Проверенные продуктовые исправления уже содержатся в ae2851aa. QA-only helpers
с закреплёнными nonce/хостами не выдаются за готовую переносимую команду.

# Устойчивость генерации: контракт SDK и адресное исправление ошибок

Дата: 3 ноября 2026. Пользователь поручил автономно исследовать, реализовать и проверить устойчивость генерации, включая полноценный пользовательский тест. Технические решения ниже — выбор исполнителя в пределах этого поручения.

## Наблюдаемый отказ

На API/controller `40b291ee` и web `884cfeec` новый QA-проект получил три подтверждённые позиции из описания. Каталог и обычные сохранения работали. Первая генерация закончилась отказом через 20м01с/39 шагов. Проверки TypeScript обнаружили `YleumAppProfile.name` и затем семь обращений к `YleumMaxContentItem.name`; действительные поля — `app_name` и `title`. Рабочая версия не была принята. Не доказано, что каждая задержка вызвана именно этими ошибками.

## Подходы и решение

1. Усилить только общий prompt: небольшой объём, но инструкция может потеряться при выборе окружения и не даёт свежих данных для ремонта.
2. Ограничить продукт готовыми экранами: меньше свободы генератора, зато существенно меняет продукт и требует отдельного переустройства.
3. Сохранить генерируемый интерфейс, закрепив обязательный SDK-контракт, свежую диагностическую обратную связь и существующие проверки приёмки. Выбран этот вариант как законченный проверяемый срез.

## Цель и границы

Обязательный контракт должен доходить до фактического запроса модели во всех поддерживаемых маршрутах. Подтверждённая ошибка исходников должна возвращать точные диагностики, текущий затронутый код и нужное объявление типа SDK. Успех остаётся результатом действующих gates, а не обещанием модели.

Не менять модели, цены, квоты, роли, права, бизнес-данные, семантику реставрации или схему БД. Не отключать TypeScript, не исправлять ошибки через `any`/подавления и не делать глобальную замену `name`. Не увеличивать сроки или число попыток без отдельного доказательства недостаточности существующих бюджетов. Память проекта не заменяет обязательный контракт.

## Обязательный контекст

- Выделить из `MAX_MODEL_DIRECTIVE` один компактный `MAX_MANAGED_SDK_GUIDANCE` с фактическими profile/catalog/selection/business API и корректным JSX-примером.
- Добавлять этот блок после выбора provider guide в `build_max_agent_guide`, ровно один раз. Не возвращать в portable-окружение несовместимые старые инструкции sandbox/network/install.
- Свести относящиеся к этому блоку дубли в существующем directive. Обязательные правила frozen intents, quote confirmation, личной истории, loading/error/empty сохраняются.
- Проверять итоговые prompts и запросы injected provider без сети; отдельно сверять пример с настоящими TypeScript-типами шаблона.
- Не менять уже закреплённый запрос незавершённой durable provider attempt при recovery.

## Адресная обратная связь

- Общая точка: `generation.agent_runtime.checked_fast_check`. Использовать существующую `coordinator.source_failure(result)`, проверяющую owner, terminal receipt и актуальность source digest.
- Только подтверждённый source failure получает bounded repair context. Infrastructure, неизвестная причина, stale receipt или иной owner новых прав/контекста не получают.
- Контекст формируется из текущего owned snapshot: locations диагностик, ограниченные релевантные участки изменяемых исходников, точные объявления распознанных SDK-типов. Для наблюдаемого случая — `YleumAppProfile` и `YleumMaxContentItem`.
- Из `max-config.ts` разрешены только объявления типов; значения конфигурации и весь файл не копировать. Использовать существующую secret redaction; неизвестный/слишком большой материал честно обозначать как omitted/incomplete.
- Один renderer для model-facing observations должен сохранить полезный repair context в legacy, native explicit build и native automatic early build. Короткий UI preview остаётся отдельным.
- Обратная связь не является доказательством прогресса и не пополняет step/read/repair/deadline allowances. Повторный red check использует новый snapshot, не старый cached context.

## Бюджеты и безопасность

Существуют проверяемые source changes, loop breakers, source/proof invalidation и резерв финализации (initial 300s/repair 180s). Сохранить эти механизмы и их регрессии. Не подменять source_failure классификацию поиском строки TS в произвольном логе. Изолировать тестовые данные и процессы; не выполнять fixture DB tests на production.

## Дополнение пользователя: справка и быстрый старт

Параллельно исправить наблюдаемое отсутствие ответа на «Создать прилржение». Использовать лёгкое детерминированное сопоставление с нормализацией русского текста, ограниченной устойчивостью к опечаткам и проверками против ложных совпадений; не добавлять платные AI-вызовы или тяжёлую NLP-зависимость.

Карточки `/max/start`: акцент на следующем действии «Подробная инструкция», компактная вторичная информация вместо рамки «Результат этапа». ## Приёмка

- RED→GREEN для portable guide replacement и всех build/edit/native prompts; правильные поля и бизнес-контракт присутствуют один раз.
- Compiler repair context переживает observation/UI caps, доходит до первого следующего реального provider boundary без сети и обновляется после изменения исходника.
- Infrastructure/stale/mismatched receipt, secrets, oversized/unknown source не расширяют полномочия и не дают ложного green.
- Существующие source-progress, deadline, cancellation, recovery и acceptance tests остаются зелёными.
- Независимый read-only review всего diff, обязательные lint/types/tests/CI; затем intended commit, upstream push, documented production deploy и точная проверка ревизии/health.
- Live: отдельный QA-проект, позиции прямо в описании → подтверждённый каталог → принятая первая сборка → работающий экран → изменение названия/цены, новая позиция и скрытие без AI/перепубликации → refresh/reopen. Заказ/история/owner status проверяются на документированном тестовом назначении без вмешательства в существующие приложения.
- Для оценки повторяемости нужен ещё один самостоятельный новый initial build. Отдельно фиксировать первый успех, длительность и число попыток; два успеха не являются доказательством 99% или 100% надёжности.

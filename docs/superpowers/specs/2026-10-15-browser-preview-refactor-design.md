# Превью без MAX и рефакторинг Yleum

Дата: 15 октября 2026. Согласован подход: развивать существующий механизм превью отдельными проверяемыми поставками. Этот проект описывает поведение и границы реализации; функции ниже ещё не реализованы.

## Результат для пользователя

Владелец открывает приложение в редакторе или по постоянному адресу просмотра после входа в Yleum. Установка MAX, создание бота и публикация для этого не нужны. Гость получает отдельную ссылку и может проверять действия на изолированных демо-данных. Оплаты и внешние отправки в гостевом режиме запрещены сервером.

«Превью всегда доступно» означает: если существует принятая сборка и доступна инфраструктура, её можно открыть без MAX; новая генерация не подменяет и не останавливает этот результат. До первой принятой сборки показывается понятное состояние подготовки. При отказе инфраструктуры показываются причина, состояние восстановления и действие повтора; не обещается изображение несуществующего приложения или абсолютная доступность при любом отказе.

## Выбранная архитектура

Сохраняются текущие API, orchestrator, managed core и механизмы сборки/запуска артефактов. Новый самостоятельный сервис превью и новый универсальный движок генерации не создаются. Внутри существующего контура разделяются три назначения runtime:

1. **Candidate** — изменяемая среда генерации. Она не обслуживает закреплённое принятое превью.
2. **Owner preview** — принятый артефакт, доступный проверенному владельцу через оболочку Yleum.
3. **Guest demo** — тот же выбранный принятый артефакт, отдельная демо-БД, отдельные учётные данные и гостевые identities.

Назначение runtime входит в его проверяемую identity и область ingress/credentials. Нельзя получить доступ к другому назначению заменой URL, project ID или параметра запроса.

### Закрепление версии

Превью связывается с `project_id`, `snapshot_id`, source revision, digest собранного артефакта, schema digest и `serving_epoch`. Эти значения проверяются перед выдачей сессии, запуском и подтверждением готовности.

Принятая сборка запускается из sealed environment artifact, а не из editable volume агента. Переиспользуются проверка и восстановление артефактов из `machine_adapter.py`, `cell_publication.py` и `MachineEnvironmentStore`; пользовательский шаг публикации при этом не вызывается. Если нужного принятого артефакта нет, подготовка выполняется из сохранённого принятого snapshot без модели и проходит необходимую сборку/проверку. Seed snapshot или последнее HTTP 200 не заменяют доказательство принятой версии.

Candidate и принятое превью имеют разные serving targets. Пока новая версия строится или отвергнута, owner preview сохраняет прежний target. После принятия новая версия сначала запускается и проверяется, затем выполняется fenced переключение. UI указывает фактически показанную версию. Старый результат не называется новой готовой версией.

Candidate также имеет отдельную БД и credentials: DDL, seed или ошибочный SQL агента не выполняются на принятом preview dataset или public DB. Проверка candidate использует схему и синтетические данные. Переход принятого owner dataset на новую схему выполняет только доверенный coordinator после проверенной копии, restore rehearsal и подтверждения совместимости. Неподтверждённый переход оставляет прежний код и данные доступными. Для несовместимого перехода старые записи переносятся в новый target после краткого fencing записей, сверяются, затем атомарно меняется serving identity; запрос во время fencing не получает ложного подтверждения сохранения. При отказе до переключения сохраняется прежняя пара «артефакт и dataset». Этот проект не меняет схему рабочей public DB.

Гостевая ссылка по умолчанию закреплена за версией, выбранной при создании. Новая генерация не обновляет её молча. Создание ссылки на новую версию — явное действие владельца. Удаление проекта или недоступность сохранённого артефакта закрывает соответствующие ссылки, а не переключает их на другой проект или candidate.

### Просмотр владельца

Постоянный адрес: `/max/{project_id}/preview`. Страница требует обычный вход Yleum и проверку владельца. Она содержит доверенную оболочку и iframe приложения; отдельная вкладка больше не зависит от `window.opener` или открытого редактора.

Один контроллер подготовки владеет текущей identity и последовательностью «определить версию → подготовить/разбудить runtime → проверить привязку → создать сессию → подтвердить готовность». Редактор и отдельная страница используют этот контроллер. Одновременные запросы одного назначения и identity разделяют выполняемую подготовку. Свежие проверки после изменения identity не заменяются старым кэшем.

При истечении cookie доверенная оболочка получает новую capability и повторяет только установление доступа. Она умеет восстановить и первую навигацию, когда HTML приложения ещё не загружен. Ошибки авторизации владельца возвращают к входу Yleum; они не отправляют пользователя устанавливать MAX. Настоящий MAX запуск остаётся отдельным протоколом без fallback к preview actor.

Оболочка и защищённый preview origin обслуживаются по HTTPS внутри одного schemeful site настроенного домена платформы; имя/IP сервера не зашиваются в код. Поэтому штатный просмотр не зависит от third-party cookies. При входе из внешнего кабинета открывается канонический адрес оболочки как верхняя страница, а не ослабляется cookie/auth boundary. Если браузер отвергает даже необходимые first-party cookies, после ограниченной проверки показывается причина и инструкция разрешить хранение сессии; нет бесконечного renewal, показа защищённых данных без сессии или направления в MAX. Имя домена само по себе никогда не даёт preview-права.

Продление не перезагружает исправную форму и не повторяет бизнес-запрос. Неподтверждённый POST нельзя считать неисполненным и посылать ещё раз. Смена проекта, версии или epoch отменяет старую подготовку и делает недействительными поздние ответы.

Готовность подтверждается ответом доверенной runtime boundary с ожидаемой identity и authenticated проверкой страницы/API. `iframe.onload` и наличие URL сами по себе не переводят интерфейс в «Подключено». Сообщения iframe проверяют source, origin, nonce и ожидаемую identity; generated script не может сам выдать серверное доказательство готовности.

### Гостевая ссылка

Владелец создаёт и отзывает ссылку из управления превью. Предлагаемый API: `POST /projects/{id}/preview-shares`, список активных ссылок и `DELETE /projects/{id}/preview-shares/{share_id}`. Гость открывает `/preview/{opaque_token}`. Ссылки — bearer capabilities только для выбранного демо-приложения, а не права на аккаунт владельца.

Запись grant хранит project/snapshot/artifact identity, создателя, mode `guest_demo`, hash случайного токена, срок действия, время отзыва и epoch. Сырой токен возвращается только при создании и не записывается в логи. Срок по умолчанию — 24 часа; владелец видит его и может выбрать более короткий срок или отозвать доступ. Не создаются бессрочные ссылки по умолчанию.

Вход по ссылке проверяется сервером. URL с capability не попадает в Referer, аналитику, сторонние ресурсы или диагностические сообщения. После обмена используются защищённые HttpOnly cookies с узкой областью. Отзыв и истечение проверяются при доступе к boundary и managed API; ещё действующая cookie не должна продолжать работу после отзыва. В рабочую MAX-сессию гостевая сессия не превращается.

### Изоляция демо-данных и действий

Каждый grant закрепляет артефакт и публичные demo seeds. Каждая гостевая браузерная сессия получает отдельные runtime, dataset и DB credentials; неизменяемый артефакт можно переиспользовать. Секреты чужих guest datasets отсутствуют в generated process. DB role не имеет superuser/BYPASSRLS, прав создавать роли или обращаться к другим datasets. Поэтому даже произвольный generated route с прямым SQL не читает и не меняет записи гостя B из runtime гостя A. Managed API дополнительно проверяет серверную identity сессии. Не используется общий owner actor `preview` и не принимается client-supplied user ID как доверенная личность.

Доверенный registry связывает guest session с grant, runtime identity, dataset и сроком, не превышающим срок grant. Reload с действующей сессией возвращает тот же demo dataset; другой браузер получает новый. Потерянная сессия не восстанавливается подстановкой известного dataset ID. Expiry/revocation grant закрывает все его guest sessions.

Начальные данные берутся из явно демонстрационных seeds и допустимого публичного каталога приложения. Реальные пользовательские записи, выгрузка рабочей БД, платежи, CRM-состояние, токены интеграций и секреты владельца не копируются. Существующие owner preview данные и рабочие данные сохраняются; новая функция не обнуляет проекты.

Гость может создавать и менять демо-записи через настоящий серверный API и демо-БД. Заказы в этом режиме являются демо-заказами. Оплата не имитируется как настоящий успешный платёж: интерфейс явно сообщает, что в превью она не проводится.

Серверная capability boundary запрещает платежи, сообщения, CRM-синхронизацию, внешние webhooks и прочие внешние отправки, включая фоновые задачи. Production credentials не выдаются guest runtime. Его сеть разрешает только собственные demo DB/core targets; прямой обход через generated route или background process тоже должен получить отказ. Браузерные CSP/sandbox и выдача assets не допускают незаметных внешних отправок из демо; нужные публичные assets обслуживаются разрешённым read-only путём без секретов. Клиентского скрытия кнопки недостаточно.

Demo runtime использует существующее ресурсное admission и завершает lifecycle по expiry/revocation. Очистка касается только принадлежащих этому demo dataset ресурсов. При нехватке мощности показывается ожидание/отказ подготовки; нельзя молча занять owner/public runtime или поменять его ingress. Ресурсные пределы модели и количество бизнес-объявлений этим проектом не меняются.

## Рефакторинг отдельными поставками

Изменение поведения превью отделяется от чистого рефакторинга генерации. Файлы не дробятся механически по числу строк. Каждый пакет сначала фиксирует прежний контракт, затем устраняет конкретный повтор и проходит независимое ревью.

| Пакет | Граница | Проверяемый эффект |
| --- | --- | --- |
| Контроллер превью | Подготовка, identity, отмена и recovery отделены от JSX истории/восстановления версий в `MaxLivePreview.tsx` | Один владелец подготовки; нет параллельных wake-цепочек для одной identity; меньше повторных запросов при одинаковой корректности |
| Загрузка proof receipts | Loader отделён от чистой сборки/валидации `ProofBundle` в `max_finalization.py` | На зелёной fixture сначала убрать повтор bootstrap: 7 → 6 чтений; при сохранении контракта батчировать lookup до 3, включая proof row |
| Учёт применённых файлов | Чистый reducer file deltas в native loop вместо двух реализаций для file tools и shell `obs.files` | Совпадают written/progress/evidence для write/edit/shell/no-op/empty/deletion; нет дополнительных model/tool calls |
| Продолжение сегментов | Общий reducer накопленного результата и решения continue/stop, раздельные legacy/native адаптеры | Сохраняются transcript, checkpoint, cancellation/deadline, ABA detection и число вызовов; внутренние протоколы моделей не объединяются |

Proof lookup сохраняет ключи `workspace_id + dimension + dimension_key` и допустимое повторное использование receipts между source identities. Кэш не переживает смену identity или ремонтный проход. Сохраняются artifact binding, release receipt matching и проверка текущего дерева.

До/после фиксируются поддерживаемые production LOC/bytes, число дублирующих реализаций, DB/RPC/model/tool calls, время выбранных сценариев и неизменность результатов. Уменьшение токенов или перенос функции в другой файл не объявляются ускорением. Для preview измеряются отдельно cold/warm startup и восстановление после expiry; исходные значения сначала снимаются на сопоставимой среде.

## Приёмка

Все проверки выполняются без новых платных генераций: используются существующие артефакты, синтетические приложения и disposable PostgreSQL/runtime. Отдельная реальная проверка новых генераций сохраняется для последующего восстановления провайдера.

1. Владелец без бота, публикации и MAX открывает рабочее приложение в редакторе и по постоянному адресу.
2. Первая навигация без preview cookie, reload после 15 минут и expiry во время заполнения формы восстанавливают доступ без MAX и потери формы. Бизнес-POST не повторяется автоматически. Owner iframe, отдельная страница и guest demo работают при отключённых third-party cookies на каноническом same-site контуре; полный запрет session storage даёт ограниченный понятный отказ без циклов или auth bypass.
3. Cold/parked runtime восстанавливается; missing runtime восстанавливается из принятого артефакта либо возвращает конкретный отказ без выдачи ложной готовности. Owner preview не получает agent mutation authority.
4. Candidate не меняет accepted origin, digest и видимую версию. Candidate DDL, изменения данных и последующий отказ не меняют схему/записи принятого owner dataset. Failed/cancelled generation не убирает доступный принятый результат. Проверяются отказ миграции, rollback до cutover, сохранение подтверждённых записей при fencing и свежая runtime identity после перехода.
5. Loaded 401/error page, старый iframe, поддельный postMessage и поздний ответ другого epoch не дают состояние «Подключено».
6. По гостевой ссылке без аккаунта Yleum/MAX можно менять демо-данные. Записи сохраняются в этой демо-сессии после reload; owner, другие grants и гости A/B не читают и не меняют чужие личные записи подстановкой ID. Проверяется обход managed API через custom generated route, прямые SQL read/update/delete и попытка соединения с чужим dataset.
7. Неверная, истёкшая, отозванная ссылка и старая cookie после отзыва получают отказ. Смена project/snapshot/artifact/epoch не расширяет доступ.
8. Платёж, сообщение, CRM/webhook и обход через custom server route/background task не вызывают внешнее действие. На тестовом приёмнике — ноль отправок; production credentials и owner DB недоступны.
9. Демо-очистка не меняет owner/public volumes и данные. Публикация, реальный MAX вход, возврат версии, редактирование, amoCRM и биллинг проходят существующие regression gates.
10. Для чистых рефакторингов одинаковые fixtures до/после дают одинаковые permit/rejection, outputs, side-effect ordering и число модельных вызовов. Continuation fixtures сохраняют 11 productive segments, 2 при ABA и 1 при claimed-files-only/terminal.

Основные существующие опоры: web `max-live-preview-recovery`, `max-app-provider-session`, `owner-preview-renewal`, `preview-bootstrap-json`, editor navigation; API `test_max_finalization_progress`, `test_generation_continuation`, native/source-repair/output-limit; orchestrator `test_max_preview_session`, `test_machine_boundary`, runtime/publication/artifact tests. Новые сценарии дополняют эти проверки, а не заменяют их ослабленными ожиданиями.

## Поставка

Сначала закрываются owner shell и честная готовность, затем immutable accepted preview, затем гостевой demo lifecycle. Чистые рефакторинги поставляются отдельно, начиная с loader proof receipts. У каждого пакета — исполнитель, независимый reviewer, проверки до/после и короткий checkpoint.

Миграции grant/demo identity добавочные; прежние строки не удаляются и не переписываются. До production migration проверяются копия, восстановление и безопасный переход. Rollout допускается только после совместимых boundary/core/API компонентов; при несовпадении версии протокола доступ закрывается, а не переходит в anonymous/owner fallback.

Code/CI/GitHub и production ревизии фиксируются отдельно. Production меняется только документированным `infra/release/` путём с проверкой health и выбранных пользовательских сценариев. Публикация приложения в MAX не является условием приёмки превью. Готовность всей работы не заявляется по одним unit tests или по наличию новой ссылки.

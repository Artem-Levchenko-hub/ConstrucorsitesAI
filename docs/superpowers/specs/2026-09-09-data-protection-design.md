## 1. Что получит предприниматель

Человек создаёт приложение салона, магазина или сервиса. Omnia сама создаёт защищённое хранилище, настраивает доступ, сохраняет копии и проверяет восстановление. У владельца нет переключателей «шифровать базу», «включить защиту» или «создать ключ».

Пример:

1. Клиент записывается в салон.
2. Omnia проверяет его личность и разрешение на запись.
3. Запись сохраняется в базе этого салона.
4. Клиент видит свою запись. Сотрудник видит только то, что разрешено его рабочей ролью.
5. Запись переживает перезагрузку, обновление приложения и восстановление после сбоя.
6. База, файлы и резервные копии хранятся зашифрованными.

Владелец принимает обычные бизнес-решения: кого пригласить сотрудником, кому разрешить экспорт, какие сведения собирать. Техническое исполнение этих решений берёт на себя платформа.

**Критерий готовности:** новое приложение не публикуется, пока обязательные проверки не пройдены. Существующее приложение получает этот статус только после миграции и проверки именно его рабочей среды.

## 2. Что означает «зашифровано всегда»

Обязательное обещание: данные зашифрованы при хранении на постоянных носителях и при сетевой передаче. Это касается не только таблиц, но и журналов PostgreSQL, файлов, снимков, временных архивов и внешних копий.

Разрешённый серверный процесс и браузер пользователя обрабатывают нужные им данные в открытом виде. Шифрование диска не защищает от полного захвата работающего сервера. Поэтому отдельно нужны проверка прав, изоляция процессов и запрет лишнего доступа. Это соответствует разграничению способов шифрования в [PostgreSQL 16](https://www.postgresql.org/docs/16/encryption-options.html).

В этот выпуск не входит обещание сквозного шифрования, при котором сама Omnia никогда не может прочитать данные. Для такого продукта потребовалась бы другая модель поиска, восстановления ключей, фоновых задач и доступа сотрудников.

Не обещаем юридическое соответствие только на основании наличия шифрования. Места хранения, состав данных и договорные обязанности отдельно подтверждаются по фактической инфраструктуре.

## 4. Выбранная архитектура

Сохраняем отдельные PostgreSQL-базы проектов. Добавляем обязательный платформенный профиль managed_data_v1.

~~~mermaid
flowchart LR
    U[Клиент или сотрудник] -->|HTTPS| G[Доверенный MAX gateway]
    G -->|Проверенная сессия| D[Доверенный Data API Omnia]
    D -->|TLS и ограниченная роль| P[(Отдельная PostgreSQL проекта)]
    P --> S[Зашифрованное хранилище]
    P -->|Backup и WAL| B[Зашифрованная внешняя копия]
    F[Файлы приложения] --> S
    F --> B
    K[Отдельный сервис ключей] --> D
    K --> B
    A[Генератор] --> T[Черновик с синтетическими данными]
    T --> M[Проверяемый план миграции]
    M --> C[Доверенный контроллер миграций]
    C --> P
~~~

В диаграмме ключевые связи показывают полномочия, а не передачу всех ключей каждому компоненту. Дисковый ключ нужен узлу хранения; backup secret — backup worker; migrator credential — только контроллеру миграций.

### 4.1. Почему этот вариант

| Вариант | Сильная сторона | Ограничение | Решение |
|---|---|---|---|
| Отдельные PG + шифрование хранения + Data API | Совместим с текущей Project Cell и произвольными бизнес-сущностями через контракт | Потребуются обязательные API и миграция старого доступа | Основной путь |
| Перенести всё в shared managed PostgreSQL | Часть эксплуатации у провайдера | Меняет текущую модель изоляции/административной разработки; провайдерские возможности неизвестны | Не включать в первый выпуск |
| Шифровать отдельные поля в сгенерированном коде | Можно скрыть выбранные значения от самой БД | Код может забыть поле; сложнее поиск/индексы/ротация | Дополнительный слой через доверенный сервис |

Сам текст промпта «работай безопасно» не является механизмом защиты. Генератор не может отменить policy, поменяв свой файл или отключив preload.

### 4.2. Профиль защиты и охват

managed_data_v1 хранится у платформы, привязан к project/workspace/environment и имеет возрастающую версию. Продуктовый manifest содержит запрос возможностей, но не право отключить защиту.

Профиль включает:

1. Подтверждённое encrypted storage.
2. Ключи и DB credentials вне генерируемого продукта.
3. Доверенную сессию и обязательную проверку действий.
4. Раздельные DB-роли, RLS и отсутствие опасных grants.
5. TLS на сетевых соединениях с данными.
6. Зашифрованные внешние копии с проверенным recovery.
7. Разделение генерации и production.
8. Проверки перед публикацией и наблюдение после неё.

Первый вертикальный выпуск — MAX/Node22 Project Cell. Общая цель «все пользователи» считается достигнутой только после инвентаризации и перевода ВСЕХ поддерживаемых способов публикации. Другие шаблоны получают адаптер к тому же профилю; неподдерживаемый путь не получает зелёный статус. Внешнее размещение клиента требует проверяемого адаптера инфраструктуры и входит в отдельную волну.

## 5. Хранение и ключи

### 5.1. Что должно лежать на зашифрованном носителе

PGDATA, WAL, tablespaces, DB temp files, Docker data-root/overlay там, где возможны пользовательские данные, source/home/data volumes, uploads, checkpoint/rootfs exports, controller state, локальный backup staging, очереди/Redis persistence, журналы с потенциально чувствительными сведениями, swap и crash dumps.

Если компонент нельзя защитить шифрованием, убрать из него чувствительные данные: tmpfs для временного секрета, отключённые core dumps, редактирование логов. Одного названия encrypted_volume или Docker label недостаточно.

Основной вариант для текущего Linux/Docker: отдельное управляемое зашифрованное хранилище на уровне block device (LUKS2) или проверенное шифрование дисков провайдера. Не запускать переустройство действующего диска вслепую. Если текущий узел не может дать доказательство покрытия всех путей — подготовить защищённый replacement-узел по той же Docker-архитектуре и выполнить миграцию.

Docker volumes пишут в файловую систему хоста; сам volume не доказывает шифрование. Проверять реальный mount/backing device каждого пути. [Документация Docker](https://docs.docker.com/engine/storage/volumes/).

Fail-closed запуск: если ожидаемого зашифрованного mount нет, нельзя автоматически создать обычный каталог и запустить там пустую БД. Нужны systemd-зависимость, проверка device identity и контроль непосредственно перед Docker create/start/restore.

Дисковый ключ может быть общим для защищённого узла. Это не следует выдавать за уникальный ключ каждой компании. Разделение компаний обеспечивают отдельные ресурсы и права; для backup/полевого шифрования предусматриваются отдельные project/environment keys.

### 5.2. Как управлять ключами

Выбор продукта определяется инвентаризацией: доступный управляемый KMS с нужным местом хранения и recovery либо отдельно эксплуатируемый Vault Transit. Это один сервис ключей, не параллельное внедрение нескольких систем.

Требования к выбранному сервису: отдельная identity, audit, разграничение проектов и назначений ключа, versioning, ротация, аварийное восстановление, доступность с approved production, проверенная лицензия/условия. Поставщик не выбран по догадке.

Нужны разные назначения:

- unlock хранилища;
- wrapping DB credentials;
- backup encryption;
- подпись manifest/protection evidence;
- поле с дополнительной защитой, если включено контрактом.

Не использовать один MAX bot token или один общий env-secret для всех назначений. Не хранить расшифровывающий ключ рядом с открытыми данными в том же архиве.

Envelope encryption: хранить ciphertext и обёрнутый ключ данных вместе; раскрытие ключа разрешать только нужной служебной identity. Открытый ключ данных временно существует в памяти уполномоченного процесса. Это нормальное свойство схемы, описанной в [Vault Transit](https://developer.hashicorp.com/vault/docs/secrets/transit/envelope-encryption).

Ротация wrapping key не означает пере-шифрование всего диска или всего backup. Старые версии сохраняются, пока нужны удерживаемым копиям. Rewrap выполнять возобновляемо, проверять старые и новые данные. Принципы versioning и rewrap подтверждены [документацией Transit](https://developer.hashicorp.com/vault/docs/secrets/transit).

При недоступности KMS не возвращаться к plaintext. Новые provisioning/restore/rotation приостанавливаются. Уже открытый зашифрованный диск может продолжить работу; его ключ находится в памяти ядра. Отзыв доступа в KMS сам по себе не закрывает уже открытый диск — incident runbook должен отзывать сессии и останавливать/изолировать конкретный workload при необходимости.

Для аварии проверяется восстановление самого сервиса ключей. Его root recovery не должен зависеть только от той БД, которую он помогает расшифровать. Доступ оператора временный, журналируемый; destructive key deletion требует второго уполномоченного оператора.

Обычная расшифровка требует совпадения исходного scope. Для восстановления в новую среду используется отдельное подписанное RecoveryGrant: source scope, target scope, backup id, разрешённые key refs, operation id, срок и issuer. Recovery worker может прочитать только указанный источник и записать только в назначенный изолированный target. Обычный runtime не получает такого права. Старый ciphertext не переписывается ради совпадения identity; target получает новые credentials и claims. Повторный запуск той же операции разрешён идемпотентно, использование grant другой операцией или после срока запрещено.

## 6. Доступ к данным приложения

### 6.1. Доверенный Data API

Расширить существующее immutable MAX core, а не помещать универсальный контроллер БД в редактируемый продукт. Зарезервировать /api/omnia/data/* и /api/omnia/files/* за trusted gateway. API вызывается browser SDK; серверный продукт получает только ограниченные capabilities для явно разрешённых рабочих процессов.

Продукту не выдаются DATABASE_URL/PGPASSWORD рабочей БД, admin/migrator secret, signing secret или backup credentials. Прямой SQL доступ к live DB из продукта запрещён. Среда разработки может иметь административную роль только своей синтетической БД.

Data API поддерживает декларативные сущности, связи и операции: list/get/create/patch/delete, ограниченные фильтры и сортировка, cursor pagination, batch/transaction из разрешённых действий. Нет универсального endpoint «выполни SQL».

Каждое изменение несёт contract revision и writer epoch. Доверенный сервис сверяет их с реестром допустимой совместимости активного release. Версия от клиента не выдаёт дополнительных прав. PATCH/DELETE и каждый элемент transaction имеют record preconditions; операция старой вкладки либо выполняется по проверенному адаптеру с ограниченной маской, либо получает 409 с требованием обновить приложение. Неизвестная версия не трактуется как текущая.

Правила формирует и применяет доверенный компилятор контракта. Генератор предлагает сущность и поля, но не может объявить секретное поле публичным одним произвольным SQL.

### 6.2. Роли и бизнес-сценарии

| Субъект | Базовый доступ |
|---|---|
| Посетитель | Только явно опубликованный каталог/расписание без персональных полей |
| Клиент | Собственные записи и разрешённые действия |
| Сотрудник | Данные своего бизнеса в рамках выданных обязанностей |
| Владелец бизнеса | Управление сотрудниками/данными этого бизнеса; экспорт — отдельное право |
| Webhook | Только действие интеграции после проверки подписи и защиты от повторов |
| Фоновая задача | Выданная платформой capability: проект, операция, ресурсы, срок |
| Генератор | Код, схема, синтетические данные; live identities и production DB отсутствуют |

Связь владельца Omnia-проекта с владельцем бизнес-приложения устанавливается проверенным процессом, не равенством случайного user_id. Роли сотрудника берутся из доверенного реестра; тело запроса не может присвоить owner/admin.

Выдача и отзыв прав записываются в отдельный авторитетный журнал control plane с возрастающим security epoch. Запись в проектной DB — проверяемая проекция этого журнала, не источник истины после PITR. Журнал, его подтверждённый актуальный head и owner bindings сохраняются независимо от исторических business backups. Подтверждение изменения прав пользователю выдаётся после долговечной записи события; в multi-region/узловой схеме отдельно проверить её durability.

После восстановления старых бизнес-данных сначала накладывается актуальный реестр прав/отзывов, затем выдаются новые sessions/capabilities. Старые токены не действуют. Если актуальность журнала или принадлежность бизнеса не доказана, восстановленное приложение закрыто для доступа; восстановление прав требует отдельной проверки уполномоченного владельца по независимому актуальному источнику. Нельзя подтверждать владельца только по старой восстановленной membership-строке.

У каждой сущности явно заданы owner/reference, разрешённые поля, операции, диапазон видимости, ограничения значений, правила удаления и public projection. Новое поле по умолчанию закрыто. Для неизвестной сущности публикация останавливается до формирования проверяемого контракта.

### 6.3. Второй барьер внутри PostgreSQL

Bootstrap/admin, migrator, runtime Data API и backup — разные credentials. Runtime не владеет бизнес-таблицами; нет SUPERUSER/BYPASSRLS/CREATEROLE/CREATEDB/REPLICATION, членства в привилегированных ролях и доступа к pg_read_server_files/pg_write_server_files/pg_execute_server_program.

Включить FORCE ROW LEVEL SECURITY и USING/WITH CHECK. Снять ненужные PUBLIC grants, CREATE в schema/database, опасные функции и расширения. Контролировать views, SECURITY DEFINER, search_path, sequences, triggers, foreign tables и старые object owners.

Superuser и BYPASSRLS обходят row policies; table owner обычно тоже. Именно поэтому одного ENABLE RLS недостаточно. [PostgreSQL RLS](https://www.postgresql.org/docs/16/ddl-rowsecurity.html).

Контекст пользователя не берётся из произвольного SET user_id. Gateway формирует проверяемые claims с project/environment/epoch/purpose/audience/expiry. DB guard проверяет подпись; запрос выполняется в отдельной транзакции с локальным контекстом. После commit/rollback/timeout контекст не должен попасть следующему пользователю через pool.

Существующий WIP HMAC token — полезная основа, но его TTL и scope необходимо расширить тестами ролей/отзыва. Продуктовый preload — только удобство, не защита. Новый Data API устраняет необходимость доставлять DB token в произвольный backend.

Разрешённый frontend всё равно видит отображаемые сведения. Нельзя обещать, что злонамеренный UI или полностью захваченный trusted core не способен их раскрыть. Сокращаем риск через выдачу минимальных полей, запрет лишнего egress, CSP, проверку зависимостей и журналирование экспорта.

## 7. Сеть, файлы, логи и генерация

Внешний HTTPS завершается в доверенном gateway; downstream сетевые соединения с данными также шифруются. Если процессы общаются по Unix socket в одной доверенной границе, это отмечается как локальный канал, а не «TLS по сокету».

Inventory содержит список каждого ребра: browser→edge, edge→gateway/core, gateway→product при передаче пользовательского контекста, core→Data API/DB, API→orchestrator, сервисы→Redis/MinIO, backup→object store, recovery→backup/key service, observability/integrations. Для каждого указаны переносимые данные, доверенные identities, TLS/mTLS и проверка сертификата либо разрешённый локальный канал. Внутренний HTTP по loopback не считается шифрованием. Проверки выполняются по каждому ребру, а не только на входном HTTPS и PostgreSQL.

PostgreSQL принимает только предусмотренные hostssl-правила; plaintext не проходит. Клиент проверяет CA и SAN/hostname. Для libpq — verify-full; для pg/asyncpg — эквивалентная конфигурация драйвера и отрицательный тест wrong-CA/wrong-hostname. Нельзя переносить строку libpq без проверки драйвера. [PostgreSQL TLS](https://www.postgresql.org/docs/16/libpq-ssl.html), [node-postgres SSL](https://node-postgres.com/features/ssl).

Uploads закрыты по умолчанию. Object key не является разрешением. Выдача файла проверяет того же пользователя, проект и назначение; download link имеет короткий срок. Имя, MIME, размер и содержимое валидируются; HTML/SVG и другие активные документы не исполняются на доверенном origin.

Кеши ответов включают project/user/role version или отключены для приватных данных. Никаких общих CDN/browser service-worker кешей персональных ответов без доказанного разделения.

В логах, трассировках, Sentry, очередях, SQL errors и prompts не должно быть токенов, строк БД и тела персональных запросов по умолчанию. Редактирование сообщений дополняет запрет получения live data генератором, а не заменяет его.

Проверки build/install/test выполняются без live mounts и credentials. Физический seed черновика может содержать изменённые HBA, роли и опасные функции; его нельзя слепо превращать в production. Новую рабочую БД создавать из доверенного PG image, проверенной схемы и разрешённых справочных seed-данных.

Production product запускается непривилегированным пользователем с read-only rootfs, без повышения capabilities и host mounts. Запись разрешена только в объявленные encrypted mounts/tmpfs. Root для установки пакетов остаётся в изолированном draft/build; исключение для production не выдаётся автоматически.

## 8. Backup и восстановление

### 8.1. Целевые показатели

Это начальные инженерные цели, а не уже действующий SLA:

| Показатель | Начальная цель |
|---|---|
| RPO — допустимая потеря последних изменений при утрате узла | Не более 15 минут для поддерживаемого профиля |
| RTO — время восстановления | Не более 2 часов для проекта до 5 GiB DB и 10 GiB файлов при свободной recovery capacity |
| PITR retention | Не менее 35 суток с необходимой базовой копией до начала окна |
| Backup/WAL мониторинг | Каждые 5 минут; stale >15 минут — критический инцидент |
| Автоматический restore | Для каждого проекта до защищённой публикации; далее не реже одного раза в 7 суток и после изменения backup/keys |
| Проверка потери узла | До общего запуска; затем ежеквартально |
| Ротация serving credentials | По утверждённой политике, исходная цель 90 суток и немедленно при компрометации |

Большие базы, массовая авария узла и более строгие требования получают отдельный профиль с измерением RTO и резервом ресурсов. Объём нельзя замалчивать, показывая одну универсальную цифру.

### 8.2. PostgreSQL

Целевой инструмент — pgBackRest: backup и WAL, отдельная stanza/cluster identity для независимых баз. Репозиторий шифруется до отправки. Отдельный project/environment namespace и отдельная backup identity не позволяют приложению читать/удалять чужие копии.

Начальная конфигурация: weekly full + daily differential, WAL archiving непрерывно, archive_timeout как стартовая настройка 300 секунд с последующим измерением. Низкая активность, размер WAL, compress/upload latency и число проектов учитываются при проверке RPO и стоимости.

Не копировать обычным tar работающий PGDATA как доказанно согласованный backup. Physical backup и WAL должны соответствовать кластеру/major version/timeline. Изменения внешних postgres config также сохраняются или воспроизводятся из доверенного управления. [PostgreSQL PITR](https://www.postgresql.org/docs/16/continuous-archiving.html).

У pgBackRest cipher settings существующего repository нельзя просто поменять после настройки. Для смены backup passphrase создаётся новый repository с новым ключом, проверяется первая полная копия и восстановление, старый сохраняется на весь retention. Rewrap в KMS меняет только защиту того же passphrase. [pgBackRest guide](https://pgbackrest.org/user-guide.html).

Архив WAL не имеет разрешения молча отбрасывать обязательные сегменты ради зелёного статуса. Зафиксировать backlog, storage headroom и backpressure policy; ошибка архивации делает RPO неподтверждённым.

### 8.3. Всё, что кроме PostgreSQL

Backup manifest связывает: project/environment/cluster identity, DB restore point, immutable code/core image, schema и policy digests, object versions/uploads, controller state и ссылки на необходимые версии ключей.

Есть отдельные project и platform scopes. Platform scope охватывает control DB, legacy shared DB, controller state, журнал доступа, object store metadata и key service. Общий physical cluster нельзя представить как изолированную копию одного бизнеса. Для него отдельные IAM/keys, manifest и recovery; проектное извлечение из shared cluster выполняется в закрытой recovery-среде.

Для файлов использовать versioned objects; запись DB ссылается на завершённый объект. Garbage collection сохраняет все версии, нужные ЛЮБОЙ точке удерживаемого PITR-окна, включая созданные и удалённые между full/diff backup. Безопасное исходное правило: сохранять version не меньше 35 суток после её последней ссылки/удаления плюс необходимый запас на базовую копию и незавершённый backup; дополнительно удерживать pinned manifests. Object lifecycle не может удалять версии раньше общего retention controller. Recovery проверяет DB/file связи для промежуточных моментов, не только времени ежедневной копии.

Для checkpoint/source/rootfs экспортов использовать потоковое шифрование стандартным существующим CMS-механизмом с проверяемым подписанным manifest либо иной уже проверенный backend хранилища. Не писать собственный потоковый шифр. Незашифрованные промежуточные данные допустимы только в памяти или на проверенном encrypted staging, недоступном продукту. Для временных секретов — tmpfs и 0600.

Checksum показывает целостность относительно доверенного эталона; checksum, присланный вместе с подменённым архивом, не подтверждает автора. Manifest подписывается отдельной служебной identity и фиксирует object version/size/digest. [OpenSSL CMS](https://docs.openssl.org/3.5/man1/openssl-cms/).

Публикация backup атомарна: incomplete → encrypted → uploaded → verified → committed. Восстановление и retention видят только committed. Ключ восстановления и инструкции доступны в отдельном recovery-контуре.

### 8.4. Что является доказанным восстановлением

1. Создать отдельную лабораторную среду без production endpoints и внешних интеграций.
2. Скачать именно внешнюю копию, проверить identity, signature и object versions.
3. Получить RecoveryGrant на исходный backup/key scope и новый target.
4. Восстановить DB на новый encrypted volume; файлы — в отдельный namespace.
5. Проверить строки, владельцев, связи, количества и контрольные значения.
6. Восстановить актуальные права/отзывы, сменить security/session epoch; затем запустить нужную версию приложения с текущим минимально допустимым профилем защиты.
7. Проверить создание/изменение/перечитывание записи, двух пользователей и файл.
8. Измерить фактический recovery point и длительность.
9. Сохранить отчёт без содержимого клиентских данных.

Тесты не используют scratch DB внутри production-контейнера. Cleanup проверяет laboratory identity и пути; никогда не удаляет рабочие ресурсы.

Полная потеря платформы проверяется отдельно: независимые root recovery keys/identities → key service → control DB и controller state в закрытой сети → актуальный журнал доступа/отзывов и новый global security epoch → object store/catalog → проектные DB/files → policy/proofs → маршруты и фоновые задачи. Если какая-либо часть зависит от исходного диска или недоступной registry, cold recovery ещё не доказан. Повторно использовать старые active leases/jobs после restore запрещено.

## 9. Обновления, старые приложения и откат

Миграции выполняет доверенный контроллер. Генератор предлагает декларативное изменение схемы; контроллер проверяет grants, опасные функции, потерю полей, locks, бюджет времени и совместимость старого кода.

Обычное обновление кода сохраняет live DB. Старый backend не получает возможности стереть новые поля JSON replace или cascade delete. Изменение данных отделено от восстановления исторической версии кода.

Миграция старого приложения:

1. Инвентаризация DB/owners/functions/views/triggers/files/roles.
2. Проверенная внешняя копия и восстановление на изолированной среде.
3. Адаптация к Data API и доверенному контракту; проверка всех ролей и jobs.
4. Репетиция cutover с тем же объёмом и структурой данных.
5. Lease/fence и остановка всех writers: HTTP, jobs, webhooks, старых вкладок.
6. Финальная согласованная копия или синхронизация; зафиксированный cutover point.
7. Импорт в доверенно созданную БД, без переноса небезопасной auth-конфигурации.
8. Ротация старых credentials, прекращение старых сессий, policy и отрицательные тесты.
9. Атомарное переключение маршрута и controlled resume очередей.
10. Новая запись после переключения, reload, повторная проверка двух пользователей.

До первой новой записи можно вернуться к сохранённому старому источнику в закрытом режиме. После новых записей возврат к старому volume без их переноса запрещён. Откат — совместимый код на актуальных данных либо проверенная обратная синхронизация под fence. Защита не откатывается к postgres/admin/plaintext. При неопределённости сохраняем данные и включаем обслуживание.

Незашифрованные старые диски/snapshots/backups остаются риском до закрытия retention и подтверждённой утилизации у провайдера. Простое удаление файла на SSD не доказывает стирание. Срок существования наследованных копий фиксируется; обещание полного охвата не выдаётся раньше закрытия этого пункта.

## 10. Публикация и наблюдение

ProtectionReport связан с project, environment, DB cluster identity, storage identity, release/core image digest, schema/policy digest, epoch и временем проверки. Отчёт из draft или другого приложения не подходит. Источник отчёта — доверенный контроллер, не файл генератора.

Перед сменой публичного маршрута выполняется свежая проверка обязательных условий, затем сравнение тех же identity/digests под operation lease. При изменении схемы/ключа/политики/образа соответствующие доказательства аннулируются.

| Событие | Реакция |
|---|---|
| Нет профиля/зашифрованного mount/ключа при provisioning | Не создавать незащищённую рабочую БД |
| Не прошёл доступ между пользователями | Не публиковать; сохранить предыдущую рабочую версию |
| Потерян ответ после операции | Reconcile по operation id и fence, без двойного применения |
| Backup просрочен | Снять статус актуальности backup, сообщить оператору, остановить рискованные миграции; не стирать БД и не выключать сайт только из-за метрики |
| Найден открытый доступ к чужим данным | Закрыть конкретный опасный маршрут/credential, отозвать сессии; сохранить evidence и данные |
| KMS временно недоступен | Не создавать plaintext fallback; режим зависит от уже открытых ресурсов |
| Drift политики или образа | Блокировать новый выпуск, пересчитать proof, исправить доверенным reconciler |

В интерфейсе владельца: «Защита данных включена», время последней успешной копии и понятный статус восстановления. Детальные алгоритмы, grants и KMS-пути доступны операторам. Зелёный статус не должен появляться при неизвестном результате или по одному feature flag.

## 11. Очерёдность и контрольные точки

| Этап | Задачи | Результат, после которого идём дальше |
|---|---|---|
| M0 — зафиксировать основу | T01 | Inventory, поддерживаемые пути, опасные legacy backup-пути и проверяемая лаборатория |
| M1 — защитить хранение | T02–T04 | Диски/секреты/TLS проверены, plaintext fallback отсутствует |
| M2 — защитить операции | T05–T08 | Trusted Data API, роли/RLS, файлы и генератор изолированы |
| M3 — доказать восстановление | T09–T10 | Внешняя зашифрованная копия восстановлена на отдельной среде |
| M4 — сделать обязательным | T11–T12 | Publication gate и наблюдение, включая обходные пути |
| M5 — перевести пользователей | T13–T14 | Новые приложения и все группы существующих прошли выпуск/миграцию |

T09 можно готовить параллельно с T05 после T02/T03. T13 готовит и испытывает механизм миграции в лаборатории. Его применение к пользователям начинается только в T14: canary и наблюдение предшествуют каждой следующей волне. Ключи, schema/policy и live DB миграции имеют одного последовательного владельца. Не создавать конкурирующие реализации поверх текущего restoration WIP.

Роли команды: ответственный за storage/backup/operations; ответственный за Data API/DB/runtime; независимый QA/security reviewer. Это распределение ответственности, а не требование нанять конкретное количество людей.

Оценка трудозатрат до inventory ненадёжна. После T01 оценивать отдельно объём legacy схем, число кластеров, restore throughput, свободный storage и адаптацию пользовательских backend. Не обещать готовность за один короткий спринт.

## 12. Стоимость и ёмкость

На пилоте измерить: размер DB/files, WAL в сутки, коэффициент сжатия, скорость шифрования/backup/restore, p95 запросов, KMS calls, память/CPU дополнительных процессов, число активных баз, object operation/egress расходы.

Нужный резерв: удерживаемые full/diff/WAL + versions файлов + место для одного изолированного restore + место для migration candidate + запас роста. Для массовой аварии считать отдельную recovery capacity.

Сначала ограниченная параллельность backup/restore, приоритет live workloads и мониторинг очереди. Цель пилота: p95 типового действия не ухудшается более чем на 20% при согласованной нагрузке; при превышении исследовать профиль, не отключать проверки доступа.

Ротация, retention и отдельные ключи не должны требовать ручной ежедневной работы на каждый проект.

## 13. Когда продукт можно считать готовым

Все задачи T01–T14 приняты. Матрица проверок выполнена на реальных контейнерах и пользовательских сценариях. Inventory не содержит неизвестных поддерживаемых путей. Покрытие действующих проектов — 100%, без молчаливых исключений.

# Письма Yleum: регистрация и подписка

User scope: оформить существующий код регистрации присланным техническим логотипом;
отправлять подтверждённую оплату подписки, напоминания за три дня и за один день.
Тексты по-русски. Предпросмотр: output/Yleum-Email-Preview-2026-10-26.html во внешнем workspace.

## Решения

- Существующий SMTP и Python EmailMessage; новый сервис рассылок потребовал бы новых
  credentials и передачи адресов ещё одному провайдеру. HTML плюс текст, CID PNG из
  исходного файла пользователя, inline CSS и presentation tables без JS/трекеров.
- Общий белый блок на светлом фоне, синий #005cff, логотип и Yleum; код крупно.
- Helvetica Neue с локальными fallback Aptos, Helvetica и Arial; заголовки лёгкие,
  удалённых шрифтов и трекинга нет. Файл исходного логотипа включён в MIME через CID.
- Текущая семантика кода/ссылки остаётся: 10 минут / 24 часа.
- Подтверждение оплаты создаётся в той же транзакции, что verified succeeded payment,
  для initial и renewal. SMTP выполняется отдельно после commit. История оплат не
  рассылается повторно при внедрении.
- Напоминания в окнах (48h,72h] и (0h,24h], только активные платные подписки.
  Дата и время конца периода явно по Москве; ключ subscription + period_end + days.
  Продлённые, отменённые/заменённые периоды проверяются повторно перед доставкой.
- Autopay copy сообщает о предстоящем списании и сумме; manual copy просит продлить.
- Durable SQL outbox с UNIQUE event_key, SKIP LOCKED claim, sending фиксируется до
  SMTP. Повторные webhooks, ticks и несколько workers не создают дубли.
- Повторять только однозначный отказ до принятия письма. Неопределённый SMTP outcome
  или crash после claim -> uncertain, не повторять вслепую. SMTP не обеспечивает
  атомарную exactly-once доставку; фиксированный Message-ID — дополнительная защита.
- Никаких токенов, кодов, SMTP ответов или адресов в служебных журналах.
- Перед доставкой проверяются личный владелец, active user, email и подтверждённая
  пара phone_e164 + phone_verified_at либо канонический accounts.has_verified_email.
  Старый email_verified_at без receipt/OAuth/admin authority не считается доказательством.
  Подтверждение email остаётся необязательным для владельца
  с подтверждённым телефоном; само поле email_verified_at письмами не изменяется.

## Эксплуатация очереди

Миграция 0094_email_notifications добавляет только пустую таблицу: прошлые оплаты
не создают письма. Unique event_key фиксирует paid + payment ID либо subscription
+ UTC period_end + days. Уведомление и подтверждённая оплата фиксируются одним commit.
Отдельная asyncio-задача в billing worker обнаруживает напоминания и доставляет
очередь; зависший или недоступный SMTP не задерживает billing health/heartbeat.

`pending` выбирается через FOR UPDATE SKIP LOCKED, затем `sending` и attempts
фиксируются перед SMTP. Подтверждённая доставка даёт `sent`, неактуальное письмо —
`skipped`. Однозначный отказ либо отсутствие SMTP-конфигурации возвращает `pending`
с задержкой пять минут. Неоднозначный результат — `uncertain`; оставшийся после
падения процесса `sending` через десять минут также становится `uncertain`.
Автоматического повторения uncertain нет: сначала требуется проверить принятие
письма SMTP-провайдером. Message-ID сохраняется из UUID строки при каждой попытке.

Роль commerce `max_billing` получает SELECT/INSERT/UPDATE только новой таблицы
email_notifications; для проверки канонического подтверждения email — column-only
SELECT (id, user_id, purpose, used_at, expires_at) в auth_tokens и
(id, user_id, provider, provider_user_id, email) в user_identities. Доступа к секретам
подтверждения и записи в auth-таблицы нет. Миграция 0094 содержит замороженный
условный GRANT для существующей роли. Повторяемый bootstrap после миграций —
infra/max-k3s/commerce/remote/billing-email-grants.sql, вызываемый шагом
10-core-billing-access.sh. Это намеренное дублирование исторического DDL и текущего
bootstrap, чтобы очередное обновление не зависело от повторного provision хоста.

Для диагностики без раскрытия адресов и содержимого:

```sql
SELECT status, failure_category, count(*)
FROM email_notifications
GROUP BY status, failure_category;
```

## Приёмка

MIME содержит HTML/text/CID logo; escape непроверенных значений; payment rollback
не оставляет событие; повтор успешного webhook оставляет одно; новый период даёт
новые напоминания; Free/expired/refunded/blocked user не получают неверных писем;
SMTP сбой не отменяет оплату; crash и неоднозначный ответ не вызывают повторную
отправку. Тесты, независимое review, exact SHA CI, canonical deploy и health.

## Подтверждение телефона

После согласованного расширения задачи регистрация MAX собирает email, телефон
и пароль. Отдельное действие отправляет шестизначный SMS-код через SMS Aero;
проверенный номер связывается только с одним аккаунтом. Код действует десять
минут, допускает пять попыток и привязан к аккаунту и версии его сессии.
Вход и восстановление пароля остаются через почту; повторная SMS при входе не нужна.
Подтверждение почты не подменяется и остаётся дополнительным действием после SMS.

Отправка выполняется после сохранённых согласий на актуальные документы.
Ограничения стоимости фиксируются до внешнего запроса: 5 запросов на пользователя
и номер, 20 на IP, 100 всего за скользящие сутки; пауза между запросами 60 секунд.
Неоднозначная доставка не повторяется автоматически; поле кода доступно и после
обновления страницы. Незавершённая попытка не занимает уникальный номер аккаунта.

Обязательная проверка включается явным PHONE_VERIFICATION_ENABLED. Пока рабочее
имя отправителя и канал SMS Aero не подтверждены, флаг выключен и действует
каноническое подтверждение почты. Недостающая конфигурация при включённом флаге
не отменяет требование телефона. Секрет SMS принадлежит только HTTP API.
На 26 октября 2026 у провайдера нет одобренного имени отправителя; поддержке
отправлен согласованный запрос об условиях договора и снятии модерации API.
Платные услуги и договоры этим запросом не подключались.

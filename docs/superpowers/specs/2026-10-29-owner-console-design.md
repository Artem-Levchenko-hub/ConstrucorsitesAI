# Кабинет владельца для новых MAX-приложений Yleum

Дата: 29.10.2026. Статус: согласовано пользователем, реализация начата.

## Подтверждённые решения пользователя

- Основное управление приложением находится в Yleum.
- При создании любого нового приложения владелец должен получать понятные инструменты обычного ежедневного управления.
- Добавление услуг и товаров, изменение цен, разделов и других бизнес-данных должны выполняться формами, без генерации приложения.
- Привязка аккаунта MAX не обязательна для первой версии. Это возможное последующее удобство.
- Пользователь подтвердил весь предложенный состав первой версии: каталог, заказы/заявки/записи по дате, настройки и статистика.
- Пользователь подтвердил сохранение 100 позиций каталога для первого выпуска.

## Зачем

Создатель миниаппа должен уметь вести свой бизнес после публикации: менять ассортимент, принимать заказы или заявки, работать с записями. Для этого ему не нужно разбираться в коде, базе данных и промптах.

Успех — владелец создаёт приложение, публикует, затем добавляет новую услугу обычной формой; клиент видит её в MAX, оставляет обращение; владелец видит его в Yleum и меняет рабочий статус. Последующие изменения приложения не уничтожают бизнес-данные.

## Что работает сегодня — подтверждено по коду

- MaxOwnerCatalog уже поддерживает позиции, разделы, изображения, цены, наличие, варианты и скрытие.
- Каталог хранится в max_project_configs. Транспорт отделён от исходного кода: изменение данных не создаёт снимок или генерацию.
- useYleumCatalog/getYleumServerAppConfig читают один управляемый бизнес-конфиг в runtime.
- MaxPostLaunchDashboard и MaxOwnerAnalytics показывают публикацию и события. Клиентское «Сообщение о заказе» не является универсальным реестром заказов.
- Первая генерация уже получает инструкции использовать каталог, но инструкция сама по себе не гарантирует правильного подключения.
- Управляемые maxBusinessActions в БД миниаппа хранят пользовательские действия. Их текущий API разрешает пользователю читать только свои записи.
- Разрешены собственные таблицы сгенерированных приложений; поэтому нельзя автоматически считать каждую такую таблицу стандартным заказом или без проверки открыть её владельцу.
- В текущем API каталог ограничен 100 позициями; файл бизнес-конфига и его транспорт имеют отдельные ограничения размера.

## Рассмотренные подходы

1. Общий кабинет в Yleum, повторно используемые средства управления и контракт каждого приложения. Понятный единый интерфейс; не требует второго входа; сохраняет отделение административного доступа от клиентского миниаппа.
2. Генерировать отдельную админку внутри каждого MAX-приложения. Нужны отдельное подтверждение владельца, роли и дополнительный набор проверок для каждого результата. Качество интерфейса и безопасность зависят от генерации.
3. Кабинет в Yleum плюс дополнительный вход/ярлык из MAX. Удобное дальнейшее развитие первого подхода, но не обязательное условие базового управления.

Пользователь выбрал первый подход. Третий возможен позднее. Общеплатформенная роль admin не используется как роль владельца приложения.

## Предложение первой версии — на согласование

Общая точка входа: «Мои приложения → приложение → Управление».

Разделы включаются по назначению приложения, а не показываются пустым одинаковым набором:

- Каталог: товары или услуги, разделы, фото, цена/подпись, наличие, варианты, скрытие.
- Обращения: реестр заказов и заявок; для приложения с записью — список записей по дате.
- Настройки: название, описание, часы/контакты и другие заранее поддержанные настройки выбранного модуля.
- Статистика: существующая аналитика, честно отделённая от реестра бизнес-записей.

Предложенный MVP для обращений: список с поиском, фильтром статуса и дат, карточка, разрешённый рабочий статус и внутренняя заметка владельца. Примеры состояний: новое, в работе, завершено, отменено. Конкретные допустимые переходы определяет модуль, а не свободный ввод.

Не включать в первую версию оплату/возвраты из админки, рассылки клиентам, приглашение сотрудников, редактирование любых SQL-таблиц, конструктор произвольной схемы БД и вход через MAX. Усложнение логики и новые экраны по-прежнему выполняются через билдер.

## Обычные действия владельца

Каталог: «Добавить услугу» → заполнить название, цену, описание и прочие поля → «Сохранить». Не требуется генерация или повторная публикация.

Новый раздел: владелец задаёт раздел в позиции; новая категория появляется в клиентском приложении без изменения кода.

Заказы/заявки/записи: владелец открывает карточку, видит сохранённый состав и отправленные клиентом сведения, меняет только разрешённый рабочий статус и заметку. Сумма, названия, дата и позиции исходного заказа остаются историческим снимком. Изменение каталога не пересчитывает прошлые заказы.

Сохранение показывает отдельные состояния: данные сохранены, применяются в приложении, применение подтверждено либо требуется повторить. Не обещать мгновенного обновления, когда runtime ещё не подтвердил версию.

Перед публикацией в кабинете виден каталог; раздел обращений объясняет, что рабочие данные появятся после запуска. После публикации основной реестр показывает только рабочую БД; данные предпросмотра и проверки не смешиваются с ней.

## Технические решения, предлагаемые автором проекта

### Управление — часть платформы

Оболочка кабинета, формы базовых модулей, проверка доступа, журнал изменений, состояния сохранения и доставки принадлежат Yleum. ИИ не создаёт заново административную авторизацию и произвольный backend админки для каждого приложения.

На этапе подготовки нового приложения сохраняется версионируемый контракт управления. Он перечисляет включённые модули, русские названия разделов, типизированные поля и разрешённые операции. Контракт валидируется по реестру платформенных модулей; не принимает SQL, адрес внешнего API, имена произвольных таблиц или исполняемый код.

Реестр первой версии: catalog, orders, leads, bookings и базовые settings. Не каждое приложение обязано иметь каждый модуль. Для личного дневника, например, не появляется доступ владельца к дневникам всех клиентов.

### Источник данных обращений

В первой версии использовать существующую управляемую maxBusinessActions в БД опубликованного приложения. Добавить типизированные определения бизнес-ресурсов и серверные операции владельца поверх этой таблицы; не создавать вторую копию заказов в основной БД Yleum.

Клиентские операции по-прежнему выполняются от проверенного MAX-пользователя и видят только его записи. Владелец получает отдельный доступ к разрешённым бизнес-ресурсам своего проекта.

Управляемый order-модуль должен сохранять авторитетный серверный снимок каталога, суммы и состава перед записью. Нельзя считать произвольный payload createMaxAction готовым безопасным заказом. Для заказа цена проверяется по актуальному конфигу, при изменении требуется отдельное подтверждение. Идемпотентность сохраняется.

Рабочий статус и внутренняя заметка — серверная метаинформация управления, не перезапись суммы/состава заказа. Изменения имеют ревизию, ключ операции и запись аудита.

### Граница доступа

Браузер владельца обращается только в API Yleum с его обычной сессией. API проверяет текущего владельца проекта. Токены бота и служебные ключи не передаются браузеру.

Для доступа к рабочей БД API обращается к управляемому маршруту runtime, используя краткоживущее подписанное утверждение: проект, точная операция и путь, тело запроса/его хеш, срок действия, версия контракта и активная публикация. Адрес runtime берётся только из подтверждённой публикации, не из запроса клиента.

Runtime проверяет подпись, проект, срок, версию контракта и разрешённую операцию. Конкретный алгоритм/разделение секретов и транспорт builder выбирает по существующему платформенному механизму утверждений; нельзя использовать клиентскую MAX-сессию в роли владельца или открывать общий произвольный SQL-доступ.

Данные возвращаются только по заранее разрешённым полям ресурса. Все списки — с серверной пагинацией и ограниченной выборкой. Не возвращать сырые MAX initData, служебные секреты, весь payload или личные записи других пользователей без соответствующего бизнес-контракта.

### Подключение при первой генерации

Выбранные модули входят в исходный бриф и управляемый SDK до первого билда. Каталог не должен требовать отдельной платной доработки для нового приложения, если этот модуль нужен по его сценарию.

Генератор создаёт пользовательские экраны и подключает готовые бизнес-модули. Для новых управляемых сценариев нельзя молча выбрать собственные таблицы и заявить, что готова штатная админка.

Перед принятием первой сборки проверяется не только импорт SDK и текст обещания агента, но реальное поведение выбранных модулей. Неподключённый модуль означает неподтверждённую сборку с понятным результатом; запрет не должен порождать бесконечные платные попытки.

## Совместимость и существующие приложения

Новые приложения получают штатное подключение по умолчанию.

У старых приложений сохраняются исходные таблицы, ID, клиентские владельцы и исторические суммы. Не выполнять массовое переписывание кода или перенос заказов при открытии кабинета.

Для уже совместимых managed-actions можно подключить соответствующий контракт после проверки. Собственные таблицы вроде sever_orders требуют отдельного явного адаптера/совместимого обновления через нормальный процесс билда и публикации. До этого показывать честную недоступность реестра, а не пустой список «заказов нет».

Приложения «Север» и их 13 нынешних серверных заказов не являются мишенью автоматического изменения в рамках внедрения.

## Каталог и объём данных

Первый выпуск управления сохраняет текущий контракт каталога: до 100 позиций и существующие проверки размера/поля. В интерфейсе лимит виден до отправки формы; ошибка не уничтожает введённые данные.

Это предложение границы MVP, а не требование пользователя. Более крупный каталог требует отдельного постраничного runtime-источника вместо увеличения числа в JSON-валидаторе. Если больший объём нужен сразу, включить его как отдельную часть реализации до окончательного плана.

## Защита данных и ошибок

- Чужой аккаунт Yleum не может читать/менять реестр проекта по подставленному ID.
- Обычный пользователь MAX не получает маршруты владельца.
- Пользователь MAX A не читает заказы B; владелец видит только разрешённые бизнес-поля.
- Вторая вкладка с устаревшей ревизией получает конфликт и предложение обновить данные, а не перезаписывает чужую правку.
- Повтор после сетевой ошибки использует тот же ключ и не создаёт вторую запись/смену статуса.
- Операции каталога и реестра не создают AI-вызовы, кредиты генерации, исходные снимки или публикации.
- Удаление позиции в MVP — скрытие/архивирование; заказы не удаляются, их исторический снимок остаётся.
- При неуспешной новой сборке работающая опубликованная версия и её данные продолжают обслуживаться.

## Приёмка

1. Новый проект с каталогом сразу получает рабочую панель; первая сборка читает этот каталог.
2. Через Yleum добавить услугу, изменить цену, раздел и наличие; изменения доходят в MAX без генерации/публикации.
3. Создать заказ пользователем MAX; увидеть ровно эту запись в рабочем реестре Yleum.
4. Изменить рабочий статус владельцем; клиент видит разрешённый статус. Повторный запрос не создаёт дубль.
5. Отдельно проверить заявку и запись по дате на штатных модулях; не объявлять неподдержанный сценарий готовым.
6. Изменить цену уже после добавления в корзину: заказ не создаётся до отдельного подтверждения новой суммы.
7. Новый MAX-пользователь видит только свои записи, второй владелец Yleum не видит проект.
8. Тестовые данные предпросмотра отсутствуют в рабочем списке.
9. Выполнить совместимое обновление приложения и публикацию; все контрольные бизнес-записи сохраняются.
10. Неуспешный билд не заменяет рабочую публикацию.
11. Проверить потерянный ответ, повтор, конфликт двух вкладок, пагинацию, пустой список, ошибку и отсутствие сети.
12. Сравнить число AI-вызовов, снимков и генераций до и после обычных административных действий — без увеличения.

Проверки с моделью и реальные платные canary-запуски проводить только для конкретного недостающего доказательства, без бессмысленных циклов. Платежи и рассылки для приёмки не нужны.

## Порядок реализации после согласования

1. Описать и проверить модульный контракт/границу данных и доступа, расширить управляемый SDK и защищённый runtime-мост.
2. Создать единый кабинет и реестры, используя существующий каталог и аналитику.
3. Подключить новые приложения при первой генерации и добавить обязательную поведенческую проверку.
4. Выполнить независимую проверку, затем точную ревизию: тесты, commit, push, каноническая production-выкладка и проверка здоровья.
5. Пройти живой сценарий нового приложения в MAX; сохранить снимки, ID версий и сверку записей.
6. Подключать несовместимые старые приложения отдельно, без скрытой миграции.

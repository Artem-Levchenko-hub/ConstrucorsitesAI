# Завершение резервирования Yleum: Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development or superpowers:executing-plans to implement this plan task-by-task. Независимое ревью уже разрешено владельцем; Git и production-доставка выполняются последовательно одним инженером. Чекбоксы ниже обозначают ещё не принятый результат.

**Goal:** Довести текущую резервную копию до проверенного восстановления,
закончить автоматическое резервирование и production-доставку; затем довести
существующую основу PR №99 до проверенного восстановления всех трёх ролей.

**Architecture:** Один идентифицируемый backup связывает код, данные, образы,
владельцев, получателя шифрования и квитанции. Restore использует только новую
изолированную среду и фиксирует каждый этап. Отдельная команда аварийного
восстановления управляет ролями и новыми endpoints через локальный защищённый
профиль; старые IP не зашиваются в продукт.

**Tech Stack:** PostgreSQL, MinIO/S3, CMS/OpenSSL, Python, systemd, Docker,
Kubernetes/K3s, WireGuard, GitHub Actions, штатный production deploy-prod.

**Spec:** [Фактический отчёт и ограничения](../../../reports/BackupReadiness-2026-10-21/README.md),
[действующий backup contract](../../../infra/backup/README.md),
[согласованная переносимая основа PR №99](https://github.com/Artem-Levchenko-hub/ConstrucorsitesAI/pull/99).
Документы portable-recovery из PR №99 читать на его точном head; в main они
ещё не объединены.

## Global Constraints

- Пользовательский путь, MAX, оплаты, интеграции и платные генерации не запускать.
- Существующие данные и старые CMS не удалять; владельцев и привязки не менять.
- Закрытый CMS-ключ остаётся на стороне владельца. GitHub содержит код и
  безопасные метаданные, а не секреты или расшифрованные архивы.
- Прерванную изменяющую команду сначала сверить по её PID/start/журналу/exit;
  неизвестный результат не разрешает второй запуск.
- Failed-попытки сохраняются failed. «Запущено» не означает «завершено».
- Не снимать release fences вручную и не запускать параллельные выкладки.
- Текущая копия и подготовленные worker/validator связаны с 6b39. Сначала
  закончить её proof на закреплённом API, затем доставлять новый выпуск.
- Число прошедших unit tests не означает число успешных живых восстановлений.
- Использовать существующие инструменты и passed evidence; при изменении кода
  выполнить соответствующие регрессии и независимое ревью до мутации.

## Review Focus

1. Прерывание сети после записи данных: следующий запуск сначала определяет
   результат прежнего, не создаёт второй процесс и не перезаписывает файлы.
2. Разные UUID/owner/Pod/PVC или новые записи после копии: копия не получает
   разрешение закрыть прежнее покрытие без точного сопоставления.
3. Несовпавший ключ, большой CMS, ошибка ctime/длины/EOF: отказ без изменения
   исходника и без передачи закрытого ключа на сервер.
4. Потеря registry, старых IP или первого компьютера: восстановление использует
   закреплённые образы, новые endpoints и проверяемую переносимость профиля.
5. Старый зелёный proof/artifact при новой копии: подтверждение относится к
   точным timestamp/hash/версии, а не к последнему удобному успешному запуску.

  доступен только GitHub+защищённый экспорт+разрешённый способ разблокировки.
  Доступ к исходному user/machine DPAPI не считать переносимостью.
- [ ] Выполнить существующие profile/contracts/release_bundle tests и отдельный
  CI нового пакета. Сохранённые 133 старых теста не заменяют этот прогон.

### B2. Реализовать один возобновляемый runner поверх этой основы

**Файлы:** существующий cli.py; создать рядом runner.py и tests/test_runner.py
после согласования интерфейса с contracts.py. Новые публичные команды должны
иметь режим проверки без изменений; названия в этом плане не означают, что CLI
уже существует.

- [ ] Ввести конечные этапы: validate → prepare_roles → fetch → decrypt_local →
  import → start → verify → switch. Каждый этап получает run_id, input hashes,
  before/after observations и durable terminal result.
- [ ] Перед выполнением проверять SSH host keys, ОС/архитектуру, диски, роли,
  время/сеть и отсутствие старого незавершённого runner.
- [ ] При повторном вызове сначала определять фактический результат прошлого
  шага. Ошибка/таймаут допускают explicit reconciliation, а не второй importer.
- [ ] Red→green tests/test_runner.py: crash до записи; crash после записи до
  ack; неизвестный результат; изменённый input; чужой run; повтор завершённого
  шага. Импорт и переключение выполняются не более одного раза.
- [ ] Объединить только обобщённые проверенные операторы. QA payload с
  конкретными inode, nonce, IP или UUID не объявлять универсальным runner.

### B3. Запускать новые роли с новыми адресами и импортировать состояние

**Файлы:** infra/max-k3s/provision.sh, lib.sh, remote/, documented production
configuration; новый adapter рядом с runner.py для роли→endpoint.

- [ ] Получать три уже созданных VPS через защищённый профиль с ролями. API
  провайдера оставить дополнительным adapter, а не блокером первого результата.
- [ ] Идемпотентно установить закреплённые зависимости и сеть между ролями.
  Сгенерировать новую конфигурацию из inventory, не заменять IP строками в коде.
- [ ] Загрузить архивные образы без доступа к прежнему registry; проверить
  исходную index/manifest/config/layer цепочку и нужную архитектуру.
- [ ] Импортировать платформу, базы приложений, роли/права, объекты, состояния
  контроллеров и публикаций. Отказать при отсутствии любой обязательной части.
- [ ] Запустить read-only verification до переключения публичного адреса.
  Старую площадку при плановом переносе оставить доступной для отката.
- [ ] Перед переключением согласованно остановить изменяющие операции,
  подтвердить последний перенос записей, настроить DNS/TLS и внутренние service
  endpoints через действительные credentials, измерить окно простоя. Сохранить
  публичный домен и прежние callback/webhook URI; внешние интеграции в рамках
  этой приёмки не перенастраивать и не тестировать.

### B4. Настоящее учение и Windows-кнопка

- [ ] Выполнить runner на трёх чистых совместимых VPS с другими адресами и без
  доступа к дискам прежних серверов. Покупку/удаление VPS согласовывать отдельно.
- [ ] Проверить данные, владельцев, версии, службы и сохранность после рестарта
  на новых ролях. Опубликовать технический scope и отличать его от отложенного E2E.
- [ ] Прервать перенос на одном безопасном этапе и доказать корректное resume
  без второго импорта, потери строк, изменения владельца или двойного webhook.
- [ ] Замерить каждый этап и фактические RTO/RPO. «Несколько минут» не ставить
  в отчёт до измерения полного сценария.
- [ ] Добавить тонкий Windows launcher, который вызывает тот же runner и
  показывает его этап/ошибку; отдельную вторую реализацию восстановления в BAT
  не писать. Ручной ввод новых адресов допускается, старые IP не обязательны.

## C. Защита и эксплуатация после приёмки

- [ ] Для provider snapshots проверить тариф, диски/WAL, экспорт, независимость,
  срок хранения и реальный restore на отдельный VPS. Snapshot ID недостаточен.
- [ ] Зафиксировать расписание и сроки хранения. До отдельного решения
  автоматическая очистка остаётся выключенной; накопление места мониторится.
- [ ] Проверить независимый доступ к ciphertext и восстановительному профилю
  без production account; иметь второй проверенный защищённый экземпляр ключа.
- [ ] Регулярно выполнять техническое восстановление новой копии. Периодические
  учения не подменять envelope-check или HTTP 200 существующего сервера.
- [ ] Отдельно спроектировать PITR/WAL и удалённую долговечность, если требуется
  минимальная либо нулевая потеря последних подтверждённых записей при потере
  всех VPS. Не пытаться применять WAL поверх обычного logical SQL dump.
- [ ] Versioning/Object Lock проверять на выбранном независимом хранилище;
  отсутствие Delete в коде не равно запрету удаления на уровне хранилища.

## Финальная проверка плана

Порядок A1→A9 обязателен там, где этап использует результат предыдущего.
Исследование B/C можно вести независимо, но Git/deploy/операции с рабочим
состоянием остаются последовательными. Пользователь уже разрешил исполнение
с независимым ревью; повторного общего согласования этого плана не требуется.
Новые покупки, удаление данных, отправка сообщений и расширение E2E этим планом
не разрешаются.

Финальный отчёт должен ответить на четыре разных вопроса: создана ли копия;
есть ли независимый экземпляр; восстановлены ли её данные; работает ли вся
платформа на новых трёх VPS. Каждый ответ получает собственное доказательство.

# Интеграции для готовых MAX Mini Apps

Дата: 30 июля 2026
Статус: первый рабочий контур подключений доставлен; доменные операции в работе

## Что уже реализовано

В MAX Studio появился отдельный Integration Hub на странице проекта. Сейчас
он умеет:

- показывать каталог по задачам бизнеса, искать и фильтровать сервисы;
- проверять реквизиты read-only запросом к API самого поставщика;
- хранить токены и ключи зашифрованно только на backend;
- не возвращать секреты в браузер после сохранения;
- повторно проверять, обновлять и отключать соединение;
- привязывать соединение к конкретному проекту и его владельцу;
- честно показывать требования к интеграциям, которые пока нельзя подключить.

Живые проверки доступны для ЮKassa, iikoCloud, облачного Битрикс24,
МойСклад и Яндекс Метрики. Для r_keeper, YCLIENTS, amoCRM, 1С и CDEK каталог
уже объясняет необходимые лицензии, OAuth или локальный коннектор, но не
показывает ложную кнопку подключения.

Этот этап подтверждает и безопасно сохраняет доступ. Он ещё не означает, что
сгенерированное приложение уже может создавать платежи, заказы и записи.
Следующий контур — описанные ниже стабильные доменные методы, обработка
webhook, idempotency, журнал операций и runtime SDK для конечного приложения.

## Цель

Пользователь должен собирать приложение, подключать уже используемые сервисы и
получать работающий продукт без передачи ключей разработчику и без ручного
редактирования сгенерированного кода.

Интеграции нельзя вшивать напрямую в каждый сгенерированный проект. Они должны
работать через общий Integration Hub Omnia:

- секреты и OAuth-токены хранятся только на стороне платформы;
- пользовательское приложение вызывает стабильные доменные методы Omnia;
- адаптер поставщика переводит их в API ЮKassa, r_keeper, YCLIENTS и других;
- webhooks сначала принимаются платформой, проверяются и только затем
  превращаются в события приложения;
- каждое действие имеет idempotency key, статус, повторные попытки и журнал.

## Реальные ограничения поставщиков

### ЮKassa

Сейчас ЮKassa платформы и ЮKassa конечного продавца — разные контуры. Платёжные
данные Omnia нельзя использовать для продаж в пользовательском мини-приложении.

Целевой сценарий — партнёрский OAuth: продавец авторизует свою кассу, а Omnia не
просит и не показывает его секретный ключ. Для первого пилота можно разрешить
`shopId + secretKey`, но только с серверным шифрованием, маскированием,
проверкой тестовым запросом и ротацией.

Подтверждение оплаты строится только по webhook и последующей сверке статуса.
Возвраты и чеки должны быть частью адаптера, а не кодом конкретного приложения.

Источники:

- https://yookassa.ru/developers/using-api/interaction-format
- https://yookassa.ru/developers/using-api/webhooks
- https://yookassa.ru/developers/solutions-for-platforms/partners-api/basics

### r_keeper

Под названием «Кипер» в плане подразумевается r_keeper. Нужны два адаптера:

1. `r_keeper Delivery` — облачное API для меню и заказов.
2. `r_keeper 7 Local` — локальный агент Omnia рядом с кассовым сервером или
   защищённый доступ к XML API.

r_keeper Delivery требует отдельную лицензию `Delivery_Api` и создание
подключения в административной панели клиента. Через API доступны меню,
стоп-лист, создание, изменение, отмена и поиск заказов. Для локального r_keeper
7 могут потребоваться XML-лицензия, адрес кассового сервера, VPN или агент в
сети ресторана. Поэтому универсальная кнопка «подключить без настроек» здесь
невозможна; зато мастер может проверить каждый обязательный шаг.

Источники:

- https://docs.rkeeper.ru/delivery/podklyuchenie-po-api-4043842.html
- https://docs.rkeeper.ru/delivery/oplata-i-zavershenie-zakaza-65930732.html
- https://docs.rkeeper.ru/rk7/latest/ru/xml-interfejs-r_keeper-7-19605640.html

### CRM

amoCRM следует подключать как публичную OAuth-интеграцию, а не просить старый
API-ключ. После подключения Omnia подписывается на необходимые webhooks.
Битрикс24 для пилота допускает входящий webhook, но продуктовый сценарий лучше
строить через приложение/OAuth: URL webhook содержит секрет и остаётся только
на сервере.

Источники:

- https://www.amocrm.ru/developers/content/oauth/auth-public-integrations
- https://new.amocrm.ru/developers/content/crm_platform/webhooks-api
- https://apidocs.bitrix24.com/api-reference/events/index.html

### МойСклад и 1С

МойСклад имеет серверный JSON API, токены и webhooks, поэтому подходит для
первого складского адаптера. 1С поддерживает OData, HTTP/REST и JSON, но
конкретные объекты зависят от конфигурации и публикации базы. Для облачной 1С
можно использовать прямой адаптер; для локальной — тот же Local Connector,
что и для r_keeper.

Источники:

- https://dev.moysklad.ru/doc/api/remap/1.2/
- https://wonderland.v8.1c.ru/blog/avtomaticheskiy-rest-interfeys-prikladnykh-resheniy/

### Карты и аналитика

Коммерческое использование Яндекс Карт и геокодера требует подходящего тарифа,
а некоторые тарифы ограничивают хранение полученных данных. Метрика
подключается через OAuth; цели и счётчик можно создавать через API, а
серверные события отправлять Measurement Protocol.

Источники:

- https://yandex.ru/dev/commercial/doc/en/concepts/jsapi-geocoder
- https://yandex.ru/dev/metrika/ru/

## Архитектура Integration Hub

### Сущности

1. `integration_providers`
   - код поставщика, версия адаптера, доступные возможности;
   - способ авторизации, обязательные договоры и лицензии;
   - sandbox/production endpoints.
2. `integration_connections`
   - владелец и business profile;
   - зашифрованные credentials/OAuth tokens;
   - scopes, expiry, состояние и результат последней проверки.
3. `project_integration_bindings`
   - проект, connection, включённые возможности;
   - сопоставление организаций, филиалов, складов, касс и статусов.
4. `integration_webhook_endpoints`
   - отдельный непредсказуемый URL;
   - секрет подписи, версия схемы и поставщик.
5. `integration_events`
   - уникальный provider event ID;
   - нормализованный тип события;
   - состояние обработки и число попыток.
6. `integration_sync_runs`
   - ручные и фоновые синхронизации;
   - статистика, ошибки и ссылка на безопасный журнал.
7. `integration_audit_log`
   - кто подключил, переподключил, изменил mapping или отключил сервис.

### Доменные возможности вместо API поставщиков

Сгенерированный проект получает ограниченный SDK:

```ts
payments.create({ orderId, amount, returnUrl })
payments.refund({ paymentId, amount })
catalog.list({ locationId, cursor })
orders.create({ cart, customer, delivery })
orders.getStatus({ orderId })
bookings.getSlots({ serviceId, date })
bookings.create({ slotId, customer })
crm.captureLead({ source, customer, fields })
analytics.track({ name, properties })
```

SDK обращается к backend-for-frontend Omnia. BFF проверяет подпись MAX
`initData`, пользователя, проект, доступную capability и лимит. Браузер не
видит credentials поставщика.

### Надёжность

- idempotency key на платежи, заказы, записи и входящие события;
- transactional outbox перед отправкой внешних запросов;
- очередь, экспоненциальные повторы и dead-letter queue;
- webhook acknowledgement без тяжёлой синхронной обработки;
- reconciliation jobs: сверка зависших платежей, заказов и записей;
- rate limit на проект, поставщика и connection;
- circuit breaker и видимый статус деградации поставщика;
- версионированные схемы событий и контрактные тесты адаптеров;
- маскирование PII и секретов в логах;
- хранение только необходимых данных и сроки удаления по категории.

## Как это выглядит в интерфейсе

### Центр интеграций

Первый уровень — не сетка логотипов, а цели:

- «Принимать оплату»;
- «Загружать меню и передавать заказы»;
- «Открыть онлайн-запись»;
- «Передавать лиды в CRM»;
- «Синхронизировать товары и остатки»;
- «Рассчитывать доставку».

После выбора цели студия предлагает подходящие сервисы и отраслевой пакет.

### Мастер подключения

Один последовательный экран:

1. **Что понадобится** — договор, тариф, лицензия, права администратора.
2. **Авторизация** — OAuth или защищённый ввод credentials.
3. **Выбор контура** — организация, филиал, ресторан, склад, касса.
4. **Сопоставление** — статусы, способы оплаты, товары, модификаторы.
5. **Проверка** — тестовый read, затем безопасный тестовый write/dry run.
6. **Активация** — подписка webhooks и включение фоновой сверки.

### Карточка подключённого сервиса

Она показывает факты, а не декоративную галочку:

- `Подключено` / `Нужно действие` / `Ошибка` / `Недоступно у поставщика`;
- проверенный аккаунт и выбранные филиалы;
- время последней успешной синхронизации;
- число необработанных событий;
- одну главную кнопку для текущего действия;
- «Журнал» и «Настройки» как вторичные действия.

### Отраслевые комплекты

- **Ресторан:** r_keeper или iiko + ЮKassa + доставка + Метрика.
- **Услуги:** YCLIENTS + ЮKassa + amoCRM/Битрикс24 + уведомления.
- **Магазин:** МойСклад + ЮKassa + CDEK + Метрика.
- **Лояльность:** POS/CRM лояльности + MAX-бот + аналитика.

Выбор комплекта добавляет capabilities в проектный бриф, но подключение каждого
внешнего аккаунта всё равно подтверждает владелец.

## План реализации

### Этап 0. Партнёрские условия и прототипы

- зарегистрировать приложения/OAuth clients у ЮKassa, amoCRM, Битрикс24,
  Яндекса и МойСклад;
- получить условия партнёрского API YCLIENTS, iiko и r_keeper;
- собрать тестовые аккаунты и лицензии;
- утвердить модель обработки персональных данных и платёжных событий.

Результат: таблица доступов и подтверждённые sandbox credentials.

### Этап 1. Общее ядро

- миграции и модели Integration Hub;
- envelope encryption credentials;
- OAuth callback/state/PKCE;
- единый webhook ingress с проверкой подписи;
- очередь событий, outbox, retries и DLQ;
- аудит, provider health и журнал для пользователя;
- capability SDK для сгенерированных приложений.

Результат: один демонстрационный адаптер проходит connect → test → event →
disconnect без изменения кода проекта.

### Этап 2. ЮKassa для конечных приложений

- отдельный merchant connection;
- создание платежа с idempotency key;
- webhook, сверка статуса, возврат;
- сохранение минимально необходимого платежного состояния;
- UI оплаты внутри MAX с переходом по разрешённой HTTPS-ссылке;
- тестовый и боевой режим;
- чек-лист чеков/фискализации для выбранной схемы.

Результат: тестовый заказ оплачивается, статус подтверждается webhook, повторный
клик не создаёт второй платёж.

### Этап 3. Ресторанный комплект

- `r_keeper Delivery` cloud adapter;
- `iikoCloud` adapter;
- импорт меню, модификаторов и стоп-листа;
- mapping филиалов, оплат и статусов;
- заказ только после подтверждённой оплаты, если так выбрано;
- фоновая сверка статуса заказа;
- прототип Local Connector для r_keeper 7.

Результат: меню синхронизируется, тестовый заказ проходит до кассы, сбой
поставщика не теряет событие.

### Этап 4. Услуги и CRM

- YCLIENTS/Altegio: услуги, специалисты, слоты, запись и отмена;
- amoCRM и Битрикс24: контакт, лид/сделка, source attribution и webhooks;
- готовый пакет «Услуги».

### Этап 5. Торговля и доставка

- МойСклад: товары, остатки, контрагенты и заказы;
- CDEK: расчёт, ПВЗ, отправление и трекинг;
- DaData/Яндекс Карты для адреса;
- готовый пакет «Магазин».

### Этап 6. Local Connector и 1С

- подписанный контейнер/агент с исходящим mTLS-соединением в Omnia;
- allowlist методов, автоматическое обновление и health heartbeat;
- r_keeper 7 XML и 1С OData/HTTP adapters;
- мастер установки без входящих портов в сеть клиента.

## Критерии готовности каждого адаптера

- credentials никогда не возвращаются клиенту после сохранения;
- scopes минимальны и отображаются до авторизации;
- test connection проверяет реальное право на нужную операцию;
- create-операции идемпотентны;
- webhooks имеют подпись/секрет, дедупликацию и повторную обработку;
- есть sandbox или безопасный dry run;
- disconnect отзывает токены и выключает подписки, где API это позволяет;
- журнал не содержит секретов и лишних персональных данных;
- ошибка содержит понятное действие пользователя;
- provider outage не превращается в «неверный токен»;
- контрактные, интеграционные и e2e-тесты проходят до выпуска.

## Что нельзя автоматизировать полностью

- заключение договора с платёжным, POS или CRM-поставщиком;
- покупку лицензии r_keeper и включение API администратором;
- одобрение OAuth-доступа владельцем внешнего аккаунта;
- публикацию OData/HTTP endpoint локальной 1С без доступа администратора;
- модерацию MAX-бота;
- ручные действия в кабинете MAX, для которых платформа не предоставляет
  публичного API.

Задача Omnia в этих местах — показать точный prerequisites checklist, проверить
результат и продолжить автоматически, а не выдавать ручной шаг за завершённый.

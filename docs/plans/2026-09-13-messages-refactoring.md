# Разделение обработки запросов и генерации

Продолжение Task 9 общего плана. Исходная ревизия:
`fad210f0a68827485fdf44d78966caf38a8a8a03`.
В исходном `routers/messages.py` было 9243 строки, в `_process_prompt` — 5150,
в `post_prompt` — 872. Цель — выделить владельцев операций и состояния,
сохранив действующие протоколы, транзакции и условия публикации.

## Владельцы операций

Новый пакет находится в `apps/api/src/yleum_api/services/generation/`.

| Граница | Ответственность |
| --- | --- |
| `routers/messages.py` | HTTP, авторизация владельца, схемы запросов и ответов, чтение истории и отмена |
| `acceptance.py` | Резервирование или повтор запроса, допуск, маршрутизация, сообщения, сохранение dispatch и ответа в одной сессии запроса |
| `onboarding.py`, `lightweight_turns.py` | Уточнения, интервью и ответы без сборки приложения |
| `supervisor.py` | Единый реестр фоновых задач, наблюдение за отменой и очередью, восстановление задач |
| `lifecycle.py` | Контекст одного запуска, выбор сценария, обработка ошибок и освобождение ресурсов |
| `agent_pipeline.py` | Последовательность агентной генерации, проверки кандидата, восстановления и публикации |
| `agent_preparation.py`, `agent_prompt.py`, `agent_runtime.py`, `agent_seed.py`, `agent_generation.py` | Подготовка запроса и среды, исходное дерево, вызов агентной модели |
| `agent_recovery.py`, `agent_verification.py` | Восстановление изменённых файлов, проверки сборки и продукта; отдельный результат исходного кандидата |
| `agent_finalization.py`, `agent_publication.py` | Финализация MAX с `ProofBundle`, затем публикация проверенного дерева |
| `streamed_pipeline.py` | Последовательность потокового сценария, включая редактирование и контейнерные приложения |
| `stream_preparation.py`, `stream_attempt.py`, `stream_candidate.py` | Подготовка модели, одна попытка ответа, извлечение и повтор неполного результата |
| `surgical_recovery.py`, `static_quality.py`, `static_acceptance.py`, `asset_composition.py` | Точечные исправления, проверки HTML, выбор кандидата и композиция ресурсов |
| `stream_publication.py`, `container_realization.py` | Основной снимок и отдельные действия после commit, включая прежний второй снимок после ремонта контейнера |
| `progress.py` | Долговечные события и ограниченная история шагов; отдельное состояние потокового сообщения |
| `runtime.py`, `publication.py`, `file_transforms.py`, `stream_support.py`, `agent_messages.py` | Общие операции прежних веток без обратной зависимости от HTTP-router |

`contracts.py` содержит узкие типы: идентификаторы запуска, факты проекта,
исходное дерево, возможности исполнителя и результаты проверок. Владелец
ресурсов `GenerationRuntime` хранит исполнитель, координатор финализации и
задачу тайм-аута. Общего контейнера всех переменных генерации нет.

## Сохранённые условия

- Повтор по idempotency key возвращается до повторной адаптации, маршрутизации
  и списания. Записи запуска и сообщений сохраняются до запуска фоновой работы;
  worker получает долговечный dispatch и не запускается параллельно из API.
- Блокировка worker действует до завершения обработки, включая защищённое от
  отмены освобождение Project Cell. Основные фазы и освобождение исполнителя
  ожидаются; прежние фоновые best-effort warm/compile probes сохранены.
- Неуспешный кандидат остаётся неуспешным после восстановления рабочего
  приложения. Зелёная проверка восстановленного дерева не разрешает публикацию
  отклонённого кандидата.
- В ветке координатора финализации MAX настоящий `ProofBundle` и проверенное
  дерево передаются до публикации с `exact_tree`. Прежняя ветка без координатора
  сохраняет `proof=None` и `exact_tree=False`. Признаки остановки, частичного результата и необходимости
  финализации не объединены в один флаг успеха.
- Снимок, итоговое сообщение и бесплатная генерация остаются в одной SQL
  транзакции. Постановка preview в очередь и `snapshot.created` идут после commit.
  Нового списания денег в API нет: прежний владелец списания — gateway.
- Нумерация долговечных событий выделяется БД. Номер и содержимое потокового
  сообщения сохраняются между попытками; вывод и usage отдельной попытки имеют
  собственное состояние. История шагов ограничена 200, долговечные события — нет.
- Выбранный Project Cell не заменяется legacy-средой при ошибке. Исполнитель
  и проверки привязываются к фактически выбранной среде.
- Порядок аварийной очистки сохранён. В частности, повторная отмена при ожидании
  shielded release может прервать последующую очистку hot-stream состояния;
  этот существующий порядок не объявляется исправленным данным рефакторингом.

## Два ограниченных исправления

Оба случая сначала воспроизведены регрессионными тестами.

1. При `use_build_plan` план менял уже отсоединённый `Project`, а commit старой
   закрытой сессии не сохранял изменение. После ответа модели открывается новая
   сессия, читается актуальный проект, выполняются merge и commit. Сессия не
   удерживается на время модельного вызова.
2. В ветке выбранного исполнителя для non-MAX локальный импорт MAX-константы
   мог отсутствовать; после устранения этого исключения обнаруживался старый
   legacy callback. Импорт и привязка исправлены вместе. Тест явно предоставляет
   выбранный Cell и запрещает вызов legacy. Текущий стандартный factory обычно
   возвращает `None` для non-MAX: тест не доказывает доступность такого режима
   всем пользователям и не меняет политику допуска.

Остальные переносы сохраняют поведение. Схема БД, зависимости, модельные
инструкции и правила доступа этим пакетом не пересматриваются.

## Проверка и поставка

Характеристические тесты вызывают настоящий tracker, процесс генерации и worker
с PostgreSQL и Git; внешние модели и транспорт среды заменены управляемыми
двойниками. Проверяются результат запуска, точное содержимое сообщений,
снимки, usage, бесплатный лимит, порядок событий и ожидание освобождения среды.
Миграция тестов меняет владельцев импортов и monkeypatch, сохраняя ожидания.
Тест публикации должен вызывать настоящий production callable, а не фрагмент AST.

До поставки обязательны полный API Ruff/mypy, необходимые API regression suites,
независимое ревью, проверка неизменности OpenAPI и строковых литералов, CI на
Linux/Python 3.12. Доставка использует production compose `full`: API, worker и
generation-worker получают одну точную ревизию. Web и host-orchestrator имеют
собственные неизменённые ревизии; равенство всех компонентов одному SHA не нужно.
Перед переключением проверяются активные запуски и Cell-операции, делаются
резервные копии, сохраняются сторонние серверные изменения и путь отката.

Исходная реальная проверка на `fad210f0` остановилась с
`PROVIDER_AUTH_FAILED`. У свежего обычного тестового аккаунта подтверждены
назначение и готовность Project Cell. Запуск завершился ошибкой; тестовый проект
удалён с проверкой 404, аккаунт переведён в `deletion_pending`, сессия отозвана.
Это исходный сбой провайдера, а не результат нового кода. Успешная генерация,
запись и чтение после обновления страницы, а также редактирование через модель
этим запуском не подтверждены.

Само уменьшение router не означает уменьшения суммарного кода или ускорения.
Перенесённые строки, новые границы модулей и действительно удалённые повторы
учитываются отдельно. Полная матрица бизнес-сценариев общего плана не считается
закрытой только на основании этой декомпозиции.

Локальная проверка завершена: 618 уникальных focused cases прошли, один прежний
`xfail` сохранён; дополнительно прошли шесть затронутых проверок helper/границ.
Ruff всей API, mypy 316 исходных файлов, compileall, сборка 3717 тестовых случаев
и diff-check прошли. Независимое ревью закрыто без открытых замечаний. Сверка
OpenAPI сохранила пять путей и десять связанных схем; все исходные строковые
литералы длиной от 40 символов сохранены без изменения пробелов внутри них.
Полный Linux CI и доказательства production относятся к последующей поставке.

Итоговый router занимает 282 строки. Вместе с 33 модулями генерации это 11383
строки и 493410 UTF-8/LF байт против исходных 9243 строк и 460186 байт.
Рост отражает явные интерфейсы и отдельные модули; уменьшение суммарного объёма
исходников не заявляется. Удалены повторные механизмы восстановления дерева,
записи событий и резервный дубль списка команд продолжения.

# MAX: английские правила изменения данных — проверка и остаточные риски

Дата: 9 сентября 2026. Статус: **первый пакет поставлен на production** — начало реализации
[согласованной архитектуры](../superpowers/specs/2026-09-09-client-versioning-design.md).

## Изменение

Единый английский policy block включён в MAX build/edit/continuation, native/text
agent guide, one-shot и repair. Project Cell получает его после замены шаблонных
инструкций. Imported MAX edits сохраняют политику. Other stacks и prose-only
art direction не получают эти правила; язык пользовательского ответа сохраняется.

Примеры: добавочная nullable-фамилия, переименование подписи без смены колонки,
переход денежных единиц с сохранением старого представления, частичное изменение
строки/JSON с контролем конкуренции, новые дочерние записи и старое удаление.
Перед изменением схемы/смысла данных агенту предписано записать короткий план в
`.omnia/data-evolution.md`; наличие файла не считается проверкой совместимости.

Это **доставка инструкций**, не доказанная дисциплина реальной генерации,
не SQL-фильтр и не готовое восстановление версии. Права БД и MAX restore guard
не изменены. Реальные пользовательские/модельные генерации не запускались.

## Известные оставшиеся риски

| Риск | Почему остаётся | Что должно закрыть риск |
|---|---|---|
| Модель нарушит правила | Prompt не отнимает полномочий | Доверенный контроллер миграций и обязательные независимые проверки |
| DDL или изменение данных из install/build/start | В рабочем контейнере остаются административные DB credentials | Раздельные роли и отсутствие migrator secrets в продуктовых процессах |
| Старые привилегии сохранят обход | Владение объектами, membership, SECURITY DEFINER, сохранённые credentials/connections | Аудит/ротация/прекращение старых соединений; реальные privilege-тесты |
| Импортированная настройка БД обойдёт новые роли | Физический PostgreSQL seed переносит конфигурацию; ротация пароля не удаляет ранее добавленное правило trust | Доверенная политика authentication вне власти продукта; отказ admin-входа без/с неверным/старым паролем после seed/restart/reconcile |
| Массовая смена ролей сломает приложения | Миграции, sequences/functions и startup могут требовать прежние права | Проверенный opt-in новых runtime, отдельная миграция существующих |
| Старый UPDATE или JSON replace сотрёт новые данные | DML-only роль всё ещё может менять целую запись | Принудительные field-level операции/ограниченные представления, проверки unknown fields |
| Старый DELETE уничтожит новые дочерние данные | FK cascade/триггеры действуют независимо от экрана | Проверяемый контракт удаления и сохранения зависимостей |
| Совпавший schema hash даст ложную совместимость | Смысл, единицы, enum, JSON и записи могут измениться без новой схемы | Контракты чтения/записи и проверка фактических значений |
| Неоднозначные или тяжёлые backfills | Перевод типов/денег может терять точность; DDL создаёт locks | Явные правила перевода, сохранение оригинала, bounded restartable миграции |
| Старый код продолжит писать в прежнее представление | Одноразовый перенос не синхронизирует следующие записи | Источник истины, переход чтения/записи, совместимость всех writers |
| Build/runtime probe не проверит продуктовые данные | Проверяется запуск и managed MAX path, не полный CRUD собственной сущности | Реальный create/update/reload/cross-user сценарий каждой поддерживаемой сущности |
| Проверка черновика не докажет публикацию | Draft/public могут иметь разные БД/настройки | Изолированная проверка именно целевой среды непосредственно перед применением |
| Гонка двух операций или сбой на переключении | Durable restore coordinator/reconciliation ещё не реализован | Idempotency, expected HEAD, fencing, журнал намерения, fault injection |
| Старые вкладки/jobs продолжат несовместимые записи | Одного переключения маршрута недостаточно | Версии контрактов, drain/fence writers, безопасная передача очередей |
| Повтор платежа/сообщения или изменение внешнего сервиса | Кодовый откат не отменяет внешние эффекты | Изоляция проверки, idempotency интеграций, отдельное согласование внешних действий |
| Историческая сборка не воспроизведётся | Пакет/образ может исчезнуть; старый код может быть уязвим | Неизменяемые артефакты и удержание зависимостей; явно отмеченная адаптация |
| Придётся восстанавливать повреждённые данные | Возврат кода сам не восстанавливает значения | Отдельные проверенные backups/PITR и адресное восстановление, без замены live БД старой |
| Подготовка будет медленной или дорогой | Копия большой БД и кандидат требуют CPU/RAM/disk | Измерения, ограничение параллелизма, retention/cache; ресурсы действующего приложения сохраняются |
| Новые инструкции увеличат вход модели | Policy добавляется к каждому MAX code prompt | Один экземпляр после provider selection; реальное влияние на latency/token cost ещё не измерено |
| Новые обходные prompt paths появятся позже | Будущий code path может забыть общий guide | Матрица regression-тестов и code review при добавлении генераторов |

Это перечень выявленных рисков, не гарантия отсутствия неизвестных дефектов.
Следующий технический пакет: non-owner роль нового опубликованного runtime,
отдельный migrator, управляемая аутентификация БД, реальные разрешённые CRUD и
запрещённые DDL/admin-login сценарии. Для свежего штатного кластера код задаёт
TCP SCRAM и отключает Unix-сокет; PGDATA не подключён в product container.
Наличие trust в реальной публикации не проверялось и здесь не утверждается.
Риск касается переноса изменяемой конфигурации: метод trust позволяет клиенту
выбрать пользователя без проверки пароля ([PostgreSQL 16](https://www.postgresql.org/docs/16/auth-trust.html)).

# Завершение первой генерации MAX без снижения скорости

## Подтверждённая причина

Последний исследованный запуск на `fad210f0` завершён отменой. Счётчик 289
обозначал последовательность событий; worker зарегистрировал 76 шагов модели
в четырёх сегментах. Эти числа не доказывают ускорение генерации в четыре раза.

Обычный bootstrap создавал pending-журнал защиты новой БД до создания machine
manifest. Следующий execute сначала проверял сохранённую защищённую среду,
получал 409 из-за отсутствующего manifest и не доходил до первоначального
создания машины. Для воспроизведения не требуется предполагать падение сервера.

Повтор SQL bootstrap использовал ID от ограниченного ключа кеша, хотя полный
proof команды менялся. Семь production proofs дали один ID операции, шесть
отличались от сохранённого полного proof. Повтор завершённой activity тоже
терял исходную причину отказа. Неисправимость инфраструктуры превращалась
в обычную обратную связь модели и порождала бесполезные попытки исправить код.

Переданный worker запрос совпал с текущим сообщением пользователя. Гипотеза
подмешивания старой истории не подтвердилась. Профиль, история и ниша лояльности
были в текущем скомпилированном brief. Ложными оказались сон по общему слову
«восстановление» и запись на приём по техническим «записям в БД».

## Изменения и границы

- До создания policy сохраняется доказательство первоначального допуска:
  identity, фактические лимиты, образы и защищаемые material mounts. Продуктовые
  команды, маршруты и cache IDs могут меняться при сохранении этих ограничений.
  Возобновление проверяет актуальную generation fence. Потерянный существующий
  том не пересоздаётся; неизвестный исход создания остаётся закрытым.
- Запрет восстановления защищённой среды без machine evidence проверяется
  до изменения исходников и данных. Старые pending-журналы без нового admission
  требуют отдельно доказанного восстановления; они не становятся доверенными
  автоматически после обновления программы.
- Ключ кеша SQL bootstrap сохраняет прежнюю размерность. ID исполняемой команды
  учитывает полный envelope. Завершённая операция не запускается заново;
  сохранённый результат читается из журнала с исходной классификацией ошибки.
- `protected_environment_recovery_required` — конкретный терминальный отказ.
  Он прекращает модельный ремонт, локальные fallback и публикацию незавершённого
  результата, сохраняя обязательное освобождение среды. Обычные временные ошибки
  и их ограниченные повторные попытки остаются отдельным поведением.
- Контракт brief различает технические записи и намерение записаться на услугу,
  общее восстановление и восстановление в фитнесе. Явные отрицания и списки
  исключений учитываются без удаления положительно запрошенных функций.

Модель, лимиты шагов, параллелизм и настройки быстрого кеша не понижаются.
Более высокая полезная скорость требует измерения завершённого реального
запуска; количество событий не используется как показатель производительности.

## Приёмка и поставка

Регрессии воспроизводят bootstrap → изменение product manifest → execute,
прерывание и безопасное продолжение, новую fence после отмены, отказ старой
fence, несовместимые ресурсы, неизвестные тома, restore preflight, SQL replay
с неизменным/изменённым proof, терминальный отказ без следующего модельного
вызова и без snapshot с ожидаемым освобождением runtime. Независимое ревью,
Ruff/mypy и полный Linux CI относятся к точной отправленной ревизии.

Поставка расширяет API-only пакет рефакторинга: production compose `full`
обновляет API и оба worker, документированный host `omnia-orchestrator`
получает ту же ревизию. Web сохраняет свою подтверждённую версию. До переключения
проверяются активные runs/operations/leases, создаются резервные копии, временно
закрываются новые записи. Откат возвращает образы API, env и изменённые исходники
host-orchestrator; данные и журналы не откатываются. Сторонние серверные изменения
сохраняются. При неудачном откате ограничение записи остаётся включённым.

Реальная приёмка: новый обычный MAX-проект; две задачи, изменение статуса,
создание и удаление третьей задачи; серверная история и три чистых браузерных
контекста; редактирование заголовка через модель с сохранением данных.
Межпользовательская изоляция требует отдельной HTTP-проверки двух principals.
Проверка серверных тестовых сессий не доказывает вход через сеть MAX.

Успех CI и health не заменяет эту приёмку. Исходный тест на старой версии
завершился `PROVIDER_AUTH_FAILED`; успешная генерация и все реальные сценарии
должны подтверждаться новым receipt. Старый постоянный smoke-проект отсутствует,
поэтому исправление диагностики мониторинга само по себе не устраняет его 502.

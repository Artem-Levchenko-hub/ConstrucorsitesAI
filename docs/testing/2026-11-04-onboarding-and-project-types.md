# Дополнительные замечания: обучение, регистрация, типы приложения

Продолжает опубликованные пакеты `def7c873` и `5eb02290`. Последующие комментарии пользователя добавляются к исходной задаче генерации и каталога.

Принятые требования:

- Регистрация: звёздочки у четырёх обязательных полей и трёх обязательных согласий; рассылка остаётся необязательной. Удалить три пояснения под кнопкой.
- Подтверждение email: показывать введённый адрес, срок ссылки 24 часа и кода 10 минут; ясный текст без «Если письмо уже пришло». API сейчас не доказывает фактическую доставку, поэтому без неподтверждённого «Мы отправили». Повторная отправка подтверждает принятие запроса.
- Первый вход: центральное приветствие перед коротким обучением; далее линейные Next/Back без списка «Раздел обучения». Во время тура фон неактивен. Незавершённый тур возобновляется перед созданием; завершение само не создаёт проект. Прежний completed, повтор обучения, смена аккаунта и ошибки storage учитываются отдельно.
- Обучение: верхняя подпись «Обучение», первая фраза шага про идею без прежнего продолжения, ясная справка по созданию приложения и его запуску в MAX. Исправить перекрытие подсвеченного заголовка руководства.
- Карточки: «Готовые приложения», «Открой готовое приложение и поправь его под себя»; существующий мастер с готовой идеей сохраняется.
- Мастер: можно выбрать несколько типов. Все выбранные сценарии сохраняются при возврате, попадают в проверку и один запрос создания. Первичный тип совместим с прежним API; дополнительные сценарии передаются через существующие features, UI MaxFeature не расширяется произвольными строками. Каталог и его цены/ID сохраняются при другом первичном типе.
- Справка: фраза создания приложения с одной опечаткой в каждом из двух слов предлагает подходящий вопрос; автоматический ответ остаётся строгим, посторонние вопросы не получают ответ по старому контексту.

## Автоматическая проверка каталога — 5 ноября

Старый canary закрывал первый тур и сразу нажимал «Создать приложение». После введения обязательного обучения это снова открывает тур, поэтому мастер недоступен. Offline Chromium воспроизвёл timeout до любого POST создания. Исправленный сценарий ждёт готовности списка проектов и проходит welcome → «Начать обучение» → «Далее» → «Завершить» обычными контролами. Возобновлённый тур после нажатия создания также обработан; существующему владельцу без тура не записывается ложное evidence прохождения. Навигация ограничена восемью переходами. Необязательные туры редактора по-прежнему можно закрыть.

52 проверки включают реальный offline Chromium, неверные цены до POST, ровно один project/prompt при успехе и отсутствие записей storage/cookies со стороны harness. Расширенный прогон в существующем API-окружении с совпадающим uv.lock дал 243/243; Playwright 1.60.0, Ruff и синтаксис — 0 ошибок. Независимый read-only review полного diff — без findings. Первые локальные попытки не дошли до тестов из-за формата `--basetemp`, затем из-за отсутствующего tree_sitter в системном Python; логи сохранены, окружение исправлено без изменения зависимостей и общих настроек.

У найденного приложения ЮKassa callback `/api/integrations/oauth/yookassa/callback` совпадает с реализованным маршрутом Yleum; включены только `checkout:payments_create` и `checkout:payments_get`. Настройки приложения не менялись, grant ещё не выдан, сохранённая привязка магазина не подтверждена. Вход через Яндекс ID требует отдельной авторизации; VK ID заблокирован политикой безопасности встроенного браузера. Обходы аутентификации не применяются.

Исправление обучения опубликовано в `4c85dcf16bfed894e429c6f1edf41622f64dabb9`. Один штатный catalog acceptance `41916115623` запущен через защищённую production QA-учётку на подтверждённых web `44b7c155` и API `07706538`, до выкатки изменений canary. Результат — `login_failed`, cleanup `ok`, без созданного проекта, generation run, snapshot и платных вызовов. В ограниченном окне серверного лога найден один POST `/api/auth/login` с HTTP 401. Это не отличает отсутствующего пользователя от отсутствующего хеша или неверного пароля; браузер также остаётся на форме входа. Значения QA-секретов не извлекаются. Неизменённые credentials повторно не проверялись. Отдельного login-only режима у этого сценария нет; неизвестные CLI-флаги не делают его безопасным dry-run.

При разборе найдены две независимые ошибки harness: отчёт терял безопасный HTTP status, а HTTP-клиенты не передавали Origin после обычного входа. Настоящий `CookieOriginMiddleware` отклоняет такие cookie-authenticated API-записи с 403; это не объясняет исходный 401 до входа. Общий client factory теперь добавляет Origin только для небезопасных same-origin `/api/` запросов, сохраняет явно переданный foreign Origin и не меняет запросы к preview. Повторный вход использует тот же factory; локальное выделение reconnect убрало дублирование и сохранило ответственность за logout каждого выданного сеанса. В отчёт передаётся только валидированный `CanaryFailure.http_status`, без ответа сервера и текста исключения.

RED→GREEN включает настоящий origin middleware, синтетический серверный Set-Cookie, initial/reconnect, runtime/OAuth start/logout и отказ чужому Origin. Шесть canary-файлов: 251/251 за 56,41 с; Ruff четырёх файлов и mypy двух source-файлов — без ошибок. Независимый read-only review полного diff, связанных auth/origin/cleanup и обучения — без findings. Эти проверки не подтверждают устранение фактического login 401 и не заменяют production E2E.

Дополнительная read-only сверка OAuth подтвердила наличие настроенного серверного секрета и правильный callback, но Client ID сервера не совпадает с видимым Client ID найденного приложения Yleum. Сравнивались только хеши, значения реквизитов в evidence не записывались. Несовпадение требует исправления согласованной пары настроек до настоящего grant; параметры кабинета и секрет не регенерировались. Полный путь до сохранённой ready-привязки магазина после refresh остаётся открытым.

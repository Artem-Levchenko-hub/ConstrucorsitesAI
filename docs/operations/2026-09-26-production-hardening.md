## Порядок исполнения и ответственность

Сроки задаются условиями перехода: дата завершения без доступов и длительности
живых генераций была бы выдуманной. Независимые проверки идут параллельно;
Git, миграции и выкладка имеют одного владельца — интегратора.

| Очередь | Ответственный | Работа | Условие перехода |
|---|---|---|---|
| 1, сейчас | Capacity implementer | Бюджет DB-пула, показатели состояний, тест настоящего dispatcher loop | Перекрытие задач, отсутствие дублей, освобождение слотов, сохранение соединения для управления |
| 1, параллельно | Restoration implementer | Schema-only witness hint из полного наблюдённого каталога в исходном prompt | Нет бизнес-значений; hint переживает сокращение отчёта; legacy bundle и проверка целостности сохранены |
| 1, параллельно | Security reviewer + интегратор | Исправить H260, разделить лабораторное и production-доказательство | Отрицательный контроль под superuser, независимое ревью, явный незакрытый риск |
| 2 | Интегратор | Целевые и обязательные пакетные тесты, lint/types, ревью, commit/push, CI точного SHA | Нет P0/P1; P2 исправлены либо явно отложены; нет чужих изменений/секретов в diff |
| 3 | Единственный deployment owner | Тихое окно, backup, штатный production deploy | Рабочий SSH, нет активных/ожидающих генераций и чужой выкладки, CI прошёл |
| 4 | Независимый QA | N=2 генерации; R0/R1/R2; restart/fault matrix | Данные/поведение подтверждены независимо от модели; один расчёт; точные SHA |
| 5 | Security implementer + reviewer | Ограниченная роль trusted core и обязательный A/B release gate | Миграция существующего core, Docker/K8s, восстановление и отказ без утечки |
| 6 | Infra/оператор + ответственный за данные | Restore drill, удаление/сроки, мониторинг, договорная карта | Практическое восстановление и удаление, измеренные сроки, ответственные и доказательства |

Не запускать новую платную генерацию, если уже существующая пара версий и
сохранённые синтетические данные закрывают тот же пробел. Не повторять прошедший
тест без изменения его зависимостей. Экономия измеряется временем, числом модельных
вызовов и принятыми сценариями; снижение качества не считается оптимизацией.

## Приёмка параллельной генерации

1. Два разных QA-проекта, отдельные резервации и generation IDs. Начать с двух,
   а не со стресс-теста на 64. Один проект не получает двух одновременных владельцев.
2. Записать моменты model/build фаз: `max(start_A, start_B) < min(end_A, end_B)`.
   Две ожидающие coroutine или счётчик active=2 этого не доказывают.
3. При исчерпанных ресурсах показать waiting_capacity отдельно от running;
   допускается ожидание, не ложная ошибка и не двойное списание.
4. Отменить один QA-run: lease/слот/резервация освобождаются, соседний завершается.
5. Перезапуск воркера на отдельной тестовой среде не воспроизводит уже исполнявшийся
   запрос модели и не присваивает чужой advisory lock.
6. При загруженном хосте A задача для свободного B должна начать работу. Текущий
   FIFO может заполнить все coroutine ожиданием A; fairness остаётся открытым
   отдельным изменением. Ограничение DB-пула не закрывает этот пункт.

## Приёмка откатов

Обязательный контракт — [max-restoration-test-contract.md](../testing/max-restoration-test-contract.md).
История выполнения — [план 21.09](../plans/2026-09-21-max-rollback-completion.md).
Замороженные проверки не ослабляются ради зелёного результата.

| Сценарий | Действие | Обязательные доказательства |
|---|---|---|
| R0 | Exact-возврат при доказанно пустых бизнес-объектах | Полный inventory; восстановление запускается; новый CRUD работает; AI-вызовов и списания нет |
| R1 | Exact-возврат при совместимых непустых данных | IDs/owners/связи/скрытые колонки/значения сохранены; CRUD после reload; AI-вызовов и списания нет |
| R2 | Несовместимость → needs_changes → явное «Адаптировать и восстановить» | Одна принятая генерация, адаптация исторического кода, неизменный schema digest, completed, независимый CRUD и A/B denial, один расчёт |
| R2-refusal | Неполный каталог, неверный witness, повреждённый bundle или неуспешный probe | Кандидат не активируется, старая версия доступна, диагностика сохраняется без данных/секретов |

Образец witness — подсказка имён из каталога, не свидетельство корректности.
Нельзя заменять им подпись/binding, SQL-сверку, независимый CRUD и проверку чужого
пользователя. Нельзя выдумывать значения обязательных FK/CHECK-полей.

Пять отказов проверяются на одноразовых ресурсах с той же версией компонентов:

1. Crash API после `proof_ready`, до commit.
2. Crash воркера после durable offer.
3. Рестарт orchestrator во время активации.
4. Потерян ответ уже принятого apply.
5. Два callback одного результата.

Во всех случаях: однозначный итог после reconcile, не более одной активации,
версии и settlement; отсутствие второй генерации; сохранение данных; lease
освобождён либо явно quarantined. После точки невозврата проверяется доведение
вперёд, а не опасное переключение на старую БД. Журнал попытки должен объяснять
фазу, возраст, следующий reconcile и доступное действие оператора.

## Матрица безопасности

Использовать два синтетических создателя, по два пользователя MAX и отдельные
приложения. Сохранённые артефакты содержат только обезличенные итоги и контрольные
хеши. Отсутствие доступа — «не проверено», а не PASS.

| ID / приоритет | Граница | Испытание | Критерий |
|---|---|---|---|
| S01 / P1 | MAX → доверенный core | Неверная/просроченная подпись, пустая личность, чужой app/bot, повтор и сессия после logout | Отказ до чтения данных; собственная валидная сессия работает; секрет не попадает в клиент |
| S02 / P1 | Пользователь A → данные B | GET/list/detail/search/export, PATCH/DELETE, связи и файлы через API и Server Actions | Нет чужих данных и побочных изменений; независимое чтение B это подтверждает |
| S03 / P1 | Создатель A → проект B | Preview, snapshot/download, restore, logs, integrations, deployment, delete | Проверка владельца на каждом входе; чужая операция не стартует |
| S04 / P1 | Trusted core → PostgreSQL | Узнать current_user/rolsuper/rolbypassrls через фактическое подключение процесса; запрос без фильтра | Runtime не superuser/BYPASSRLS и не может получить такую роль; без личности нет чужих строк |
| S05 / P1 | Произвольный код → core/хост/сосед | Env/volume/network boundaries, metadata/SSRF, Docker socket, filesystem, подмена actor | Нет core/admin DSN и управления хостом; ограничение SQL личности проверено отдельно |
| S06 / P1 | Кандидат → публикация | Встроить контролируемый IDOR в disposable candidate | Gate обнаруживает именно доступ B и блокирует публикацию; прежняя версия работает |
| S07 / P1 | Платформа → копии/откаты | Restore drill в новой изоляции, corrupt/missing backup, проверка owners/digest | Восстановлены схема и данные; измерены RPO/RTO; повреждённая копия не принимается |
| S08 / P1 | Секреты | Наличие секретов в git/history/image/client/log/CI без вывода значений; доступы и ротация | Нет непредусмотренного распространения; для раскрытых реквизитов смена и отзыв доказаны |
| S09 / P2 | Аккаунт → удаление | delete_after, остановка доступа, purge worker, повтор/restart, копии/legal hold | Доступ отозван сразу; физическое удаление/исключения соответствуют документированным срокам |
| S10 / P2 | Внешняя сеть → серверы | Инвентарь firewall/listeners/TLS/SSH/patches и least privilege | Открыты только необходимые входы; ключевой доступ работает; проверены все три узла |
| S11 / P2 | Инцидент → оператор | Синтетический отказ/утечка-сигнал вне customer data | Алерт дошёл; ответственный и процедура сохранения доказательств известны |
| S12 / P2 | Данные → договоры/провайдеры | Карта целей/оснований/ролей/получателей/сроков/мест хранения | Карта соответствует фактическому MAX, AI, логам и backup; документы проверены ответственным и юристом |

P1 здесь обозначает приоритет незакрытой защиты перед заявлением о готовности,
а не утверждение, что эксплуатация или утечка уже обнаружена.

### Ограниченная роль trusted core: безопасный следующий шаг

1. Controller/helper выполняет миграции и выдаёт DML-права отдельной роли
   `NOSUPERUSER NOBYPASSRLS NOCREATEROLE`; владелец схемы не доступен runtime.
2. `server.js` получает только runtime DSN. Admin DSN не остаётся в env процесса,
   файлах, образе или доступном ему secret. Простая замена DATABASE_URL после
   запуска в контейнере с доступным admin secret границу не доказывает.
3. Docker и K8s проходят одинаковые проверки создания, повторного применения,
   рестарта, ротации, обновления существующего core и сохранения данных.
4. Проверить отсутствие SET ROLE к привилегированной роли и DDL/TRUNCATE.
   `withMaxUser` с непроверенным GUC не защищает произвольный недоверенный SQL;
   эта угроза требует отдельного broker/подписанного actor либо другого контракта.
5. Не удалять старую роль/секрет до успешного upgrade и заранее проверенного
   восстановления. Возврат к superuser не считать безопасным security rollback.

### Локальный кандидат

- Effective cap генерации: `min(configured, (20−4)//2)`, то есть максимум 8
  при текущем общем пуле. Default 8 сохранён. Это защищает от исчерпания пула
  одними ownership-checkout, но не доказывает отсутствие всех возможных

- Heartbeat различает running/waiting_capacity/other и configured/effective;
  статусы являются снимком сканирования, а не измерением model calls.

  mixed-case identifiers. Необязательные подсказки не могут переполнить 64 КиБ

до pushed SHA, полного CI, выкладки и live acceptance они не считаются доставленными.

## Основа проверки

- [PostgreSQL 16: Row Security Policies](https://www.postgresql.org/docs/16/ddl-rowsecurity.html):
  superuser/BYPASSRLS обходят политики; FORCE относится к обычному владельцу.
- [MAX: проверка данных мини-приложения](https://dev.max.ru/docs/webapps/validation).
- [OWASP ASVS](https://owasp.org/www-project-application-security-verification-standard/)
  и [API Security](https://owasp.org/www-project-api-security/) — карта требований,
  а не сертификат безопасности проекта.

Юридическая ответственность не выводится из наличия RLS или договора одной
строкой. Фактическая карта обработки и тексты документов должны быть отдельно
проверены; этот технический план не устанавливает, кто отвечает перед регулятором.

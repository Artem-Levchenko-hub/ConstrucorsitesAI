# Защищённые данные MAX-приложений

## Что реализовано

Доверенное MAX-ядро предоставляет CRUD `/api/omnia/data`. Целиком шифруется JSON payload записи: AES-256-GCM, случайный nonce, проверка целостности и привязка к проекту, коллекции, записи, владельцу, ревизии и версии ключа. Поля поиска и доступа (`project_id`, `collection`, `id`, `owner_id`, даты, revision) остаются открытыми. Существующие бизнес-таблицы и MAX-профили этим механизмом не преобразуются.

Доступ по умолчанию только владельцу записи; администратор бизнеса не получает скрытый обход. Общие коллекции и делегирование сотрудникам не реализованы. Проверенный пользователь поступает из MAX-сессии. Идентификатор владельца из тела запроса запрещён. Создание/изменение/удаление и аудит проходят в одной транзакции; аудит не содержит payload. PUT полностью заменяет payload и требует текущую revision. Удаление тоже требует revision.

Новые отдельные PostgreSQL проекта защищаются до запуска первого пользовательского процесса: controller migrations, runtime role без административных прав, подписанный actor и RLS. Существующая неизвестная БД не переводится автоматически на пустую схему. Это отдельный механизм от шифрованного CRUD в managed core.

## Включение на production

Для включения нужен обслуживаемый Vault по HTTPS с корректным сертификатом, резервированием и проверенным восстановлением. Он может работать на том же сервере отдельным сервисом. Такой вариант защищает от утечки SQL-дампа, но не отделяет ключи от злоумышленника с полным доступом к серверу. Отдельный сервер/KMS даёт другую границу хранения ключей. На проверенном production Vault пока отсутствует. Не включать флаг до выполнения всех условий ниже.

Локальный Vault слушает только loopback, работает отдельным непривилегированным пользователем и не получает Docker socket. Для частного TLS CA задаётся явный `CELL_DATA_VAULT_CA_FILE`: переменные `SSL_CERT_FILE` и системное хранилище сами по себе не меняют доверие клиента с `trust_env=False`. Проверка сертификата и hostname остаётся обязательной.

Режим запуска выбирается явно. При Shamir и хранении unseal-материала вне сервера после рестарта нужна разблокировка оператором. Хранение этого материала на том же сервере позволяет автоматизировать запуск, но не защищает от компрометации всего хоста. Нельзя обещать одновременно автономный запуск без внешнего сервиса и отсутствие материала разблокировки на хосте. Runtime tmpfs после reboot пуст: сначала восстанавливается доступ к Vault, затем keyrings и cores. До включения необходимо проверить этот порядок и восстановление из копии.

Оператор Vault заранее создаёт Transit key `omnia-app-data` с `type=aes256-gcm96`, `derived=true`, `exportable=false`, `allow_plaintext_backup=false`. Клиент не создаёт ключ автоматически. Токену нужны `read` для `transit/keys/omnia-app-data`, `update` для `transit/encrypt/omnia-app-data` и `transit/decrypt/omnia-app-data`; административные права не нужны. Не выдавать токен браузеру, проекту или генератору.

Host orchestrator читает `/opt/omnia/apps/orchestrator/.env`. Настройки:

| Переменная | Назначение |
|---|---|
| `CELL_DATA_VAULT_ADDRESS` | HTTPS origin отдельно обслуживаемого Vault; пусто означает CRUD недоступен |
| `CELL_DATA_VAULT_TOKEN_FILE` | Приватный файл токена; по умолчанию `/etc/omnia/app-data/vault-token` |
| `CELL_DATA_VAULT_CA_FILE` | Необязательный PEM-файл доверенного CA для локального/private TLS; пусто — стандартные доверенные CA |
| `CELL_DATA_VAULT_MOUNT` | Transit mount, по умолчанию `transit` |
| `CELL_DATA_VAULT_KEY` | Заранее созданный Transit key, по умолчанию `omnia-app-data` |
| `CELL_DATA_WRAPPED_KEY_ROOT` | Только зашифрованные DEK, по умолчанию `/opt/omnia-runtime/app-data-wrapped-keys` |
| `CELL_DATA_RUNTIME_KEY_ROOT` | Только tmpfs; по умолчанию `/dev/shm/omnia-app-data-keys` |

Директории и токен принадлежат пользователю host orchestrator; директории 0700, токен 0600. Runtime-файл имеет 0444 внутри приватной директории; только он монтируется read-only в immutable core как `/run/omnia-data/keys.json`. Сгенерированный процесс не получает этот mount, Vault token или ключи. Swap должен быть выключен, поскольку tmpfs может выгружаться в swap. Провайдер проверяет tmpfs и запрещает обычный диск для открытых ключей.

Нужно собрать новый immutable core через документированный `scripts/build-public-max-core.sh`, задать его digest в `CELL_PREVIEW_CORE_IMAGE` и `CELL_PUBLIC_CORE_IMAGE`. Image должен иметь label `omnia.max-core.secure-data-protocol=1`. Изменение ключевого mount пересоздаёт только trusted core; база и пользовательские данные сохраняются.

Это НЕ настройка шифрования дисков. Шифрование физических томов PostgreSQL, старых данных, вложений и всех копий требует отдельной подготовки хранилища и переноса с проверкой восстановления. Автоматическое преобразование действующего root-диска в эту поставку не входит. Не заявлять «все базы зашифрованы» по наличию CRUD.

## Генератор и API

При доступном `secure_data_crud` инструкция генератору требует сохранять чувствительные данные через готовый браузерный клиент:

```typescript
import { secureCollection } from "@/lib/omnia/data-client";
const notes = secureCollection<{ text: string }>("notes");
const { record } = await notes.create({ text: "Личная заметка" });
await notes.get(record.id);
await notes.list({ limit: 20 });
const changed = await notes.update(record.id, record.revision, { text: "Изменено" });
await notes.delete(changed.record.id, changed.record.revision);
```

Коллекции: 1–64 ASCII-символа, первая строчная буква, затем строчные буквы/цифры/`_`/`-`. Payload — JSON-объект до 64 KiB; HTTP body до 256 KiB. Пагинация по UUID, лимит 1–100. Поиск по содержимому шифротекста не предоставляется.

| Запрос | Тело / результат |
|---|---|
| `POST /api/omnia/data/notes` | `{ "payload": { "text": "..." } }` → 201 `{record}` |
| `GET /api/omnia/data/notes?limit=20` | `{records,nextCursor}` |
| `GET /api/omnia/data/notes/ID` | `{record}` |
| `PUT /api/omnia/data/notes/ID` | `{ "revision": 1, "payload": { "text": "..." } }` → `{record}` |
| `DELETE /api/omnia/data/notes/ID` | `{ "revision": 2 }` → 204 |

Ошибки: 401 без сессии; 403 неправильный Origin; 404 чужая/отсутствующая запись; 409 устаревшая revision; 503 ключи/хранилище недоступны. Открытый текст не используется как запасной вариант. Ответы `Cache-Control: no-store`. В браузере разрешены запросы только со своего origin.

## Восстановление и ротация

Для восстановления одновременно необходимы: SQL-копия managed PostgreSQL, весь каталог wrapped DEK, соответствующий Transit key и все его нужные исторические версии во внешнем Vault. Наличие только SQL dump недостаточно. Зашифрованные DEK и `data-key-binding.json` нужно включить в отдельную проверенную off-host копию; существующая копия платформенной БД не доказывает охват Project Cell PostgreSQL. Runtime tmpfs в backup включать нельзя.

Из каталога orchestrator:

```text
uv run python scripts/manage-app-data-keys.py verify PROJECT_UUID
uv run python scripts/manage-app-data-keys.py rotate PROJECT_UUID
```

Verify восстанавливает runtime keyring из Vault и не выводит ключи. Rotate сохраняет старые DEK, добавляет новый и требует штатного пересоздания core для новых записей новой версией. Старые записи читаются старым DEK. Автоматического удаления ключей нет. После 32 версий ротация отказывается продолжаться, не удаляя историю. Потерянный keyring установленного проекта не генерируется заново.

## Ручная проверка пользователем после включения

1. Создать два MAX-аккаунта для проверки и приложение с личными заметками на `secureCollection`.
2. Первым аккаунтом создать заметку, перечитать после закрытия и повторного открытия приложения.
3. Изменить заметку; отправить изменение со старой revision — получить 409, сохранить актуальную запись.
4. Вторым аккаунтом проверить список и попытаться прочитать, изменить, удалить ID первого — получить 404.
5. Первым аккаунтом удалить заметку; после перезагрузки запись отсутствует.
6. Для инфраструктурной приёмки оператор отдельно проверяет SQL ciphertext, restart, восстановление копии и rotation. Пользовательские клики этого не доказывают.

Автоматические тесты выполняются на одноразовой PostgreSQL и синтетических данных; ручная приёмка реального бизнес-приложения остаётся за пользователем.

# Commerce: ограничение роста архивов окружений

## Подтверждённая причина

28 сентября 2026 года файловая система commerce имела размер 206900281344 байта
(192,7 GiB), использовано 192134385664 байта, доступно 14749118464 байта: 93%.
Это диск примерно 200 GB; объём дисков других серверов нельзя переносить на commerce.

`/opt/omnia-runtime/state/project-machines/artifacts` занимал 157269450752 байта.
Найдено 737 tar и 736 файлов подтверждения `.tar.ok` в 25 каталогах проектов.
В исследованных больших архивах примерно 668 MB из 689 MB занимал `node_modules`.
Каждая остановка машины сохраняла новую полную копию томов. Старые архивы после
замены ссылки оставались; регулярной очистки не было. Просмотр только host JSON
дал 533 кандидата на 113,3 GiB и 33,1 GiB сохраняемых архивов. Эти кандидаты ещё
не доказаны: старые версии содержат дополнительные ссылки в `machine.json`
внутри Docker checkpoint-томов. Перед удалением обязателен полный пересчёт
обоих источников ссылок.

Похожая очистка уже описана в `publication-performance-baseline.md` (18 сентября).
Ночная резервная копия state исключает каталог artifacts; она не является
основанием для удаления нужного архива. Docker volumes остановленных проектов
также нельзя считать мусором по признаку dangling.

## Защита

- Сборщик сохраняет любой архив, имя которого встречается в любом валидном JSON
  state или Docker checkpoint, а также файлы моложе двух часов. Это сохраняет текущие окружения,
  версии, восстановление и свежие ссылки скачивания.
- Неоднозначный, повреждённый, слишком большой или недоступный JSON, небезопасный
  путь и активная публикация останавливают очистку. Содержимое state не печатается.
- Docker inventory читает только `machine.json` в существующих checkpoint-томах.
  Временный helper использует уже установленный локальный образ, чтение без
  записи и без сети; после проверки удаляется. Ошибка Docker, отсутствующий
  том сохранённой версии или небезопасные метаданные останавливают очистку.
  Имена, записанные до создания тома, допускаются только после строгой проверки
  полного журнала: в нём не должно быть checkpoint/restore операций или ссылок.
- Удаление берёт тот же межпроцессный workspace lock, что controller, затем
  заново читает все ссылки и проверяет идентичность каждого кандидата. Занятые
  проекты пропускаются. Сборщик работает от владельца state, не от root.
- Таймер запускается каждые 15 минут с задержкой до двух минут. Ошибка остаётся
  в журнале systemd; исправление причины ошибки обязательно, иначе рост продолжится.
- Неудачный снимок удаляет только собственные новые архивы. Предыдущий снимок и
  повторно использованный rootfs сохраняются.
- Захват проверяет свободное место до остановки приложения и перед записью
  каждого блока: резерв 10 GiB. Это защита общих архивов, а не физическая квота
  каждого клиента. Другие потребители диска и объём нужных версий требуют контроля.

## Доставка и первый запуск

1. Пройти orchestrator tests, ruff, mypy и Linux проверки symlink/lock; независимое
   ревью; commit/push; зелёный CI именно доставляемого SHA.
2. Проверить отсутствие активных генераций через
   `infra/release/check-active-generations.sh` на core. Доставить SHA через
   `infra/release/deploy-prod.sh <sha> --no-web`, используя production compose
   `apps/llm-gateway/deploy/full`; подтвердить ревизии и health core/commerce.
3. На commerce сохранить закрытый агрегированный отчёт и контрольные суммы
   архивов со ссылками, метаданных state и список контейнеров/томов. Не сохранять
   клиентские payload или секреты в диагностический журнал.
4. От владельца state выполнить предварительный просмотр. На проверенном commerce
   `/opt/omnia` указывает на `/opt/yleum`; installer разрешает этот alias:

   ```sh
   cd /opt/omnia/apps/orchestrator
   .venv/bin/python scripts/cleanup_orphan_archives.py --state-root /opt/omnia-runtime/state
   ```

5. Если просмотр завершился успешно, применить тот же сборщик с `--apply`.
   Сборщик самостоятельно пересчитывает ссылки под блокировками. Сверить
   контрольные суммы сохранённых архивов/state и неизменность контейнеров/томов;
   проверить свободное место. Повторный запуск должен быть безопасен.
6. Установить таймер с production checkout, сначала проверив план:

   ```sh
   sudo bash /opt/omnia/infra/max-k3s/cells/55-archive-retention.sh
   sudo bash /opt/omnia/infra/max-k3s/cells/55-archive-retention.sh --apply
   systemctl status yleum-archive-gc.timer --no-pager
   sudo systemctl start yleum-archive-gc.service
   journalctl -u yleum-archive-gc.service -n 10 --no-pager
   ```

7. Подтвердить service exit 0, активный таймер и следующий запуск; HTTP health
   production. Не запускать платные генерации или восстановление клиентского
   проекта ради проверки очистки.

## Наблюдение и откат

Контролировать свободное место и число/байты удалённых, сохранённых и пропущенных
архивов в JSON-отчёте, а также `systemctl is-failed yleum-archive-gc.service`.
Если свободное место снова сокращается, сначала разобрать отчёт: нужные версии
не удаляются автоматически. При отказе снимка из-за резерва не уменьшать резерв
без анализа занимаемого пространства. Таймер не очищает Docker volumes, БД,
пользовательские файлы или журналы.

Для остановки очистки: `sudo systemctl disable --now yleum-archive-gc.timer`,
затем `sudo systemctl stop yleum-archive-gc.service`. Предыдущие units сохранены
в `/var/backups/yleum-archive-gc/<timestamp>-<pid>`; восстановить их при необходимости
и выполнить `systemctl daemon-reload`. Удалённые неподключённые старые архивы
отключение таймера не возвращает. Нужные архивы должны пройти контроль сохранности
до принятия результата.

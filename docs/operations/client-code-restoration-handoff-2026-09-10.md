# Откат MAX: состояние работ на 10 сентября 2026

Это передача текущего результата по запросу пользователя, а не объявление готовности
production. Основная реализация отправлена в `main` коммитом `f2e0177d`.
Исправления и этот документ идут следующим коммитом. Функция по умолчанию выключена.
На рабочий сервер новый код ещё не выкладывался.

## Что реализовано

- Историческая версия восстанавливается как новый текущий черновик. Текущая база
  и накопленные бизнес-данные сохраняются. Публикация — отдельное действие.
- Постоянная операция подготовки, отчёт совместимости, явное применение, отмена,
  повтор запросов и восстановление статуса после обновления страницы.
- Проверка старого кода в отдельной среде на копии текущих данных. Изоляция
  пользователей, ограниченная роль PostgreSQL и подписанная идентификация запросов.
- Сохранение результата активации до изменения истории API, сверка фактического
  результата после потерянного ответа, восстановление прежнего кода при сбое.
- Адаптация неподходящей версии: генератор получает проверенные исходники выбранной
  версии, а не только её идентификатор в тексте. Запрос отправляет сам пользователь.
- Правила агента на английском и команда контроллера
  `omnia-db apply .omnia/data-contract.json` для поддерживаемых добавлений в схему.
- UI, миграция `0061_code_restorations`, общий контроль конкурирующих операций,
  контракт публикации и отдельная база публичного приложения.

Устройство, поддерживаемые случаи и 14 категорий оставшихся рисков описаны в
[рабочем контракте](client-code-restoration.md). Нельзя считать поддержку произвольных
SQL-схем, бизнес-смыслов и сторонних эффектов доказанной.

Ссылка на исходный CI:
[run 34410192247](https://github.com/Artem-Levchenko-hub/ConstrucorsitesAI/actions/runs/34410192247).
Его красный статус нельзя называть полным зелёным gate: исправления требуют нового CI.

Реальный одноразовый Docker/Next.js/PostgreSQL сценарий подтвердил:

1. Переход v2 → v1 → v2.
2. Чтение и запись двух пользователей с отказом в изменении чужих записей.
3. Сохранение скрытой фамилии, новых строк и изменений, сделанных после подготовки.
4. Наблюдение уже выполненного переключения новым экземпляром контроллера.
5. Первую явную публикацию v1 и независимую запись в публичную базу.
6. Сохранение публичной v1 после переключения черновика на v2.

Повторная публикация v2 остановилась на проверке immutable-образа при возобновлении
черновика. Проверка исправлена и покрыта тестами, но весь живой сценарий после этого
исправления ещё не повторён. Публичная v1 осталась доступной до удаления тестового
окружения. Перезапуск защищённой среды и следующая генерация в этом полном сценарии
до конца не проверены. Не выдавать этот запуск за полноценную приёмку.

Локальная Windows-сборка web скомпилировала приложение и страницы, но упаковка
standalone завершилась `EPERM` при создании символических ссылок. Соответствующие
Linux-сборки web и Docker-образов в CI прошли.

## Что осталось, по порядку

1. Получить полностью зелёный CI на последнем отправленном коммите, включая весь API.
2. Повторить реальный runtime canary после исправления образа. Обязательно проверить
   повторную публикацию v2: запись `PUBLIC ONLY` и скрытая фамилия должны сохраниться
   в публичной базе. Затем проверить остановку/возобновление среды и добавление поля
   через следующую генерацию с её настоящим lease/fence.
3. Завершить и проверить стенд HTTP-приёмки на новом синтетическом проекте. Нужны
   настоящие Git/SQL версии и каноническая ячейка, без FakeRuntime, выдуманного
   GenerationRun или подменённого подтверждения контроллера. Сам откат проверить
   через авторизованные API prepare/status/apply/cancel: повторы, устаревший отчёт,
   F5, одна новая версия, чтение/запись и отказ другому владельцу.
4. Перед выкладкой проверить отсутствие всех незавершённых генераций, операций ячеек,
   аренд и восстановлений; сохранить сторонние серверные изменения и сделать
   резервные копии PostgreSQL, конфигурации и метаданных контроллера.
5. Собрать и выложить точный отправленный SHA через документированный compose
   `full` в `/opt/omnia/apps/llm-gateway/deploy/full/docker-compose.yml` и сервис
   `omnia-orchestrator.service`. Миграция API должна примениться до старта workers.
   Не использовать `infra/` и не выполнять `docker compose down -v`.
6. Проверить фактические SHA API/web/orchestrator/workers, HTTP readiness и heartbeat.
   Выполнить HTTP-приёмку, удалить только её ресурсы и зафиксировать доказательства.
   Только после этого объявлять откат готовым для клиентов.

Для отката самой платформы после миграции 0061 нужен совместимый запуск прежнего API
без попытки старого Alembic прочитать неизвестную ему ревизию. Схему бизнес-данных
при такой операции назад не возвращать. Открывать шлюз записи только после
подтверждённого восстановления сервисов и heartbeat.

Проверочные скрипты в `.artifacts/client-restore-20260909/` — локальные материалы
оператора, а не доказательство выполненной HTTP-приёмки. Не публиковать их частные
дампы, конфигурацию, токены, необработанные журналы и архивы окружений в Git.

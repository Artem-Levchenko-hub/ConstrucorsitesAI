Дата живой проверки: 20 сентября 2026 года
QA-проект: `760144ab-57ca-40c1-a9db-918d3f9b6816`
Project Cell: `438e65bd-4fef-4a01-b1a8-875b13ec0259`
Исходная production-ревизия проверки: `71808582663f9bae87fdd65c480e6398e8d520ff` для API/worker и `94f0a96e12e734bf9758cc878d2e55f6d864f4ae` для orchestrator.

Этот документ фиксирует выполненные живые сценарии, обнаруженные отказы и обязательные условия выпуска. Пользовательский `MAX_Studio_Versioning_Completion_Plan_v4 (1).md` использован как спецификация и источник проверяемых сценариев, а не как инструкция запускать непроверенные действия.

## 1. Решение о готовности

Обычный откат уже доказан в двух основных ветках MVP:

1. Если бизнес-данных нет, исторический код и подготовленная пустая база восстанавливаются автоматически без ИИ.
2. Если бизнес-данные есть и текущая структура совместима с историческим кодом, exact-откат выполняется автоматически без ИИ и сохраняет записи.

Несовместимый адаптивный откат на исходной production-ревизии пока не прошёл. Система правильно обнаружила несовместимость `qa_tasks.title` и `qa_tasks.summary`, показала две существующие бизнес-записи и потребовала явный запуск ИИ. Первый dispatch сохранил запрос, но не подтвердил запуск; штатный идемпотентный повтор создал одну генерацию. Затем запуск безопасно остановился до передачи управления агенту:

```text
Адаптация остановлена до запуска агента: изолированная копия базы данных не подтверждена.
```

Текущая версия v9 и бизнес-данные после отказа остались доступны. Это правильный fail-closed результат, но не рабочий адаптивный откат.

Новый код добавляет отсутствующий протокол изолированного кандидата, proof, атомарного переключения и восстановления после сбоев. До повторного живого прогона он не считается production-доказанным.

## 2. Что проверено живым пользовательским путём

### 2.1. Версия без бизнес-данных

Проверено:

- создано рабочее MAX Mini App с отдельной PostgreSQL;
- создана следующая версия с новой обязательной скалярной колонкой;
- перед откатом бизнес-таблица была пустой;
- возврат к исторической версии прошёл автоматически;
- ИИ не запускался;
- исторический интерфейс открылся;
- после отката можно было создать новую запись.

Результат: ветка MVP без бизнес-данных работает.

### 2.2. Совместимые бизнес-данные

Проверено:

- до отката существовала пользовательская запись;
- анализатор признал исторический код совместимым с текущей БД;
- exact-откат был применён автоматически без ИИ;
- существующая запись сохранилась;
- после отката выполнены create и update;
- после reload изменённое значение сохранилось.

Результат: совместимый exact-откат с бизнес-данными работает.

### 2.3. Несовместимые бизнес-данные

Для реальной несовместимости создана v9:

- колонка `qa_tasks.title` переименована в `qa_tasks.summary` прямой data-preserving миграцией;
- старой колонки `title` в новой структуре быть не должно;
- API, формы и список работают через `summary`;
- видимый заголовок: `Мои QA-задачи · adaptive live`;
- до подготовки отката существовали две записи;
- отдельная запись `Adaptive v9 live fixture updated` сохранила описание `Сохранить через адаптивный откат` после update и reload.

Подготовка v9 → v1 вернула точный результат `needs_changes`:

- v1 читает отсутствующее поле `qa_tasks.title`;
- v1 создаёт строки без обязательного `qa_tasks.summary`;
- текущая база содержит две строки `qa_tasks`;
- пользователю показано, что будет создан новый адаптированный черновик и будет израсходован лимит ИИ;
- текущая база и публикация до доказанного применения не заменяются.

Фактический результат запуска адаптации на исходном проде: FAIL до запуска агента, потому что старый orchestrator не подтвердил isolated database copy.

## 4. Главный технический блокер живого продакшена

Вход агента защищён обязательным capability gate:

```text
database_admin = isolated_copy
restoration_adaptation_database_copy_v1 = true
```

Production API уже требовал эти признаки, а работающий production orchestrator был на более старой ревизии и не умел подготовить и аттестовать изолированного кандидата. Поэтому система отказала до model-run. Ослаблять gate нельзя: без него агент получил бы инструменты БД, способные изменить live-данные до финального доказательства.

Текущий внешний production smoke дополнительно красный из-за постоянного MAX-canary: `fitnessstat-a379d4` отвечает `502` на `/api/health` и webhook probe. Web и API самой платформы отвечают `200`, а их release identity совпадает с ожидаемой. Canary нужно восстановить либо заменить другим постоянным подтверждённым проектом до объявления production readiness.

Исправление состоит в согласованной поставке API и orchestrator:

1. Orchestrator создаёт независимый candidate workspace и копию БД.
2. Receipt связывает project, owner, generation run, operation, source snapshot, commit, fencing epoch и digest.
3. API допускает агента только по server-verified receipt.
4. Агент работает только с кандидатом.
5. Независимый proof проверяет сборку, runtime, CRUD, сохранность данных и owner boundary.
6. API записывает proof intent и outbox до внешнего эффекта.
7. Активация делает forward-only переключение под fencing и canonical lock order.
8. После точки невозврата сбой восстанавливается вперёд; старый код не возвращается к уже изменённой БД.

## 5. Найденные дефекты и принятые решения

### P0/P1 — блокируют адаптивный MVP

#### R1. Старый orchestrator не подтверждает isolated DB copy

Живое воспроизведение: генерация завершилась за 40 секунд и один шаг до запуска агента.

Решение: выкладывать API и orchestrator одной совместимой ревизией; не ослаблять gate и не разрешать fallback на live Project Cell.

#### R2. Потеря SQL-коммита после успешного proof могла уничтожить кандидата

Опасное окно: controller уже вернул `proof_ready`, но сохранение proof в SQL упало. Без durable recovery intent run оставался `issued`, lease мог освобождаться, а cleanup — удалить доказанного кандидата.

Решение:

- сохранять durable proof-request intent до внешнего запроса;
- повторять тот же proof request по idempotency binding;
- удерживать lease и candidate, пока proof intent не завершён;
- включать незавершённый proof в reconciliation;
- создавать activation outbox атомарно с SQL proof.

#### R3. Частичное переключение после точки невозврата

Решение: после sealed proof и начала apply разрешён только forward recovery. Обычный rollback файлов или БД запрещён. Routing, runtime, source manifest и release binding сводятся к одному подтверждённому состоянию.

#### R4. Двойное списание или двойная версия при повторе callback

Решение: COMPLETE/CANCELLED callbacks идемпотентны; offer/apply/cancel используют durable idempotency keys; settlement и version creation выполняются один раз.

### P2 — обязательны до выпуска

#### R5. Object storage I/O под SQL/advisory locks

Чтение source manifest из MinIO внутри project advisory lock и `FOR UPDATE` могло заблокировать cancel и остальные переходы проекта при зависшем S3.

Решение: immutable manifest читается до блокировок, затем bindings повторно проверяются под canonical lock order.

#### R6. Неактуальная проверка Alembic head

Новая цепочка должна быть закреплена как `0067 → 0066 → 0065`, с одним head и реальным upgrade/downgrade roundtrip.

#### R7. Pending activation ошибочно завершалась как generation failure

Решение: `AdaptationActivationPending` остаётся ожидающим durable-состоянием; lifecycle и supervisor не публикуют `llm.error` и не финализируют run как failed.

#### R8. Полная suite оркестратора выявила тестовые дефекты

Первый полный прогон нового дерева:

```text
1899 passed, 62 skipped, 15 xfailed, 8 failed
```

Шесть ошибок относились к Windows-кодировке fixture: тест записывал nginx-конфиг в системной кодировке и production-код читал UTF-8. Две ошибки означали, что golden manifest шаблона не включал новый обязательный маршрут `actions/[id]`. Fixtures и golden manifest исправлены. После последующих recovery-исправлений полный локальный прогон завершился результатом `1917 passed, 63 skipped, 15 xfailed`.

#### R9. Повторная авария cleanup оставляла неверный fencing epoch

Первое исправление выдерживало одну потерю результата, но второй сбой после reconcile приводил к `stale fencing epoch` для `release` и `destroy`. После расширения цепочки независимый review нашёл соседний дефект: обычный успешный reconcile без второго сбоя ложно считался циклом.

Решение:

- обходить всю подтверждённую cleanup retry-chain с ограничением глубины 16;
- на каждом звене проверять тип операции, request digest, generation lease и строго возрастающий fence;
- отклонять циклы, чужие и устаревшие связи;
- после успешного reconcile перечитывать durable-запись в текущей итерации, не регистрируя тот же operation ID второй раз;
- отдельно проверять обычное восстановление и два последовательных crash/reconcile цикла для `release` и `destroy`.

Итог: exact recovery/guard-набор `6 passed`, workspace-набор `40 passed, 1 skipped`.

#### R10. Real-PostgreSQL тест загрязнял следующий тест служебной схемой

Первый Linux CI-прогон прошёл 1943 теста и обнаружил два падения inventory. Причина: новый real-PostgreSQL тест создавал `drizzle.__drizzle_migrations`, а общая disposable fixture не очищала произвольные non-system schemas после завершения. Следующий тест правильно возвращал `unsupported=true`. Production inventory не ослаблялся.

Решение: единый reset удаляет все non-system schemas с безопасным `%I` quoting и large objects до и после real-PG fixture. Очистка разрешается только после явного подтверждения фактического имени БД; при несовпадении имени выполняется ноль разрушительных запросов, соединение всегда закрывается. Добавлены sync/async guard-тесты и real-PG regression загрязнения. Локально: exact `3 passed`, focused `20 passed, 13 skipped`, полный orchestrator `1917 passed, 63 skipped, 15 xfailed`; окончательный real-PG результат подтверждает повторный Linux CI.

## 6. Артефакты и дефекты самой генерации

### G1. Агент исчерпывает шаги до законченного вертикального изменения

Первая несовместимая попытка завершилась после 9 минут 47 секунд и более ста отображённых шагов без публикации. Continue повторно читал значительную часть проекта и только после второго длинного прогона создал v8.

Улучшение:

- до мутаций строить короткий file/schema plan;
- передавать продолжению фактический diff, незавершённые checks и последнюю ошибку;
- не перечитывать неизменённые файлы без нового основания;
- завершать один связный пакет изменений до следующего глобального анализа;
- считать прогресс по изменённым артефактам и закрытым проверкам, а не по числу tool calls.

### G2. Процедурная миграция с `DO` была создана вопреки контракту

Одна попытка сгенерировала миграцию с `DO`; migration contract остановил публикацию. Это безопасный отказ, но лишняя дорогая генерация.

Улучшение: схема инструментов и системный prompt должны сразу выдавать разрешённый профиль миграции. Для простого rename агенту нужен детерминированный template `ALTER TABLE ... RENAME COLUMN ...`, а запрещённые конструкции должны отклоняться до записи файла.

### G3. Успешная сборка не гарантировала доступный preview

v8 была отмечена готовой, но новый preview сразу не открылся. Repair прочитал runtime/health и создал v9; только после повторной проверки v9 стала доступна.

Улучшение:

- успех версии фиксировать только после внешнего signed preview probe;
- предыдущий подтверждённый preview сохранять до нового binding;
- failure card должна содержать точный runtime stage и продолжать с текущего diff;
- repair не должен создавать новую версию, если артефакт не изменился.

### G4. Безопасный fallback preview скрывает свежий отказ

Во время генерации пользователь мог видеть последнюю рабочую версию, а публичный host был временно unpublished/502. Это защищает пользователя от битого кандидата, но затрудняет диагностику.

Улучшение: UI должен явно различать `последняя рабочая версия`, `кандидат собирается`, `кандидат не прошёл runtime`, `новая версия активна`.

### G5. Счётчик шагов после reload нестабилен

В истории наблюдались изменяющиеся итоговые значения шагов для уже завершённых карточек.

Улучшение: terminal attempt summary должен хранить immutable unique event count; live progress и persisted summary показываются отдельно.

## 8. Обязательный порядок завершения

### Этап A. Закрыть кодовый candidate

1. Завершить durable proof intent/replay/lease retention.
2. Вынести MinIO source-manifest I/O за SQL locks и добавить CAS-перепроверку.
3. Обновить Alembic head test и пройти upgrade/downgrade.
4. Исправить golden manifest MAX template и UTF-8 fixtures.
5. Повторить focused и полные suites без конкурирующих DDL-процессов.
6. Выполнить независимый defect-first Astra review всего релевантного diff.
7. Все P0/P1 исправить; P2 исправить либо явно заблокировать выпуск.

### Этап B. Поставить одну совместимую ревизию

1. Убедиться, что `origin/main` не ушёл вперёд и пользовательские файлы сохранены.
2. Зафиксировать только intended API/orchestrator/web/migration/tests/report files.
3. Push в настроенный upstream без force.
4. Убедиться, что нет active `pending/running/cancel_requested` generation runs.
5. Сделать backup PostgreSQL и production configuration.
6. Развернуть API до worker; API выполняет `alembic upgrade head`.
7. Развернуть worker и generation-worker той же ревизии.
8. Собрать immutable public MAX core для этой ревизии.
9. Перезапустить orchestrator на той же ревизии с сохранённым rollback target.
10. Проверить exact SHA, service health, локальные и публичные endpoints, логи и Alembic head.

### Этап C. Повторить несовместимый live E2E

На том же QA-проекте:

1. Подтвердить v9 и обе исходные записи.
2. Подготовить v1 и получить те же два blockers `title/summary`.
3. Нажать `Адаптировать и восстановить` один раз.
4. При неопределённом dispatch повторить штатной кнопкой и доказать один run/одно списание.
5. Доказать, что агент получает candidate с `isolated_copy`, а не live DB.
6. Во время подготовки создать ещё одну подтверждённую запись на source, если writer-barrier протокол допускает этот этап; запись должна войти в S1.
7. Дождаться независимого proof и атомарной активации.
8. Проверить исторические экраны и работу с текущей `summary`-схемой.
9. Проверить обе исходные записи и запись S1 по ID и значениям.
10. Выполнить create, read, update, reload и delete на отдельной синтетической строке.
11. Проверить вторую signed identity: чужие строки не читаются и не изменяются.
12. Перезапустить приложение/среду и повторить чтение.
13. Сверить независимый PostgreSQL witness, proof receipt, version lineage, quota settlement и отсутствие двойных side effects.
14. Проверить cancel до proof, crash после proof и restart во время activation на script-owned тестовом профиле.

## 9. Критерии выпуска MVP

Выпуск разрешён только если одновременно выполнено:

- три ветки decision tree дают ожидаемый результат;
- empty и compatible идут без ИИ;
- incompatible запускает ИИ только после явного действия пользователя;
- агент физически не имеет доступа на запись к live-БД;
- candidate связан с конкретными source/project/owner/run/fencing/digest;
- до proof live runtime и live data не меняются;
- после точки невозврата работает forward recovery;
- повтор запроса, callback или restart не создаёт двойную версию и двойное списание;
- сохранность проверяется по реальным значениям, скрытым полям, связям и owner boundary;
- после активации проходят create/update/reload/delete и restart;
- UI не сообщает «готово» до завершения proof и activation;
- exact production revision, health и живой пользовательский путь подтверждены после deploy;
- в отчёте нет незакрытого P0/P1.

## 10. Что не является доказательством готовности

- зелёный build без живого preview;
- health 200 без CRUD и сохранности значений;
- сообщение агента «готово»;
- наличие snapshot без restore-smoke;
- совпадение списка HTTP method/path без проверки поведения;
- успешная подготовка без активации;

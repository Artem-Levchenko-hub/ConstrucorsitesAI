# MAX prompt preparation

New initial MAX builds can make one optional, non-streaming brief-preparation
request before coding. `PROMPT_PREPARATION_ENABLED=false` disables it. Eligibility
is frozen in new admissions; a rollout never opts old unfinished runs or edits
into a new paid step. Manual retry admissions may reuse preparation, not create
a missing one. Existing prepared execution entries remain byte-for-byte inputs
to continuation.

## Inputs and output

The MAX wizard sends the owner's description once, followed by the selected
scenarios and supplied form values. A management module enables owner tools.
The product checklist derives visitor actions from the description, selected
scenarios, requested features and primary action. The coding agent receives
platform instructions separately. Previously stored wizard messages and
prepared plans retain their original content.

The service receives one owner's description (at most 6,000 characters, with
head/tail retained for longer descriptions) and bounded explicit color, tone,
theme and font preferences. Fenced code in that description is omitted. No
workspace files, source snapshots, project memory, transcript, selected HTML,
image contents/URLs or font assets are loaded into this request. Resolving a
manual retry identifies its single original owner request; it does not send the
intervening conversation.

The instruction asks for a complete structured working prompt: goal, audience,
all essential requested functions and their connections, user flow and visual
direction. Detail follows the task rather than a fixed point or character count.
It borrows owner-first
hierarchy, typography, spacing, useful states and plain copy principles from
frontend-design and Impeccable. The visual part resolves an actual first-screen
composition, main/secondary action relationship, typographic roles and scale,
surface hierarchy, rhythm and color roles from this product and use scene.
The same request checks those choices against the owner's journey before returning
the result. Empty first visits receive deliberate composition without fabricated
records or expanded empty graphs. These are design decisions, not a fixed layout.
It supplies no industry-to-screen mappings,
template catalog, fixed navigation count, palette recipe, screenshot audit or
repair pass. Unknown facts remain unknown.

The unchanged full owner request and platform rules still go to the coding
agent. The note explicitly permits applicable implementation/design suggestions
while preserving the original request's priority. It does not prohibit following
its own design suggestions as "commands", nor grant new functions, privileges,
tools or changes to platform rules. The note is additional user-message data, never a system instruction,
acceptance proof, executable plan or source-file seed. Requested API-only work,
edits, continuations and restoration adaptations create no preparation request.

## First-build design and later preservation

The coder receives a compatible short design method in the MAX stack guide:
choose a product-specific direction, implement it, and compare it with the owner's
main journey inside the existing coding turn. Persist the actual choices in
`DESIGN.md`, retaining typography metadata. This does not install the full external
frontend-design/Impeccable command suites, add a designer/critic model role, inspect
screenshots, or create a visual acceptance gate. Build/HTTP success still must not
be described as visual verification.

On a new MAX build without an explicit font choice, the safe owner-led font is
provisional. The author may choose suitable available local/system typography and
keep manifest, CSS, dependencies and assets consistent. Explicit owner choices are
preserved. Dependency changes require normal runtime permission; otherwise use
available local/system fonts and leave protected files intact.
Ordinary edits, continuations and restoration preserve established
typography and design; the new guidance is not permission to restyle saved work.
No industry font recipes are introduced. Existing cached preparation and frozen
execution entries are not retroactively regenerated by this rollout.

MAX authoring does not offer canned visual-style choices. The initial request
keeps the owner's free description and brand colors; it does not append a
`brand`, `clean` or `bright` style label as an instruction. The existing API/SDK
style enum remains compatibility metadata for saved and already deployed
projects. Unrelated configuration saves preserve its stored value, and that
legacy value alone is not a request to restyle an existing app. No visual preset
gallery, theme registry, automatic theme application or extra prompt-check stage
is introduced.

## Expense and limits

The `prompt_prepare` model role defaults to the existing primary model and can
be configured through `ROLE_MODELS`. The call uses the provider's default output
limit and the configured generation deadline. The cache accepts a complete
response of up to 64,000 characters. An interrupted or truncated response falls
back to the original request. Reusing a saved plan incurs no additional call.

This optional service is included in generation pricing: it does not debit
another generation unit or separately debit the customer's wallet. The client
wrapper explicitly uses generic service billing (`free=true`), preserving the
real owner/project attribution and the `prompt_preparation` expense stage, but
omitting run and message identity. Ordinary coding calls retain their existing
billing and recovery context. Provider costs still belong in the independent
expense journal; `expense_owner=user` denotes attribution, not an extra debit.

The at-most-once guarantee is one **API-to-gateway request** for an owned input
fingerprint. The gateway's existing proven preconnect/refusal handling may
reach a reserve provider; ambiguous accepted requests are not replayed. This
does not promise a single TCP attempt or exactly-once delivery by the provider.

## Durable cache and failures

`generation_runs.agent_state.prompt_preparation_v1` stores a version, input
SHA256, claim UUID, state and bounded result. It stores no second copy of the
description or source code. The key includes the complete description and
preferences, not just the shortened transmitted excerpt. Cache scope is the
same project and owner. A different request/preference can create one new
preparation; a repeat of the same input reuses its saved result.

A short project-scoped advisory lock serializes cache lookup/claim. The claim
commits **before** HTTP. No database lock spans the model request. Successful
output is saved with a claim CAS and JSONB namespace update, preserving other
generation/recovery state. Ownership, messages and running status are checked
again when saving. A prepared execution entry is never retroactively replaced
by a late response.

An existing claimed, unknown, failed or malformed record never causes another
POST. Empty, overlong, timed-out or unavailable preparation falls back to the
original request. Cancellation/crash can leave a claimed record: coding can
continue without the note, and the optional call is not paid again. A response
lost before cache commit may remain unavailable; this deliberately favors
at-most-once expense over guaranteed recovery of an optional note. Raw provider
errors and owner descriptions are not written to application logs.

# Проверка изоляции пользователей MAX — 23 октября 2026

По просьбе владельца проверка выполнена без второго настоящего аккаунта MAX: две синтетические подписанные личности вошли через обычный публичный `/api/max/session` в два существующих QA-приложения. Это проверка серверной защиты, а не доказательство работы двух реальных клиентов MAX.

## Проверенные приложения

- «Заметки»: проект `35fddcca-12d9-43cf-b3d1-68101ac5a2bb`, опубликованный образ `sha256:c6bf8a607c42ca193f7d21ac5372ccfdd5cd13be995b8a4e4c86efe0f7e0276d`.
- «Задачи»: проект `93b184b4-7a86-4050-8157-8d7d97e8d2b3`, опубликованный образ `sha256:b28bb18f288fd04937564e5ba1d1457654e0982bdcf1c0ff2da5073aa2c5a5221`.
- Платформа до исправления: `d7840695488c6a465913dfdea22e28bb7ef738fe`.

## Результаты проверки прав доступа

- У каждой личности до создания записей проверен пустой собственный список.
- Каждый пользователь создаёт, читает в списке, изменяет и удаляет свою запись.
- Обе стороны пробовали изменить и удалить известную существующую запись другого пользователя. Во всех случаях получен 404, а владелец подтвердил неизменность полной записи.
- Поля владельца в JSON, параметры списка и поддельные заголовки не подменили проверенную сервером личность.
- Профиль «Заметок» показывает только собственный счётчик.
- По 24 параллельных чтения в каждом приложении не смешали данные.
- Cookie одного проекта отвергается другим проектом в обоих направлениях.
- Изменённая подпись и конфликтующие cookie двух пользователей дают отказ.
- Переключение набора cookie A → B в API-клиенте меняет доступный набор записей. Работа интерфейса настоящего MAX при смене аккаунта не заявляется.
- Созданы и удалены четыре заметки и две задачи. Отдельный SELECT подтвердил ноль бизнес-строк двух синтетических владельцев после очистки. Служебные записи пользователей и событий открытия, созданные штатным входом, не выдаются за полностью удалённые.

Отдельный GET по ID не реализован в обоих приложениях: 405 для своей и чужой строки не считается доказательством изоляции чтения. Положительное чтение проверено через списки; PATCH/DELETE проверены по реальным ID.

Фактические роли проекта ограничены, без superuser/BYPASSRLS и TRUNCATE. В этих двух старых сгенерированных таблицах RLS выключен; проверенное разделение обеспечивают серверные owner predicates. Успех текущих маршрутов не заменяет проверку будущих изменений кода.

## Найденный недочёт и исправление

Живые персональные ответы `/api/notes` не содержали `Cache-Control`. Фактическая утечка через кэш не наблюдалась. Согласно [RFC 9111, §7.3](https://www.rfc-editor.org/rfc/rfc9111.html#section-7.3), cookie сам по себе не запрещает кэширование.

Доверенная граница теперь заменяет конфликтующие политики кэширования персональных ответов единым `Cache-Control: private, no-store`. Правило действует на API, HTML/RSC, скачиваемые файлы, ошибки, HEAD и вход. Vary, ETag, проверка личности и CSRF сохраняются.

Сохранять публичное кэширование можно только у статических файлов доверенного managed core. Адрес `/_next/static/` сгенерированного приложения сам по себе недостаточен: middleware или иной сервер может вернуть по нему личный ответ. Регрессионный HTTP-тест воспроизвёл этот обход первоначального исключения. До появления проверяемого контракта статических файлов сгенерированные ресурсы также получают `no-store`; это может увеличить объём повторных загрузок.

## Приёмка исправления

Тесты должны воспроизводить отсутствие заголовка до изменения, затем проходить для двух личностей, отсутствующей/публичной/дублирующейся политики upstream, динамических маршрутов и ложного статического адреса. Необходимо отдельно проверить сохранение Vary/ETag и кэширования trusted core static.

Платформенная выкладка сама по себе не доказывает обновление уже работающего published boundary. Для двух QA-приложений нужен поддерживаемый config refresh с сохранением release, кода, данных и конфигурации, затем проверка source hash, заголовков и повторный U/V-прогон.

Повторяемые скрипты и обезличенные receipts находятся вне репозитория: `qa-evidence/actor-isolation-20261023` и `qa-evidence/max-user-isolation-20261023`. Ключи, initData и session cookies сохранены только в приватном каталоге и не входят в отчёт.

## Единый стенд и правило результата

Подготовить без AI на уже разрешённых test fixtures: обычные Studio-владельцы **A/B**, проекты **A1/A2/B1**, настоящие MAX-пользователи **U/V**, synthetic markers `A1-U`, `A1-V`, `A2-U`, `B1-U`. U в A1 и A2 — один человек с разными данными проектов. Дополнительно anonymous, preview A1, preview B1, просроченная/искажённая session. Не использовать повышенную creator/admin роль как единственный happy path. Аккаунты/боты/данные клиентов и чужие provider orders не подходят для отрицательных тестов.

Для каждой строки записать: **expected / actual / pass|fail|partial|blocked|not_run**, время МСК/UTC, platform SHA, app source/build/publication identity, project/run/version, устройство/клиент MAX, безопасные UI/API/log receipts и остаток. Скриншот без контроля состояния хранилища не доказывает сохранение; HTTP 403 без проверки тела не доказывает отсутствие утечки; 200 без собственного positive control не доказывает работоспособность. Credentials/initData/ПДн в публичный evidence не сохранять. Ошибки окружения и skipped PostgreSQL тесты учитывать отдельно.

В каждой изменяемой строке ниже сначала снять baseline, затем выполнить одно действие обычным API/UI, проверить фактическое сохранение и возврат к стенду. Приёмка с платежами, provider side effects, fault injection или clean-host DR — отдельный исполняемый этап; текущий read-only аудит его не разрешает и не исполняет.

## Редкие сочетания, которые нельзя потерять в happy path

- Один U в двух приложениях разных бизнесов; одна session с правильной подписью, но другим project/host/epoch; общий bot-level initData при независимых app-level cookies/данных; numeric IDs с ведущими нулями/очень длинные значения; unsigned `X-Omnia-Actor` и конфликт Cookie/header.
- Ошибка DB после идентификации U, затем V получает то же pooled connection; cancelled transaction и повторённый idempotency key; stale consent после изменения policy между preflight и commit.
- Закрытие вкладки/потеря сети после фактического commit; provider принял заявку, но ответ потерялся; пользователь меняется между UI preflight и POST; повтор не должен менять actor или создавать второй эффект.
- Подключение одного бота в двух проектах во время входа, revoke token при действующей cookie, публикация нового epoch одновременно с restore и открытием старого URL; первая успешная сессия не удостоверяет все последующие.
- Cold/sleeping runtime после срока хранения, restore с renamed table/полями/foreign keys/sequence; частично доступная БД; scratch restore не должен становиться production и не должен писать в live bucket.
- Пустое приложение, приложение без бизнес-данных, shared каталог и private история в одной модели; скрытый фильтр «мои» в UI при публичном API; counts/search/export могут раскрывать больше, чем список.
- Время на границе МСК дня/платного месяца, повтор webhook после plan-version cutover, active paid quota при pending новом checkout; «обновить» не должно начислять повторно.
- Invalid/encoded path, redirects, HTML error body с marker при 403/404, response cache после logout; deny-status недостаточно, если тело или cache раскрывает данные.

## Как закончить этот расширенный прогон

Сначала переоценить исторические GAP-05/06/09 по свежим receipts основного аудита, затем закрыть ISO-01..13 и P0 публикацию/consent на изолированных существующих приложениях. После этого пройти каждую фактическую вкладку и ANA/ACC; внешние эффекты и инфраструктурные drill запускать только в отдельно согласованном объёме. Новую генерацию планировать лишь для capability, которой нет в существующих fixtures.

Финиш — у каждой строки конечный статус и evidence либо точный blocker, у каждого P0/P1 есть владелец/следующее действие. Общее «всё проверено» допустимо только для явно обозначенного принятого набора сценариев и конкретного релиза. На текущем read-only этапе все новые сценарии имеют статус **not_run**, старые результаты сохранены в указанном узком объёме.

## Отдельный source patch по разрешённому пункту 11

После завершения read-only аудита основная сессия передала отдельное разрешённое исправление ограничения MAX-бота. Рабочая правка удаляет глобальный bot-id claim и `UNIQUE(bot_id)` через новую миграцию `0089_shared_max_bots`, сохраняя `UNIQUE(project_id)`, owner checks и шифрование. Connect/verify не меняют другой проект; activate/disconnect удаляют только текущий stored webhook URL. Same-bot rotation использует новый проверенный token; при смене другого бота допустимо пропустить только отказ его уже отозванного ключа, а network/прочие ошибки прерывают изменение. MAX `HTTP 200 / success:false` теперь ошибка без вывода provider body. UI объясняет повторное использование бота вместо требования отключать его в другом проекте.

RED подтверждён до исправления: 6 API regressions воспроизвели global claim, старый token, ignored negative subscription result и преждевременную in-memory смену identity; отдельный wizard regression упал по отсутствовавшему reusable-bot guidance. Дополнительный RED подтвердил потерю active status при идемпотентном reconnect. После правки изолированные API **20 passed**, wizard **21 passed**, targeted API Ruff и mypy прошли. Это local source-проверка без MAX network и без реальной DB; PostgreSQL migration/concurrency/API suite и delivery выполняет основная сессия отдельно. Независимый read-only review основной MAX-правки не нашёл actionable P1/P2; post-review уточнения проверены отдельно. Старые migration0081 tests сохранены как исторический контракт; новая0089 проверяется отдельно. Commit/deploy/live verification этой подзадачей не выполнялись.

Дополнительно: у общего бота общий чат; несколько webhook-подписок могут отвечать на одно `/start` своими app links (`max-miniapp-nextjs/src/app/api/max/webhook/route.ts`). Это не объединение business rows. UI предупреждает про общий чат и предлагает разных ботов для разных чатов. Входной MAX initData удостоверяет bot/user, а не отдельный project; требование ISO-07 уточнено для same-bot случая. Повторное подключение неизменного token сохраняет только уже подтверждённый active status; прежний error становится verified, без выдуманной успешной активации webhook.

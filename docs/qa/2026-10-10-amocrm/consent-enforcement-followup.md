# amoCRM: серверная проверка согласия и поэтапное включение

## Реализация 11 октября 2026

Ниже сохранён первоначальный анализ ревизии `164a40ab`. Новая реализация использует другой вариант: авторитетное состояние и неизменяемые события согласия находятся в PostgreSQL платформы, отдельно для пары проект/MAX-посетитель. Миграция `0085_integration_consent` после `0084_billing_catalog_v3` добавляет три таблицы без изменения прежних записей.

Доверенный Core подписывает чтение и запись события существующим HMAC-контрактом, связывающим проект, посетителя, метод, путь и тело. Запись согласия по одному MAX initData или клиентскому флагу не разрешается. Событие содержит UUID намерения, ожидаемую ревизию, разрешение/отзыв, редакцию и SHA-256 политики. Повтор того же события возвращает историческую квитанцию; он не переписывает текущее состояние. Конфликт ревизии требует явного нового действия пользователя: автоматического повторного разрешения нет. SDK сверяет ответ с текущим состоянием, а не считает любой HTTP 200 новым разрешением.

Перед первой передачей сделки и отдельно примечания проверяется текущее согласие. Новая сделка при отсутствии, отзыве, устаревшей редакции или некорректной политике получает HTTP 403 до загрузки/обновления OAuth credentials и до создания dispatch receipt. Ошибка обновления credentials также оставляет исходный ключ пригодным для безопасной повторной попытки. Уже записанный результат сделки доступен после отзыва без нового обращения к провайдеру. Если при её replay ещё не отправленное примечание запрещено, сделка сохраняет HTTP 200 с `details_status=unknown`; новой передачи примечания нет.

Передача, изменение политики и запись/отзыв согласия используют advisory locks на отдельном соединении PostgreSQL. Блокировка сохраняется между коммитами квитанций. Успешный отзыв возвращается после ранее допущенных передач этого посетителя; последующая передача уже проверяет отозванное состояние. Уже отправленный запрос невозможно отменить отзывом. Получение блокировки ограничено пятью секундами (`consent_busy`, HTTP 503); отмена и освобождение соединения проверяются отдельно. Архив событий платформы является единственным журналом для включённого `personal_data`: старые локальные записи не импортируются как разрешение.

### Обязательные границы выпуска

- Наличие кода в шаблоне не обновляет опубликованные приложения. Требуется собрать новый доверенный Core, подтвердить его неизменяемый image ID и доставить на оба контроллера.
- Без строки политики проект сохраняет прежний режим совместимости. Нельзя утверждать, что все старые приложения уже защищены новой проверкой. Сначала обновляется выбранное демо и проверяется доставка доверенного Core. Затем привилегированно включается политика только этого проекта и выполняется новое явное действие согласия с отрицательным/положительным прогоном MAX. Согласие, записанное локально до включения политики, не принимается как разрешение платформой.
- Редакция и хэш должны соответствовать сохранённому одобренному тексту политики демо; прежние редакции сохраняются. Публичного маршрута включения политики MAX-посетителем нет.
- При проблемах с новым Core новые отправки защищённого проекта приостанавливаются. Откат не должен молча отключать проверку согласия. История и ранее созданные сделки сохраняются.
- Bitrix24 и чтение истории остаются в прежнем контракте. Маркетинговое согласие не заменяет `personal_data`.

### Доказательства и незакрытые проверки

Регрессионные тесты API отдельно проверяют отсутствие, отзыв, устаревшую редакцию с initData и HMAC, чужого посетителя, одну сделку/примечание, безопасный replay и недоступность credentials. Тесты PostgreSQL проверяют порядок событий, CAS, отзыв и изменение политики во время передачи, тайм-аут и отмену блокировок. Контрактные тесты Core проверяют настоящие HMAC, потерю ответа, устаревший отзыв, задержанный grant после revoke и запрет локальной записи при недоступной платформе. Эти тесты добавлены в выпускной контур; результаты конкретной ревизии фиксируются при доставке.

На момент подготовки изменения ещё не подтверждены выкладка этой ревизии, включение политики демо и живой отрицательный/положительный запрос MAX. Изоляция двух независимых CRM и доступ модератора именно в `yalium.amocrm.ru` остаются отдельными проверками. Карточка публичной интеграции находится на проверке и закрыта для редактирования: новый пакет не считается внесённым в неё.

## Первоначальный анализ (сохранён для происхождения решения)

Проверка исходников: 11 октября 2026, базовая ревизия 164a40ab. Только анализ; API, шаблоны, схема БД и HMAC-контракт в этой работе не изменялись. Наблюдение не является заключением о юридическом соответствии всего сервиса.

## Конкретный пробел

`apps/api/src/yleum_api/routers/integration_runtime.py:create_runtime_lead` проверяет MAX-личность, подключение проекта и ключ безопасной отправки, но перед внешней записью amoCRM не проверяет факт действующего согласия посетителя. Запрос с корректной MAX-аутентификацией может миновать клиентский чекбокс. Подпись личности не доказывает согласие.

`apps/orchestrator/templates/max-miniapp-nextjs/src/app/api/omnia/integrations/[...path]/route.ts` удостоверяет личность подписанной сессией либо пересылает MAX initData. Он не читает согласия. HMAC связывает запрос с проектом, посетителем, методом, путём и хэшем тела; `apps/api/src/yleum_api/services/integration_auth.py` проверяет эти значения и срок подписи до 60 секунд. Согласия среди проверяемых полей нет.

Фактические записи согласий находятся в отдельной БД приложения: таблица `max_consents` из `apps/orchestrator/templates/max-miniapp-nextjs/src/lib/db/schema.ts`. `/api/omnia/consents` записывает `max_user_id`, `consent_type`, `granted`, `policy_version`, время и ID. `withMaxUser` устанавливает контекст посетителя для RLS. Записи возвращаются по `created_at DESC, id DESC`. Core API платформы не имеет модели или существующего соединения для чтения этой таблицы; его `LegalAcceptance` относится к пользователю платформы и не заменяет согласие MAX-посетителя.

## Граница доказательств текущего выпуска

В проверенной демоформе подтверждены отказ без согласия, создание заявки, обновление этапа и сохранение истории после повторного открытия. Это не подтверждает отказ прямого API и не доказывает изоляцию двух независимых CRM. Флаг `legal.personal_data_consent` — настройка формы, а не запись волеизъявления. Запись с `policyVersion="1"` не подтверждает содержание показанного текста без сохранённой редакции.

## Минимальная схема для отдельного изменения

1. Определить доверенное место чтения согласия. Возможный вариант — неизменяемый серверный proxy приложения: в `withMaxUser` прочитать последнее `personal_data` текущего MAX-посетителя из БД именно этого проекта. Выбирать последнее событие, включая отзыв, а не последнее положительное согласие. Сравнивать с действующей версией политики приложения; отдельная версия общих документов Yleum для этого не подходит.
2. Передавать результат в проверяемом серверном подтверждении, привязанном к существующим project/actor/method/path/body claims. Клиентские `consent=true`, произвольный ID записи и неподписанные заголовки доказательством не считать. Отсутствие, отказ, отзыв, неподходящая версия или недоступность хранилища должны запрещать новую передачу.
3. Подтверждение должно выпускаться только после реальной проверки БД. Core API обязан проверять его для новой записи amoCRM, включая прямой путь с MAX initData. Один запрет в UI или proxy оставляет прямой путь открытым. Смена HMAC-контракта требует согласованного обновления валидатора и всех поддерживаемых отправителей.
4. Подписанный снимок согласия допускает гонку между отзывом и отправкой в пределах срока подписи. TTL сам по себе не обеспечивает немедленный отзыв. До реализации выбрать требуемую семантику: краткий явно ограниченный срок либо дополнительная актуальная проверка сервером. Не обещать немедленный отзыв при проверке только ранее выпущенного подтверждения.
5. Не вводить правило для Bitrix24 или чтения истории в рамках этой задачи. Ошибка новой заявки без согласия: отдельный стабильный код, например `personal_data_consent_required`, HTTP 403, без вызова провайдера и без занесения заявки в неопределённое состояние.

## Повторы и примечания

`services/integration_operations.py:execute_once` поддерживает `prepare`: сначала возвращает существующий результат по ключу, а проверку вызывает только для новой операции. Это позволяет после отзыва прочитать успешный результат без новой сделки. Проверка после создания dispatch receipt может ошибочно пометить безопасный отказ как неизвестный исход — этого нужно избежать.

Сейчас `_secrets` вызывается до `execute_once` и может обновлять OAuth-токен. Для гарантии «ноль запросов провайдеру при отсутствии согласия» загрузку/обновление credentials нужно расположить после разрешающей проверки, сохранив replay без внешнего вызова. Сам по себе параметр `prepare` не переставляет уже выполняемые до него операции.

Сделка и примечание — две отдельные внешние записи (`lead` и `lead_note`). Повтор успешной сделки способен впервые отправить ещё не записанное примечание; такая передача также требует действующего согласия. Успешную сделку нельзя превращать в повторяемую ошибку, если примечание запрещено после отзыва. Уже записанное примечание не должно отправляться снова. Существующие `unknown`/`dispatching` нельзя автоматически повторять под новым ключом.

Нужна отдельная проверка конкурентного согласия/отзыва, заявок с одним ключом и порядка фиксации состояния. Порядок `created_at, id` при равном времени использует случайный UUID как разрешение совпадений; он детерминирован, но сам по себе не доказывает реальную очередность одновременных событий. Если требуется строгий порядок, его следует обеспечить отдельно.

## Версии и выпуск

Старые опубликованные приложения не передают нового подтверждения. Немедленный обязательный gate на общей платформе остановит их новые заявки. Перед включением нужен список активных приложений, совместимая доставка доверенного proxy, проверка точной версии каждого приложения и план явного перехода. Нельзя считать изменение шаблона обновлением уже опубликованных приложений. Не включать несовместимое изменение в выпуск цен и юридических текстов без этой подготовки.

Сохранять доступные старые редакции политики приложения и связь записи согласия с точным текстом/хэшем. Новая редакция требует новой записи; историю не переписывать. Откат не должен молча включать передачу без согласия; заранее определить, какие новые отправки будут приостановлены при откате.

## Проверки перед заявлением о готовности

- Новая заявка без записи, после отказа, после отзыва и со старой версией: 403; ноль внешних HTTP-запросов и незагрязнённое состояние повтора.
- Чужие actor/project/consent ID, подмена тела, неподписанный клиентский флаг, прямой initData и старое подтверждение: новую передачу не разрешают.
- Разрешённая заявка: одна сделка и одно примечание; двойной клик, конкурентный повтор и потеря ответа не создают дубликатов.
- Отзыв после успешной сделки: чтение результата и истории работает; новой сделки нет; ранее не отправленное примечание не уходит.
- Поздняя положительная запись после отзыва, равные времена, недоступность БД и окно подписанного подтверждения проверены согласно выбранной семантике.
- MAX-сессия и RLS подтверждают нужного посетителя; два независимых проекта/CRM не обмениваются согласием или историей.
- Bitrix24 и чтение истории сохраняют прежнее поведение; опубликованные старые и новые приложения проверены по матрице совместимости.

До выполнения этих проверок допустимое утверждение: «В проверенной форме заявка требует отметки согласия». Недопустимое: «Сервер всегда блокирует передачу в amoCRM без действующего согласия».

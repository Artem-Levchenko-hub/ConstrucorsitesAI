Оба отправления сделаны настоящим UI в одном аккаунте. Это **не проверка двух независимых пользователей**. Предыдущие попытки, при которых браузер не отправил POST и не создал run, не считаются падениями генерации.

В наблюдаемом окне gateway: 9 успешных HTTP 200 и 13 HTTP 502. За 13 ошибками шлюза стоят 10 upstream HTTP 401 и 3 upstream HTTP 429. В ошибочных логах нет run_id: распределять эти статусы между двумя приложениями по догадке нельзя. Успешные ответы ещё были после первой ошибки; после 04:12:36 наблюдались только ошибки.

В существующей авторизованной сессии кабинет LLMGW показал статус ключей **«НЕТ СРЕДСТВ»**. Это подтверждённый операционный блокер. Документация описывает для недостатка средств HTTP 402, а здесь наблюдался 401; точный `error.code/type` тела ответа не получен. Поэтому 401 не объявляется точным кодом отсутствия средств, а ошибка POST — доказательством нулевого расхода или возврата.

Подтверждённые сохранность источников/конфигурации/данных именно после этой пары должны быть приложены отдельно. На момент подготовки этого отчёта такая квитанция ещё не получена. Ошибка сама по себе не доказывает потерю данных. Новые платные генерации остановлены до пополнения провайдера пользователем.

## Что исправляет этот кандидат

**На момент отчётного коммита новая выкладка ещё не подтверждена.** Окончательные SHA, CI, образы и health будут приложены в Conversation соответствующего PR после полного delivery.

- Для обычного nonstream chat gateway сохраняет числовой HTTP-статус провайдера и признак неоднозначного расхода. Внешняя ошибка gateway остаётся 502; секретный текст ответа не передаётся пользователю.
- Legacy-агент прекращает слепые повторы 401/403/429/5xx и неизвестного результата POST. Ограниченные повторы разрешены только при доказанной ошибке **до соединения**. При отмене задача действительно отменяется.
- Остановка не превращается в успех после прежней зелёной проверки. Существующий продукт проходит восстановление источников; первая генерация не отправляется в дополнительный платный ремонт после ошибки провайдера.
- История и интерфейс показывают ошибку провайдера вместо «приложение не прошло проверку»; кнопка повтора скрыта для этой остановки. Запись прогресса отмечена ошибкой и сохраняет только проверенные HTTP-поля, attempt и ambiguity.

Модели, ключи, тарифы, старые квитанции и кошельки не меняются. Native/SSE политика повторов этим изменением не исправляется. Пополнение провайдера оно не заменяет. Миграция БД для этого кандидата не требуется.

Локальные проверки кандидата: весь gateway — **492 passed**, API-затронутые сценарии — **295 passed**, включая реальное сохранение progress на отдельной PostgreSQL 16 и восстановление источников. Ruff и mypy обоих проектов прошли (API 279 / gateway 34 source files). Независимое ревью нашло два P2 в history/progress; они воспроизведены тестами, исправлены и повторно проверены без замечаний. Это тестовый стенд без настоящих вызовов провайдера, production-платежей и клиентских строк. При первоначальном запуске тестовой PG не хватило места в Docker; изолированный повтор на временном томе памяти прошёл, только принадлежащие тесту ресурсы удалены. Полный exact-SHA CI остаётся обязательным перед merge и выкладкой.

## Статистика: не смешивать разные проверки

Историческая серия G01–G11: **33 / 27 completed / 6 failed = 81,8%**, смешанные ревизии. Более поздняя серия двух OAuth-проектов на 8 октября: **18 / 6 completed / 12 failed**, также смешанные ревизии; серия полных функциональных успехов — 0. Предыдущая узкая пара на 69cb: **1/2 completed, 0/2 полностью выполнили запрос**. Последняя пара на 32cac: **0/2 completed** при блокировке провайдера.

Эти серии не складываются в один показатель стабильности текущего SHA. Пересекающиеся тестовые suites также не суммируются как число уникальных проверок. Зелёный rollback не является принятием нового кандидата.

После полного CI и серийной production-выкладки этого кандидата работа в текущем окне завершается отчётом. Новая платная приёмка потребует восстановленного провайдерского доступа и отдельного запуска пользователя. Обещание «весь MVP готов» по имеющимся фактам было бы неверным.
